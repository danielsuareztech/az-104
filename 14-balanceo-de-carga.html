Qué se pregunta acá: el examen casi nunca te pide configurar un balanceador — te da un escenario y te pregunta cuál de los cuatro elegís. Todo se resuelve con dos preguntas: ¿el tráfico es HTTP/S (capa 7) o no (capa 4)?, y ¿el alcance es regional o global? VMs en una VNet/región + Front Door = No (Front Door es global). El resto son detalles de componentes, health probes y limitaciones de SKU.

La matriz de decisión Empezá acá

Azure tiene cuatro servicios de balanceo y se ordenan en una grilla de 2×2: capa 4 vs capa 7 en un eje, regional vs global en el otro. Si internalizás esta grilla, resolvés la mayoría de las preguntas del dominio sin leer el resto del escenario.

Árbol de decisión
  • ¿El tráfico es HTTP/HTTPS?
    • NO (SQL, RDP, SSH, SMTP, UDP, un protocolo propietario) → Azure Load Balancer. Es el único que balancea capa 4 puro dentro de una región.
    • SÍ → seguí a la pregunta de alcance.
  • ¿Cuántas regiones?
    • Una sola región, y necesito routing por URL/path, terminación TLS o WAF → Application Gateway.
    • Varias regiones, y quiero un único punto de entrada que acelere, cachee y aplique WAF global → Front Door.
    • Varias regiones o endpoints fuera de Azure (on-prem, otra nube), y solo necesito que el DNS resuelva al endpoint más sano o más cercano → Traffic Manager.

Azure Load Balancer Capa 4 · regional

Distribuye tráfico TCP y UDP. No inspecciona el contenido: no sabe qué es una URL, una cookie ni un header. Opera dentro de una región y es un recurso de plano de datos pass-through (no es un proxy: no termina conexiones ni cambia el payload).

Público vs Interno (ILB)
  • Public Load Balancer: el frontend es una Public IP. Publica servicios a Internet y además provee conectividad saliente (SNAT) a las VMs del backend pool.
  • Internal Load Balancer (ILB): el frontend es una IP privada de una subnet. Solo accesible desde la VNet, VNets peereadas, VPN o ExpressRoute. Es el patrón típico para la capa de base de datos o de aplicación en una arquitectura de N capas.
ILB: el backend no llega a su propio frontend (hairpin)

Probes OK, VMs healthy, el data port no responde. Una VM del pool intenta el VIP interno del mismo LB.

⚠️ Trampa del examen: backend healthy + data port muerto porque una VM pega al VIP = hairpinning. NSG no lo arregla. Elegí 2: proxy / Nginx o App Gateway.
Los 5 componentes que hay que saber de memoria
  • Frontend IP configuration: la IP (pública o privada) por la que entra el tráfico. Un LB puede tener varias.
  • Backend pool: las VMs, NICs o instancias del VM Scale Set que reciben el tráfico.
  • Health probe: determina qué instancias del pool están sanas. Las instancias que fallan el probe dejan de recibir nuevas conexiones.
  • Load balancing rule: mapea frontend IP + puerto → backend pool + puerto, asociando un health probe. Es el "muchos a muchos".
  • Inbound NAT rule: mapea frontend IP + puerto → una instancia específica y su puerto. Es el "uno a uno", y es la respuesta cuando el escenario pide RDP o SSH a una VM puntual detrás del LB (por ejemplo puerto 50001 → VM1:3389, 50002 → VM2:3389).
4 VMs backend: una sola Public IP + NAT

Cuatro VMs idénticas. Minimizar attack surface, admin y costo. Acceso público puntual (RDP/SSH).

Distribución: hash de 5-tupla y session persistence

Por defecto el Load Balancer usa un algoritmo de hash de 5-tupla: IP origen, puerto origen, IP destino, puerto destino y tipo de protocolo. Como el puerto origen cambia en cada conexión, sesiones distintas del mismo cliente pueden caer en backends distintos.

  • None (default) — hash de 5-tupla. Máxima distribución, sin afinidad.
  • Client IP — hash de 2-tupla (IP origen + IP destino). El mismo cliente siempre va al mismo backend.
  • Client IP and protocol — hash de 3-tupla (IP origen + IP destino + protocolo).
⚠️ Trampa del examen: el Load Balancer no entiende HTTP. Si el escenario menciona enrutar por URL, path, hostname, header o cookie, terminación SSL o WAF, la respuesta nunca es Load Balancer — es Application Gateway (regional) o Front Door (global). La "session persistence" del LB se basa en IP, no en cookies.
Health probes
  • TCP: el probe es exitoso si se completa el handshake TCP contra el puerto. Disponible en Basic y Standard.
  • HTTP: el probe pide una ruta (ej. /health) y espera un HTTP 200. Cualquier otra respuesta, o timeout, marca la instancia como no sana.
  • HTTPS: igual que HTTP pero sobre TLS. Solo en el SKU Standard.
  • Los probes salen siempre de la dirección 168.63.129.16, una IP virtual de la plataforma de Azure. El NSG del backend debe permitir el tráfico entrante desde el service tag AzureLoadBalancer, o todas las instancias van a aparecer caídas.
📍 La IP 168.63.129.16 es la misma que usa el agente de Azure para DHCP, DNS provisto por la plataforma y comunicación de estado. Es una IP virtual fija e idéntica en todas las regiones; no se puede cambiar y no es enrutable fuera de Azure.

Outbound rules y SNAT port exhaustion
  • Cuando una VM sin Public IP propia sale a Internet a través de un public Load Balancer, Azure hace SNAT: traduce la IP privada a la IP pública del frontend y le asigna un puerto SNAT efímero.
  • Cada IP pública de frontend aporta un pool acotado de puertos SNAT que se reparte entre todas las instancias del backend pool. Cuantas más instancias, menos puertos por instancia.
  • SNAT port exhaustion: si las VMs abren muchísimas conexiones salientes simultáneas al mismo destino, se acaban los puertos y las nuevas conexiones fallan con timeouts intermitentes. Es el síntoma clásico: "las conexiones salientes fallan de a ratos, pero el tráfico entrante funciona".
  • Mitigaciones: outbound rules del SKU Standard (asignar más puertos por instancia, agregar más IPs públicas de frontend, subir el idle timeout), usar NAT Gateway (la opción recomendada y la que escala mejor), o darle Public IP de instancia a la VM.
💡 Si la pregunta es "cómo resuelvo problemas de conectividad saliente a escala", la respuesta moderna es NAT Gateway, no agregar IPs al Load Balancer.

Application Gateway Capa 7 · regional

Es un reverse proxy de capa 7: termina la conexión del cliente, lee la request HTTP y decide a qué backend mandarla en función de la URL, el hostname o los headers. Al ser un proxy real, puede terminar TLS, reescribir headers y aplicar WAF.

⚠️ Trampa del examen: Application Gateway requiere una subred dedicada dentro de la VNet. Esa subred no puede contener ningún otro recurso (ni VMs, ni otro tipo de gateway) — solo instancias de Application Gateway. Si el escenario dice "el deployment falla porque la subred ya tiene VMs", la solución es crear una subred nueva y vacía. Se recomienda un /24 para dejar espacio de autoscaling.
SKUs
  • Standard_v2: balanceo L7 completo, autoscaling, zone redundancy, Public IP estática, mejor rendimiento y despliegue más rápido que v1.
  • WAF_v2: todo lo de Standard_v2 más el Web Application Firewall. Es el único SKU que trae WAF.
  • Los SKUs v1 (Standard y WAF) están retirados. En cualquier escenario nuevo asumí v2. Si la pregunta pide autoscaling o zonas, la respuesta es v2 — v1 nunca los soportó.

Features clave que aparecen en escenarios
  • Path-based routing (URL path map): /images/* al pool de contenido estático, /video/* al pool de streaming, /* al pool default. Es la señal de que la respuesta es Application Gateway y no Load Balancer.
  • Multi-site hosting: varios sitios (contoso.com, fabrikam.com) sobre un mismo gateway, cada uno con su listener y su backend pool. Ahorra desplegar un gateway por sitio.
  • Redirección: HTTP → HTTPS, a otro listener, a un path o a una URL externa; permanente (301) o temporal (302).
  • Rewrite: modificar headers de request/response y la URL (path y query string) en vuelo, con condiciones. Sirve para agregar headers de seguridad o sacar headers que filtran información del backend.
  • Cookie-based affinity: el gateway inserta una cookie propia para mandar al mismo usuario siempre al mismo backend. Es session affinity a nivel HTTP — a diferencia del Load Balancer, que solo puede afinar por IP.
  • SSL/TLS offload: el gateway termina TLS y habla HTTP plano con el backend, liberando CPU en los servidores.
  • End-to-end TLS (re-encrypt): el gateway termina TLS, inspecciona, y vuelve a cifrar hacia el backend. Necesario cuando la normativa exige cifrado hasta el servidor final.
  • WebSocket y HTTP/2 soportados en el listener.
🔐 Los certificados del listener se pueden referenciar desde Azure Key Vault, lo que requiere una managed identity en el Application Gateway con permisos de lectura sobre el secreto/certificado.
🛡️
Web Application Firewall (WAF) Add-on, no servicio
⚠️ Trampa del examen: el WAF no es un servicio standalone — no lo desplegás solo. Vive adentro de un Application Gateway con SKU WAF_v2 (protección regional) o de un Front Door Premium (protección global, con managed rule sets). Si una opción de respuesta dice "desplegar un Azure WAF" sin un host asociado, sospechá.
Qué hace

Protege aplicaciones web contra ataques comunes de capa 7: SQL injection, cross-site scripting (XSS), command injection, HTTP request smuggling, inclusión de archivos remotos, etc. La lógica viene del OWASP Core Rule Set (CRS), un conjunto de reglas administrado por Microsoft que se actualiza por versión.

  • Managed rule sets: el CRS de OWASP, mantenido por Microsoft. Elegís la versión del rule set.
  • Exclusiones: sacan de la evaluación atributos puntuales (un header, una cookie, un campo de formulario) que generan falsos positivos, sin desactivar toda la regla.
  • Reglas custom: permitir/bloquear por IP, geografía, header, método, tamaño del body, etc. Las custom se evalúan antes que las managed.
  • Bot protection: ruleset que clasifica bots (buenos, malos, desconocidos) y actúa según categoría.
  • Rate limiting: reglas que limitan la cantidad de requests por cliente en una ventana de tiempo — mitigación de fuerza bruta y de scraping.
ModoComportamientoCuándo se usa
DetectionSolo registra las coincidencias en los logs. No bloquea nada.Onboarding: se activa primero para medir falsos positivos y armar exclusiones antes de cortar tráfico real
PreventionBloquea la request que dispara una regla y la registraProducción, una vez ajustadas las exclusiones
⚠️ Trampa del examen: "protección OWASP en una sola región" → Application Gateway WAF_v2. "Protección OWASP global / en el borde / para varias regiones" → Front Door Premium. Y si el escenario dice "activamos el WAF y se rompió la app": el WAF está en modo Prevention y la solución de diagnóstico es pasarlo a Detection o agregar una exclusión para la regla que da falso positivo, no desactivar el WAF entero.

Azure Front Door Capa 7 · global

Es el application delivery network global de Microsoft: reverse proxy de capa 7 desplegado en los puntos de presencia (POP) del borde de la red de Microsoft, en todo el mundo.

Anycast y el backbone
  • El endpoint de Front Door se anuncia por anycast: la misma IP se publica desde todos los POP, así que el usuario llega automáticamente al POP más cercano por routing de Internet.
  • Desde ese POP, el tráfico viaja al origen por el backbone privado de Microsoft, no por la Internet pública. Eso reduce latencia y jitter aunque el origen esté del otro lado del planeta.
  • El handshake TLS también se termina en el POP (TLS acceleration), así que el RTT del handshake es corto aunque el origen esté lejos.
⚠️ Trampa del examen: 3 VMs en AZs de una VNet / una región + Front Door para repartir conexiones = No. Front Door es el balanceador global (borde, multi-región). Adentro de una región el examen quiere Standard Load Balancer (L4) o Application Gateway (L7). Front Door entra cuando hay varias regiones o un único hostname mundial.

Balanceo y salud
  • Latencia: entre los orígenes sanos, Front Door elige el de menor latencia medida desde el POP (dentro de un margen de sensibilidad configurable).
  • Prioridad: cada origen tiene un valor de prioridad; el tráfico va al de prioridad más alta que esté sano. Es el patrón activo/pasivo.
  • Peso: distribución proporcional entre orígenes del mismo nivel de prioridad. Sirve para canary o blue/green ponderado.
  • Health probes globales: cada POP prueba los orígenes de forma independiente y comparte resultados, así que el failover es rápido y no depende del DNS.
  • Session affinity: mediante cookie, para que un usuario siga pegado al mismo origen.
Bloquear el acceso directo al origen

Si el origen sigue teniendo IP pública, un atacante puede saltearse Front Door (y su WAF) yendo directo. Se cierra con dos controles combinados:

  1. Service tag AzureFrontDoor.Backend en el NSG o en las restricciones de acceso del origen: solo se aceptan conexiones desde el rango de salida de Front Door.
  2. Validar el header X-Azure-FDID contra el Front Door ID de tu perfil. Necesario porque el service tag es común a todos los perfiles de Front Door de Azure, incluidos los de otros tenants — el header es lo que identifica que la request vino de tu instancia.

En Front Door Premium la alternativa más fuerte es Private Link al origen, dejándolo sin endpoint público.

⚠️ Trampa del examen: filtrar solo por el service tag AzureFrontDoor.Backend no alcanza — cualquier perfil de Front Door del mundo sale por ese mismo rango. La respuesta completa es service tag + validación del header X-Azure-FDID.

Traffic Manager DNS · global
📡 Traffic Manager es puramente DNS. Cuando un cliente resuelve miapp.trafficmanager.net, Traffic Manager decide qué endpoint devolver y responde con su CNAME o IP. Después de eso, el cliente se conecta directo al endpoint — el tráfico de la aplicación nunca pasa por Traffic Manager.
Consecuencias directas de ser "solo DNS"
  • No hay SSL/TLS offload, no hay WAF, no hay caching, no hay rewrite de headers ni path-based routing. Nada de eso es posible si no ves el tráfico.
  • El failover depende del TTL. Traffic Manager detecta la caída con sus propios probes y deja de devolver ese endpoint, pero los clientes y resolvers que ya cachearon la respuesta anterior siguen yendo al endpoint caído hasta que expire el TTL. Un TTL bajo acelera el failover a costa de más consultas DNS. Front Door, en cambio, falla sobre la marcha porque termina la conexión.
  • Puede apuntar a cualquier cosa con un nombre o IP: recursos de Azure, servidores on-prem u otra nube.
  • Monitorea la salud de los endpoints con probes HTTP, HTTPS o TCP sobre el puerto y path que definas.

💡 Performance vs Geographic: se confunden todo el tiempo. Performance optimiza latencia (el más rápido, sea cual sea el país). Geographic impone reglas de negocio o legales por país, aunque ese endpoint sea más lento. Si el enunciado menciona regulación, soberanía o "los usuarios de X país deben ir a Y", es Geographic.
Tipos de endpoint
  • Azure endpoints: recursos PaaS o Public IPs de Azure (App Service, Public IP de un LB o de una VM). Traffic Manager conoce su estado de forma nativa.
  • External endpoints: servicios fuera de Azure — on-premises, otra nube, un hosting cualquiera — definidos por FQDN o IP. Es la clave en escenarios híbridos o multicloud.
  • Nested endpoints: otro perfil de Traffic Manager como endpoint de este.

Los perfiles anidados permiten combinar métodos de enrutamiento: por ejemplo un perfil padre con Performance que manda al continente más cercano, y un perfil hijo por continente con Weighted o Priority que reparte entre las regiones de ese continente. Es la única forma de aplicar dos métodos distintos en una misma resolución.

⚠️ Trampa del examen: Traffic Manager no balancea tráfico real, no termina TLS y no puede protegerse con WAF. Si el escenario pide cualquier procesamiento del tráfico (offload de SSL, cache, WAF, routing por path, o failover instantáneo sin depender de la caché DNS), la respuesta es Front Door — no Traffic Manager. Traffic Manager es la respuesta cuando el requisito es protocolo no-HTTP a escala global o endpoints fuera de Azure.

Trampas frecuentes Antes del examen
⚠️ Trampa del examen: "Necesito enrutar /api/* a un pool y /* a otro" con Load Balancer como opción tentadora. El Load Balancer no ve la URL — es capa 4. Nunca es la respuesta a un requisito de routing por path, host o header.
⚠️ Trampa del examen: "Distribuir usuarios entre regiones y hacer SSL offload" → no es Traffic Manager. Traffic Manager es DNS puro: no ve el tráfico, así que no puede hacer offload, cache ni WAF. La respuesta es Front Door.
⚠️ Trampa del examen: App Gateway es regional y Front Door es global. Un App Gateway vive en una VNet de una región y no puede ser el punto de entrada único de un despliegue multi-región. Si el requisito es "un solo hostname que sirva a usuarios de todo el mundo con failover automático", es Front Door.
Checklist final de confusiones
  • Subred dedicada: Application Gateway exige una subred propia y vacía. Compartirla con VMs hace fallar el deployment.
  • SKU matching: Public IP Basic con LB Basic, Public IP Standard con LB Standard. No se mezclan.
  • Standard LB es cerrado por defecto: sin NSG que permita el tráfico, no pasa nada. El Basic era abierto.
  • Probes bloqueados: si todo el backend aparece unhealthy, revisá que el NSG permita AzureLoadBalancer / el rango de probes y que la app responda 200 en el path del probe.
  • WAF no vive solo: WAF_v2 en App Gateway (regional) o Front Door Premium (global).
  • Front Door y Traffic Manager se combinan pero no son intercambiables: Traffic Manager puede tener el endpoint de Front Door como uno de sus endpoints, y Front Door puede apuntar a orígenes que también estén detrás de otros balanceadores. Pero si el requisito toca el contenido del tráfico, solo Front Door sirve.
  • Inbound NAT rule ≠ load balancing rule: NAT rule es uno-a-uno (RDP/SSH a una VM puntual); LB rule es muchos-a-muchos.
  • Fallas salientes intermitentes con LB público = SNAT port exhaustion. Se resuelve con NAT Gateway u outbound rules, no con más health probes.
  • HA Ports (balancear todos los puertos con una sola regla, típico para NVAs) es exclusivo del Standard internal Load Balancer.
  • Autoscaling y zonas en App Gateway solo existen en los SKUs v2.
✅ Estrategia de examen: leé el enunciado buscando tres palabras clave — el protocolo (HTTP/S vs otro), el alcance (una región vs varias vs fuera de Azure) y el requisito extra (WAF, cache, path routing, TLS). Con esas tres, la respuesta es única.
