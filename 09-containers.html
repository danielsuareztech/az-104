El árbol de decisión Pregunta de escenario

Azure tiene cuatro formas de correr un contenedor y el examen vive de confundirlas. Leé el enunciado buscando las palabras gatillo: "tarea que corre una vez", "sin gestionar infraestructura", "escala a cero", "control total del scheduler", "una sola app web".

Kubernetes completo
  • App Service: no es un orquestador. Es el host de una app web que puede ser un contenedor. Gana cuando el enunciado pide slots, custom domain, TLS gestionado o backup de App Service. Detalle operativo (puerto, CI del webhook) está en 10 · App Service.
  • ACI: el runtime más chico. Un container group (análogo a un pod), sizing fijo, sin autoescalado ni ingress gestionado. Gana en jobs, batch y “mínimo esfuerzo administrativo”.
  • Container Apps: orquestación opinada: réplicas, KEDA, scale-to-zero, revisions, ingress con TLS. No te dan la API de Kubernetes.
  • AKS: vos operás el scheduler, los node pools y los objetos de Kubernetes. Máximo control, máximo trabajo. Fuera del outline vigente; aparece como distractor cuando el escenario pide “mínimo esfuerzo”.
⚠️ Trampa del examen: si el escenario dice "mínimo esfuerzo administrativo" y "una única ejecución" o "trabajo por lotes", la respuesta es ACI, no AKS — aunque la pregunta mencione varios contenedores. Un container group de ACI ya te da varios contenedores juntos sin cluster.
ℹ️ Los cuatro servicios pueden tirar de la misma imagen en ACR. El registry es transversal: la pregunta de "dónde corre" es independiente de la de "dónde está la imagen".
💡 Segundo filtro, cuando el escenario ya descartó App Service: ¿la carga tiene que escalar sola? ACI no autoescala — el sizing del container group es fijo. Container Apps escala réplicas con KEDA y llega a cero. AKS escala réplicas y nodos. El detalle está en Container Apps y en Sizing y escalado de contenedores.

Administrar el registry (portal y CLI)

El skill medido es create and manage, no solo crear. En el portal: Create a resource → Container Registry — nombre alfanumérico, SKU, región, networking. Después del primer push aparece Repositories con tags.

  • Lock de un tag/manifiesto: impide borrar o untaguear esa versión. Si el enunciado dice “que nadie borre la imagen de producción” → lock, no un SKU más caro.
  • Retention policy (Premium): limpia manifiestos sin tag después de N días. No borra los tags que siguen apuntando a una versión.
  • Anonymous pull: se puede habilitar para que un registry público no pida auth. En un ACR privado de empresa, déjalo apagado.
  • Borrar un tag no borra el manifiesto si otro tag lo referencia; az acr repository delete / purge sí libera storage.

  • AcrPull — bajar imágenes. Es el rol de las identidades que corren cargas (AKS, ACI, App Service).

Cómo tira cada runtime de ACR Misma imagen, distinta auth

El registry es transversal. Lo que cambia es quién se autentica al hacer pull. La respuesta correcta casi siempre es managed identity + AcrPull; admin user e imagePullSecret son el atajo de lab y el distractor de examen.

RuntimeCómo se engancha al ACRQué rol / credencial
App Service Deployment Center → Container, o app settings DOCKER_REGISTRY_SERVER_*. Con identidad: asignás la managed identity de la web app al registry. Identidad de la app con AcrPull. Admin user + password en settings es el camino viejo. CI: webhook del ACR + DOCKER_ENABLE_CI=true (detalle en el módulo 10).
ACI --assign-identity al crear el container group, o usuario/password del registry. En portal: Image source = Azure Container Registry. La identidad del group con AcrPull. Usuario/password = admin user o token. No hay --attach-acr para ACI.
Container Apps --registry-server + --registry-identity system (o user-assigned) en el create/update de la app. La identidad de la app con AcrPull. Las credenciales del registry son application-scope: cambiarlas no crea revision.
AKS az aks create --attach-acr o az aks update --attach-acr. Engancha la kubelet identity (no la del control plane) al registry. AcrPull sobre esa identidad. imagePullSecret solo si el nodo no puede usar Entra ID (cluster externo, air-gap).
⚠️ Trampa del examen: “la web app / el container group / el pod no baja la imagen” y las opciones mezclan servicios. AcrPull va en la identidad que corre la carga, no en la tuya de administrador. az acr login autentica tu Docker local, no al runtime. Y --attach-acr es verbo de AKS, no de ACI ni de App Service.

Webhooks del registry
  • Se disparan ante eventos de push de imagen, delete, push de chart de Helm o cambio de quarantine.
  • Hacen POST a una URL (Logic App, Function, App Service, pipeline) → así se arma el CD: se pushea la imagen y el destino se redepliega.

ℹ️ Distinción fina que el examen aprovecha: ACR Task = automatiza el build (CI). Webhook = notifica que algo pasó en el registry (CD). Si la pregunta dice "reconstruir la imagen cuando se actualice la imagen base" → base image update trigger. Si dice "avisar a un sistema externo cuando se pushee una imagen" → webhook.

Azure Container Instances (ACI) Container groups
Container group — la unidad de despliegue
  • Uno o más contenedores que comparten ciclo de vida, red (misma IP y espacio de puertos), volúmenes y el nodo subyacente. Es el análogo del pod de Kubernetes.
  • Los multi-container groups solo soportan Linux. Con Windows, un contenedor por group.
  • Como comparten la IP, dos contenedores del mismo group no pueden exponer el mismo puerto.
  • Sizing: se piden CPU y memoria por contenedor; el group consume la suma. La facturación es por segundo sobre vCPU y memoria solicitadas.
  • Se despliega por CLI/portal o con una plantilla ARM / archivo YAML de container group.
Restart policyComportamientoUsalo para
Always defaultReinicia siempre que el contenedor se detenga, sin importar el exit code.Servicios de larga duración.
OnFailureReinicia solo si termina con código distinto de cero.Jobs que deben completarse aunque fallen intentos.
NeverNunca reinicia; el group queda en estado Terminated al terminar.Batch que corre una sola vez. Es la respuesta clásica.
Configuración y datos
  • Environment variables normales, visibles en las propiedades del container group.
  • Secure environment variables: el valor no se muestra en el portal, en az container show ni en los logs. Para connection strings y passwords.
  • Volúmenes montables: Azure Files share (persistente, el único que sobrevive al contenedor), emptyDir (efímero, compartido dentro del group), secret (archivos en memoria), gitRepo (clona un repo al arrancar).
  • ACI no tiene disco persistente propio: si necesitás persistencia, es Azure Files.
Networking
  • Público: IP pública con DNS name label opcional → FQDN <label>.<region>.azurecontainer.io. El label debe ser único dentro de la región.
  • Privado: despliegue en una subred delegada a Microsoft.ContainerInstance/containerGroups. Ahí el group recibe IP privada de la VNet y no tiene IP pública ni FQDN; se lo alcanza desde la VNet o vía VPN/ExpressRoute.
  • Una subred delegada a ACI no puede alojar otro tipo de recurso.
⚠️ Trampa del examen: "el container group debe ser accesible solo desde la VNet" → subred delegada, y perdés el DNS name label y la IP pública. No podés tener las dos cosas: o IP pública con FQDN, o despliegue en VNet. Si la respuesta ofrece "asignar un NSG a la IP pública para restringir", es distractor.
Pull desde ACR y creación en portal
  • Portal: Create a resource → Container Instances. Image source puede ser Quickstart (imagen de Microsoft), ACR, Docker Hub u Other. El skill dice “in the Azure portal”: esperá una pregunta de dónde elegir la imagen y la restart policy.
  • Con ACR privado, el camino correcto es managed identity del container group + AcrPull (--assign-identity en CLI). Usuario y password del admin user funcionan, pero son el distractor de producción.
  • Windows y Linux no se mezclan en el mismo container group. GPU se pide al crear (SKU de compute); no se “activa después”.
az container create -g miRG -n miGrupo \
  --image miRegistro.azurecr.io/miapp:v1 \
  --assign-identity \
  --acr-identity [system] \
  --cpu 1 --memory 1 --restart-policy Never

Después: asignar AcrPull a la principalId que devuelve el create. Sin eso, el group queda en Waiting / no baja la imagen.

💡 az container logs te da el stdout del contenedor y az container exec --exec-command "/bin/bash" te abre una shell adentro. Son los dos comandos de troubleshooting que aparecen.

Azure Container Apps Serverless + revisions

Container Apps es el punto medio entre ACI y AKS: por abajo corre Kubernetes con KEDA, Envoy y Dapr, pero no te expone la API de Kubernetes. No hay nodos, ni node pools, ni kubectl, ni un cluster que parchear. Vos desplegás una app y elegís cuántas réplicas puede tener.

Environment — el límite de seguridad
  • El environment es el borde seguro que envuelve a una o más container apps (y jobs). Es el análogo gestionado del "cluster": el runtime se ocupa de upgrades del SO, failover y balanceo de recursos.
  • Portal: Create a resource → Container App. El wizard crea el environment (o reusa uno) y pide imagen, ingress y réplicas. El skill medido enfatiza el portal: esperá elegir environment, imagen (ACR/Docker Hub) e ingress external/internal.
  • Las apps del mismo environment comparten: la misma virtual network, el mismo Log Analytics workspace y la configuración de Dapr. Además se descubren entre sí por nombre de app.
  • Corolario de examen: si dos cargas tienen que estar aisladas de verdad, van en environments distintos. Poner dos apps en el mismo environment es una decisión de red y de logging, no solo de organización.
  • Dos tipos: workload profiles (el default; admite planes Consumption y Dedicated) y consumption-only (legacy, solo Consumption).

El environment de Container Apps exige un Log Analytics workspace. En Bash hay dos fallos distintos: el comando no existe, o el provider no está registrado.

Revisions — versionado inmutable
  • Una revision es un snapshot inmutable de una versión de la app. No se edita: se crea otra.
  • Cambios revision-scope (van en properties.template) → crean revision nueva: imagen del contenedor, CPU/memoria, variables de entorno, scale rules, revision suffix.
  • Cambios application-scope (van en properties.configuration) → NO crean revision: ingress y división de tráfico, valores de secrets, credenciales del registry, config de Dapr, el propio revision mode.
  • Nombre: <app>-<revision-suffix>. Por default se retienen 100 revisions inactivas, que no se facturan.
Revision modeComportamientoEscenario del examen
Single default Una sola revision activa. La nueva se aprovisiona, escala y recién cuando está lista se lleva el 100% del tráfico; la vieja se desaprovisiona. "Desplegar sin downtime, sin manejar versiones."
Multiple Varias revisions activas a la vez y traffic splitting por porcentaje entre ellas. Vos activás y desactivás a mano. "Mandar el 20% del tráfico a la versión nueva", A/B testing, blue-green, rollback instantáneo moviendo el tráfico.
Regla mental: si el enunciado dice porcentaje de tráfico, canary, A/B o blue-green → hay que pasar la app a multiple revision mode. En single revision mode no existe la división de tráfico, por más revisions que tengas.
Ingress
  • External: FQDN público, alcanzable desde internet. Internal: solo desde apps del mismo environment (el FQDN no resuelve para afuera). Deshabilitado: sin FQDN; igual la alcanzan otras apps del environment por nombre.
  • No hace falta crear load balancer ni IP pública: el ingress viene con el environment.
  • HTTP: TLS termination en el ingress (TLS 1.2 o 1.3), puertos 80 y 443, y el 80 redirige automáticamente a 443. Soporta HTTP/1.1, HTTP/2, WebSockets y gRPC.
  • TCP: para protocolos que no son HTTP (Redis, por ejemplo). El TCP externo requiere que el environment esté en una virtual network.
  • --target-port es el puerto dentro del contenedor al que se rutea. Extras: IP restrictions, session affinity, CORS, client certificates (mTLS) y auth integrada.
Identidad, secrets y ACR
  • Managed identity system-assigned o user-assigned, igual que en el resto de Azure. Se usa para hacer pull desde ACR asociando la identidad al registry en la config de la app — la identidad necesita AcrPull. Sin admin user, sin secretos de registry.
  • Secrets: se definen a nivel de aplicación, no de revision, y varias revisions pueden referenciar el mismo. Se consumen desde variables de entorno, volume mounts y también desde las scale rules.
  • Cambiar o borrar un secret no impacta solo por cambiarlo: hay que desplegar una revision nueva o reiniciar la activa para que tome el valor.
  • Key Vault references: se apunta a la URI del secreto y la managed identity necesita el rol Key Vault Secrets User. Si la URI no fija versión, la app toma la última sola y reinicia las revisions activas.
Jobs — corre y termina, sin ingress
  • Una container app es un servicio de larga duración (HTTP/TCP, réplicas, ingress). Un job es un contenedor que arranca, hace el trabajo y termina: no tiene ingress ni traffic splitting.
  • Tres disparadores: manual, scheduled (cron) y event-driven (KEDA, igual que las apps: cola, Event Hubs, etc.).
  • ¿ACI con Never o Container Apps Job? Si el enunciado pide una sola ejecución, mínimo esfuerzo, sin environment → ACI. Si pide cron recurrente, scale-out por mensajes de cola, o convivir con otras apps del mismo environment → Job de Container Apps.
Dapr — opcional, por encima
  • Se habilita por app y corre como sidecar; los componentes de Dapr se definen a nivel de environment y se comparten entre las apps de ese environment.
  • Da service invocation (llamarse por nombre de app), pub/sub, state store y bindings sin acoplarse al SDK del backend.
  • Letra chica: con Dapr actors no se soporta escalar a cero.

Sizing y escalado de contenedores ACI vs Container Apps

Objetivo explícito del examen. La clave es una sola frase: ACI no escala; Container Apps sí. Todo lo demás es detalle de esa asimetría.

ACI — sizing fijo, cero autoescalado
  • Se piden CPU y memoria por contenedor y el container group consume la suma de los requests. El mínimo del group es 1 vCPU y 1 GB.
  • Además del resourceRequest (obligatorio) se puede fijar un resourceLimit opcional, que puede superar el request hasta el total asignado al group. Sin límite, el máximo de uso es el request.
  • Máximos por container group: 31 vCPU y 240 GB de memoria, también cuando se despliega en VNet. Son límites duros, no se suben por ticket de cuota.
  • ACI no tiene autoescalado ni métricas que agreguen réplicas. No hay "scale out" del group ni nada parecido al HPA.
  • El sizing se define al desplegar: cambiar CPU o memoria de un group existente implica volver a desplegarlo.
  • Para absorber más carga con ACI: desplegar más container groups y balancear por delante, o mover la carga a algo que orqueste (AKS con virtual nodes, o Container Apps).
Restart policy ≠ escalado. Always, OnFailure y Never definen el ciclo de vida del container group — si se reinicia al terminar y si queda en Terminated —, no cuántas instancias hay. Un job con Never sigue siendo una instancia. Si una opción de respuesta propone "cambiar la restart policy para manejar más carga", es distractor.
Container Apps — escalado horizontal con KEDA
  • El escalado es horizontal, en réplicas, y lo maneja KEDA a partir de scale rules declarativas. Cada revision tiene sus propios límites y reglas.
  • Límites por revision: min replicas default 0, max replicas default 10; el rango soportado va de 0 a 1000.
  • Si no definís ninguna scale rule, se aplica la regla por default: HTTP, min 0 / max 10.
  • No hay escalado vertical. Cambiar CPU o memoria del contenedor es un cambio revision-scope: genera una revision nueva.
  • Agregar o editar una scale rule también crea una revision nueva, así que distintas revisions pueden convivir con reglas distintas.
Scale ruleEn qué se basaParámetro claveEscenario
HTTP Requests HTTP concurrentes por réplica concurrentRequests default 10 API o front web. Es la regla por default de toda app con ingress.
TCP Conexiones TCP concurrentes concurrentConnections default 10 Servicios que no hablan HTTP.
Custom · CPU Uso de CPU type: cpu + utilización objetivo Carga CPU-bound (procesamiento, transcoding).
Custom · memoria Uso de memoria type: memory + utilización objetivo Carga memory-bound.
Custom · event-driven Cualquier scaler de KEDA: Azure Service Bus, Event Hubs, Kafka, Redis, colas… Ej. azure-servicebus + queueName + messageCount Worker que consume una cola: "escalar según la cantidad de mensajes pendientes". Es la respuesta clásica.
Cómo se comporta el escalado
  • HTTP y TCP se calculan cada 15 segundos sobre lo ocurrido en esos 15 segundos.
  • Las reglas custom se consultan con un polling interval default de 30 segundos y un cool-down default de 300 segundos antes de escalar hacia abajo.
  • Fórmula de KEDA: réplicas = ceil(valor actual / valor objetivo). Con messageCount: 5 y 50 mensajes en cola → 10 réplicas.
  • Las réplicas son un objetivo, no una garantía.
Scale to zero y su precio oculto
  • Con minReplicas: 0 la app baja a cero réplicas cuando no hay actividad y no se factura consumo. Es el argumento de venta de Container Apps frente a AKS y App Service.
  • El costo es el cold start: la primera request después del reposo tiene que esperar a que se levante una réplica. Si el escenario pide latencia predecible o sin cold start, la respuesta es min replicas ≥ 1, no una scale rule distinta.
  • El plan Dedicated (workload profile) no escala a cero: se paga la instancia del profile aunque no haya réplicas.
⚠️ Trampa del examen: si dejás minReplicas: 0 en una app sin ingress y sin ninguna scale rule, la app escala a cero y no queda nada que la despierte. Para una carga sin HTTP (un worker de cola) tenés que definir la scale rule event-driven o poner minReplicas en 1 o más. Y no confundas escalas: en Container Apps se escalan réplicas, nunca nodos — nodos es vocabulario de AKS.

AKS — arquitectura Fuera del outline
ℹ️ Desde el skills measured de abril 2026, AKS no se evalúa. Estas tres secciones quedan para reconocer distractores (“mínimo esfuerzo” nunca es AKS) y para el mapa mental. Operar el cluster con kubectl está en 23 · AKS operativo (complementario).
Qué es y cómo se crea
  • AKS es Kubernetes con el control plane gestionado por Microsoft. Vos pagás y administrás los nodos (VMs). No instalás etcd, ni el API server, ni kubeadm.
  • Portal: Create a resource → Kubernetes services. Basics (RG, nombre, región, tamaño y cantidad de nodos) → Node pools → Networking (kubenet vs Azure CNI, se elige acá y no se cambia después) → Integrations (enganchar ACR) → Review + create.
  • CLI: az aks create. Lo mínimo de examen/lab: node count, network plugin, --attach-acr, --enable-managed-identity.
az aks create -g miRG -n miAKS --node-count 2 \
  --network-plugin azure --attach-acr miRegistro \
  --enable-managed-identity --generate-ssh-keys

Node pools
  • Cada node pool se respalda en un Virtual Machine Scale Set: de ahí sale el escalado y las actualizaciones por lotes.
  • Dentro de un pool todos los nodos son del mismo tamaño de VM y del mismo SO. ¿Necesitás VMs con GPU o memoria alta para una carga puntual? Agregá otro node pool, no cambies el existente.
  • Se etiquetan con labels y taints para dirigir pods a un pool específico.
⚠️ Trampa del examen: "necesitamos correr contenedores Windows en AKS". Nunca es "crear un cluster con system pool de Windows" — el system pool siempre es Linux. La respuesta correcta es agregar un user node pool con Windows (az aks nodepool add --os-type Windows) a un cluster que ya tiene su system pool Linux.

AKS — escalado Fuera del outline

Esta es la pregunta de AKS en el AZ-104. Todo se reduce a distinguir qué escala cada mecanismo.

MecanismoQué agrega/quitaDisparadorEscenario
Escalado manual
az aks scale / nodepool scale		 Nodos Vos, a mano Carga previsible; ajuste puntual de capacidad.
Cluster Autoscaler Nodos Pods en estado Pending por falta de recursos; nodos infrautilizados. "Los pods no arrancan porque no hay capacidad en el cluster" → agrega nodos entre --min-count y --max-count.
Horizontal Pod Autoscaler (HPA) Pods (réplicas) Métricas: CPU, memoria o custom metrics. "La app necesita más réplicas cuando sube el CPU" → objeto de Kubernetes, se define con kubectl/manifiesto.
Virtual nodes (sobre ACI) Pods en ACI, sin nodos nuevos Pods programados al nodo virtual. Burst rápido: no hay que esperar el arranque de una VM, los pods van directo a ACI en segundos.
Cluster Autoscaler y HPA son complementarios: el HPA crea réplicas, esas réplicas quedan Pending si no hay lugar, y eso es lo que despierta al Cluster Autoscaler para sumar nodos. Si la pregunta dice "más réplicas" → HPA. Si dice "más nodos" o "capacidad del cluster" → Cluster Autoscaler.
Virtual nodes — letra chica
  • Se basan en el proyecto Virtual Kubelet y ejecutan los pods en ACI, no en VMs del cluster.
  • Requieren Azure CNI y una subred delegada a ACI. No funcionan con kubenet.
  • Solo pods Linux. No sirven para cargas que necesiten DaemonSets ni acceso a la red virtual del nodo.
⚠️ Trampa del examen: "el tráfico se dispara de golpe y hay que absorberlo en segundos". El Cluster Autoscaler tiene que aprovisionar una VM (minutos), así que la respuesta es virtual nodes / ACI. Si en cambio el escenario habla de crecimiento sostenido y costos, es Cluster Autoscaler.

Identidad y control de acceso
  • Managed Identity del cluster: es con la que AKS habla con Azure (crear load balancers, discos, hacer pull de ACR). Es la que necesita AcrPull.
  • Integración con Entra ID: los usuarios se autentican con su cuenta corporativa y se mapean a roles de Kubernetes. Dos sabores: Kubernetes RBAC (RoleBinding a grupos de Entra) o Azure RBAC for Kubernetes Authorization (permisos asignados como roles de Azure).
  • Workload Identity: le da identidad de Entra a los pods para que accedan a Key Vault, Storage, etc., sin secretos.
  • Network Policies: firewall entre pods (este namespace no habla con aquel). Se habilitan al crear el cluster.
  • Ingress: un solo punto de entrada HTTP/S con ruteo por host y path y terminación TLS, en vez de un Service tipo LoadBalancer (y una IP pública) por app.
Upgrades
  • az aks upgrade actualiza control plane y node pools; se puede actualizar solo el control plane con --control-plane-only.
  • El control plane se sube de a una versión minor por vez y los node pools no pueden estar en una versión superior a la del control plane.
  • az aks nodepool upgrade --node-image-only actualiza la imagen del nodo (parches del SO y runtime) sin tocar la versión de Kubernetes.
  • Max surge: nodos extra que se crean durante el upgrade para no perder capacidad. Se expresa en número o porcentaje; más surge = upgrade más rápido y más caro. El proceso es cordon + drain nodo por nodo (por lote).
  • Ver versiones disponibles: az aks get-upgrades.
