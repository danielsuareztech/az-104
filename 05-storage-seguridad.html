Las tres formas de autorizar Base

Toda request al plano de datos de una Storage Account se autoriza de una de tres maneras. Sabé cuál elegir según el escenario.

MétodoCómo funcionaGranularidadCómo se revocaRecomendado
Access Keys (Shared Key) Dos claves de 512 bits (key1 / key2) que dan acceso total a todos los servicios de la cuenta Ninguna: todo o nada Rotando la clave Evitar
SAS token URI firmado con permisos, ventana de tiempo y alcance acotados Alta: servicio / container / blob, permisos y tiempo Depende del tipo (ver más abajo) Acceso delegado
Entra ID + RBAC Token OAuth 2.0 de Entra ID; el acceso lo define un rol de datos asignado a un usuario, grupo, service principal o managed identity Identidad + scope de Azure Resource Manager Quitando la asignación de rol Microsoft recomienda
Por qué Entra ID es la opción recomendada
  • No hay secreto que se filtre: no guardás ninguna clave en código ni en config.
  • Soporta MFA, Conditional Access, PIM y revocación instantánea de la identidad.
  • El acceso queda auditado por identidad, no por "alguien con la key".
  • Con managed identities la app se autentica sin credenciales de ningún tipo.
Rotación de access keys — el patrón de las dos claves

La cuenta tiene exactamente dos keys (key1 / key2), no tres. Cualquiera de las dos da acceso total. Existen dos para poder rotar sin cortar el servicio: siempre hay una “de recambio” que nadie está usando.

Regla: nunca regenerés la key que las apps están usando. Regenerar invalida esa clave al instante → las connection strings viejas mueren.

Escenario de examen: apps en key1, key2 de backup, las dos pueden estar comprometidas, cero downtime. Cinco acciones:

#AcciónPor qué ese orden
1Regenerar key2 (la que nadie usa)Obtenés un recambio limpio sin tocar producción. Si migraras primero a key2, pondrías las apps sobre una key también filtrada
2Actualizar connection strings a key2Ahora las apps corren con la key limpia. key1 queda libre para rotarla
3Regenerar key1Invalida la key comprometida que estaba en producción. Las apps ya no la usan, no hay corte
4Volver las connection strings a key1Estado recomendado: apps en primary, secondary de backup
5Verificar + regenerar key2 otra vezkey2 se usó en el corte (pasos 2–4) y además estaba comprometida al inicio. El backup tiene que quedar limpio y sin uso

az storage account keys renew -g rg1 -n cuenta --key primary     # key1
# PS: New-AzStorageAccountKey -Name cuenta -ResourceGroupName rg1 -KeyName key2

⚠️ Trampa del examen: “ambas keys comprometidas + sin interrumpir” = regenerar primero la que nadie usa (key2), saltar las apps ahí, regenerar key1, volver a key1, y rotar key2 de nuevo. No hay key3. Regenerar la key en uso = outage. Docs de rotación periódica (sin leak) a veces empiezan “switch to key2”; acá el leak obliga a limpiar el recambio antes de saltar.
CLI: rotar keys de storage1 sin cortar app1

App Service lee la key de un app setting. keys list: índice [0] = primary, [1] = secondary.

key=$(az storage account keys list -g rg1 -n storage1 --query [1].value)
az webapp config appsettings set -g rg1 -n app1 --settings STORAGE_ACCOUNT_KEY=$key
az storage account keys renew -g rg1 -n storage1 --key primary
key=$(az storage account keys list -g rg1 -n storage1 --query [0].value)
az webapp config appsettings set -g rg1 -n app1 --settings STORAGE_ACCOUNT_KEY=$key
az storage account keys renew -g rg1 -n storage1 --key secondary
⚠️ Trampa del examen: drop-down = [1].value → --key primary → [0].value → --key secondary. Si renovás primary mientras la app todavía lo usa, hay corte.
⚠️ Trampa del examen: regenerar una access key invalida inmediatamente todos los Service SAS y Account SAS firmados con esa clave, porque están firmados con ella. No invalida los User delegation SAS (esos van firmados con una user delegation key de Entra ID). Si la pregunta dice "revocar un SAS sin afectar a las demás aplicaciones", rotar la key es la respuesta incorrecta.

Stored Access Policies Revocación

Una stored access policy es un conjunto de permisos + fechas guardado en el recurso contenedor, no en el token. Un Service SAS que la referencia (si=nombre) hereda esos valores en lugar de traerlos escritos en la URL.

Dónde se definen
  • Blob container · File share · Queue · Table
  • Máximo 5 policies por container / share / queue / table.
  • Solo aplican a Service SAS. Un Account SAS o un User delegation SAS nunca las usa.
Regla de oro: borrar la policy, renombrarla o adelantar su fecha de expiración invalida al instante todos los Service SAS que la referencian. Es la única forma de revocar un Service SAS sin regenerar la account key (y sin romper el resto de las aplicaciones que dependen de esa key).
Necesitás…HacéEfecto colateral
Revocar un Service SASBorrar o modificar su stored access policyNinguno en otros SAS
Revocar un Service SAS sin policyRegenerar la account key con la que se firmóRompe todos los SAS y apps con esa key
Revocar un Account SASRegenerar la account key (no hay otra)Rompe todo lo firmado con esa key
Revocar un User delegation SASRevoke User Delegation Keys o quitar el rol RBACInvalida todos los user delegation SAS de la cuenta
Modificar una stored access policy: Set Share ACL vs Container vs Table

La policy vive en el recurso contenedor del servicio. El examen nombra la operación REST:

OperaciónServicio
Set Share ACLAzure Files (file share)Sí si el enunciado dice file shares
Set Container ACLBlob (container)No — otro servicio. “Public read for blobs” es acceso anónimo, no la policy
Set Table ACLTable StorageNo
Set Queue ACLQueueEl cuarto, si aparece
 
az storage share policy update --share-name datos --name partner-ro \
  --permissions r --account-name mistorage
# REST: PUT .../share?restype=share&comp=acl  (HTTPS, no el montaje SMB)
⚠️ Trampa del examen: stored access policy en file shares = Set Share ACL. Container ACL = blobs. Table ACL = tables. El dump a veces dice “with the SMB protocol”: SMB es cómo montás el share; la policy se escribe por REST/HTTPS (az storage share policy).
⚠️ Trampa del examen: la stored access policy no se puede combinar con lo que ya está en el SAS. Si un parámetro (permisos o expiry) está definido en la policy, el SAS no puede especificarlo también: la request falla con error 400. O lo definís en la policy o en el token, nunca en los dos.

RBAC de plano de datos Entra ID

Los roles de plano de control (Owner, Contributor, Reader) gestionan el recurso Storage Account. Los roles de plano de datos —los que llevan "Data" en el nombre— son los que dejan leer y escribir blobs, files, queues y tables con autenticación de Entra ID.

RolServicioQué habilita
Storage Blob Data OwnerBlob / ADLSAcceso total a containers y blobs, incluida la gestión de POSIX ACLs en Data Lake Gen2
Storage Blob Data ContributorBlobLeer, escribir y borrar blobs y containers
Storage Blob Data ReaderBlobSolo lectura y listado
Storage Blob DelegatorBlobObtener la user delegation key para firmar user delegation SAS (no da acceso a los datos por sí solo)
Storage File Data SMB Share ContributorFiles (SMB)Leer, escribir y borrar sobre file shares por SMB
Storage File Data SMB Share ReaderFiles (SMB)Solo lectura sobre file shares por SMB
Storage File Data SMB Share Elevated ContributorFiles (SMB)Contributor + modificar NTFS ACLs
Storage Queue Data ContributorQueuesLeer, escribir y borrar colas y mensajes
Storage Queue Data Message SenderQueuesSolo encolar mensajes
Storage Queue Data Message ProcessorQueuesSolo hacer peek, recibir y borrar mensajes
Storage Table Data Contributor / ReaderTablesEscritura / lectura de entidades
⚠️ Trampa del examen: el rol Contributor (plano de control) NO da acceso a los datos cuando la autenticación es con Entra ID. Un Contributor que abra un container en el portal con "Azure AD User Account" ve AuthorizationPermissionMismatch. Pero sí puede leer las access keys y entrar por Shared Key. Si la pregunta pide "que puedan leer blobs con su identidad de Entra ID", la respuesta es Storage Blob Data Reader, no Reader ni Contributor. Para tapar el atajo de las keys, deshabilitá Shared Key access.
💡 Las asignaciones de rol de datos se pueden hacer a nivel suscripción, resource group, storage account o container / queue individual. El principio de menor privilegio del examen suele apuntar al scope más chico: el container.
ℹ️ Los cambios de asignación de rol pueden tardar unos minutos en propagarse al plano de datos. Si un escenario dice "asigné el rol y sigue dando 403", esperar/refrescar el token es parte de la respuesta.

Cifrado en reposo SSE
Punto de partida: Storage Service Encryption (SSE) cifra todos los datos en reposo con AES-256, está activo por default y no se puede desactivar. Aplica a Blob, File, Queue y Table, en todos los tiers y tipos de cuenta, sin costo extra. La pregunta nunca es "¿lo activo?", es "¿quién maneja la clave?".

Quién genera y rotaMicrosoftVos, en Key Vault o Managed HSMVos, fuera de Azure

AlcanceToda la cuentaCuenta o encryption scopeSolo Blob, por operación

Customer-managed keys — requisitos que se preguntan
  • El Key Vault necesita Soft delete y Purge protection habilitados. Sin eso, el portal ni te deja seleccionarlo.
  • La Storage Account necesita una managed identity (system-assigned o user-assigned) a la que le des permiso de Get / Wrap Key / Unwrap Key (access policy o el rol Key Vault Crypto Service Encryption User).
  • Podés fijar una versión de clave o usar rotación automática apuntando a la clave sin versión.
  • Si borrás la clave o revocás el acceso al vault, la cuenta deja de servir datos: es exactamente el escenario de "revocación de emergencia".
  • Por default CMK cubre blobs y files; para incluir queues y tables hay que optar por la account-scoped encryption key al crear la cuenta.

Antes de habilitar CMK en todas las cuentas, el examen pide tres acciones:

⚠️ Trampa del examen: CMK = vault/HSM + misma región + MI con wrap/unwrap. “Misma subnet” y “cambiar a LRS/GRS” son carnada de red/redundancia. Soft delete + purge protection del vault siguen siendo prerequisito para seleccionar la key.
Infrastructure encryption y Encryption scopes
  • Infrastructure encryption: agrega una segunda capa de cifrado AES-256 a nivel de infraestructura (doble cifrado) para cumplimiento regulatorio.
  • Encryption scopes: cifrado con clave distinta a nivel de container o blob individual —útil para aislar datos de varios tenants en una misma cuenta—. Cada scope puede usar MMK o CMK. Podés definir un scope default en el container y forzar que se use.
⚠️ Trampa del examen: Infrastructure encryption solo se habilita al crear la Storage Account y después no se puede activar ni desactivar. Si el escenario dice "una cuenta existente necesita doble cifrado", la respuesta correcta es crear una cuenta nueva y migrar los datos, no "ir a Encryption y tildarlo".

Minimum TLS version Rechaza handshakes por debajo de la versión elegida (1.0 / 1.1 / 1.2) Las cuentas nuevas usan TLS 1.2 como mínimo. Subirlo puede romper clientes viejos: es la causa típica del "dejó de conectar"
Allow storage account key access (AllowSharedKeyAccess = false) Deshabilita la autorización con Shared Key y fuerza Entra ID Al apagarlo también dejan de funcionar Service SAS y Account SAS (van firmados con la key). Solo sobreviven los user delegation SAS
Allow cross-tenant replication Permite o bloquea object replication hacia otro tenant de Entra ID Se recomienda dejarlo deshabilitado salvo necesidad concreta. Con policy Deny, un update de una cuenta que lo tenga en true también se bloquea. No se puede pasar a false si hay object replication policies activas: primero borrarlas
Microsoft Defender for Storage Detección de amenazas: subidas sospechosas, accesos desde IPs anómalas, escaneo de malware on-upload y detección de datos sensibles Se activa por suscripción o por cuenta; tiene costo. Es la respuesta cuando piden "alertas ante actividad anómala en la cuenta"
Resource locks (CanNotDelete / ReadOnly) Protegen el recurso a nivel plano de control Un lock no impide borrar blobs con SAS o access keys: eso es plano de datos
ℹ️ Complementos que se cruzan con seguridad: soft delete (blobs y containers) y versioning protegen de borrados accidentales o de un ransomware; immutability policies (time-based retention o legal hold, WORM) impiden modificar o borrar blobs incluso siendo Owner.
Storage Explorer: List/Get Storage Account(s)

Error Read: List/Get Storage Account(s) al loguearse. El user ya es Contributor de la cuenta. Least privilege en la subscription:

Rol en la subscriptionPor qué
ReaderSíLista RGs y cuentas. No escribe. Explorer necesita ver el árbol
Contributor / OwnerNoFuncionan, violan least privilege
Storage Blob Data ReaderNoPlano de datos. No lista cuentas ARM
⚠️ Trampa del examen: Contributor en la cuenta no alcanza para que Explorer arme el árbol de la subscription. El error nombra List/Get Storage Account(s) → control plane de la sub → Reader. Blob Data Reader es el distractor de “storage”.
  1. ¿Quién accede? Identidad de Entra ID → RBAC de datos. Tercero sin identidad → SAS.
  2. Si es SAS: ¿tiene que ser revocable sin rotar keys? → User delegation (blob, ≤7 días) o Service SAS + stored access policy.
  3. ¿Desde dónde? Internet → firewall con reglas de IP. VNet → service endpoint. On-prem o IP privada obligatoria → private endpoint + Private DNS Zone.
  4. ¿Requisitos de cumplimiento sobre la clave? → CMK; doble cifrado → infrastructure encryption al crear.
  5. Cerrar: secure transfer, TLS 1.2, anonymous access off, shared key off.
