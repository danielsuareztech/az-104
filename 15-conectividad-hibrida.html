Qué se pregunta acá: el examen casi nunca te pide configurar un túnel paso a paso. Te tira un escenario —"la sucursal necesita 5 Gbps garantizados", "cambiaron el rango on-prem", "60 branches nuevas"— y te pide elegir el servicio correcto o identificar el único objeto que hay que tocar. Memorizá nombres exactos (GatewaySubnet, Local Network Gateway), qué SKU habilita qué feature, y qué cosas no soporta Basic ni policy-based.
🌐
Panorama: cómo se conecta on-premises con Azure Elegir la opción

Hay cinco piezas que el examen mezcla a propósito. Cuatro son híbridas (on-prem ↔ Azure); una, el peering, es solo Azure a Azure y aparece como distractor en casi todas las preguntas de conectividad híbrida.

OpciónQué conectaTransporteRequisitos claveCuándo la eligen en el examen
Site-to-Site (S2S) VPN Toda una red on-prem ↔ VNet IPsec / IKE sobre internet VPN Gateway en Azure + VPN device on-prem con IP pública (o FQDN) + Local Network Gateway + shared key Oficina/datacenter entero, tráfico moderado, hay que levantarlo ya y barato
Point-to-Site (P2S) VPN Un cliente individual ↔ VNet OpenVPN / SSTP / IKEv2 sobre internet VPN Gateway route-based (no Basic) + address pool de clientes + método de autenticación Teletrabajo, admins remotos, demos. No requiere hardware ni IP pública fija del lado del cliente
VNet-to-VNet VNet ↔ VNet (misma o distinta región/tenant/suscripción) IPsec entre dos gateways Un Virtual Network Gateway en cada VNet + una connection en cada punta Cuando el peering no sirve o se necesita el túnel cifrado por gateway
ExpressRoute On-prem ↔ Azure (y M365) por circuito privado NO pasa por internet — circuito dedicado vía connectivity provider Contrato con el proveedor, service key, routers de borde, ExpressRoute Gateway en la VNet Ancho de banda alto, latencia predecible, SLA, requisitos de compliance ("el tráfico no puede salir a internet pública")
VNet Peering Solo Azure ↔ Azure Backbone de Microsoft, sin gateway Address spaces que no se solapen; no es transitivo por sí solo Distractor. Si la pregunta dice "on-premises", peering nunca es la respuesta
Cómo decidir en 10 segundos
  • ¿Dice "un usuario / laptop / desde casa"? → Point-to-Site.
  • ¿Dice "la sucursal", "el datacenter", "toda la red" y menciona internet o costo bajo? → Site-to-Site.
  • ¿Dice "no debe atravesar internet pública", "latencia predecible", "SLA", "Gbps"? → ExpressRoute.
  • ¿Dice "decenas/cientos de branches", "hub-and-spoke gestionado", "transit routing sin UDRs"? → Virtual WAN.
  • ¿Las dos puntas están en Azure y solo quieren que se vean? → VNet peering (y ojo: puede ser global).
⚠️ Trampa del examen: VNet peering aparece constantemente como opción en preguntas híbridas porque suena a "conectar redes". El peering no puede conectar nada que esté fuera de Azure. Si en el enunciado hay un datacenter, una oficina o un servidor físico, descartá peering de entrada.
ℹ️ Los address spaces no se pueden solapar en ninguna de estas opciones: ni entre VNets peereadas, ni entre la VNet y on-prem en un S2S, ni entre el pool de P2S y lo anterior. Un solapamiento es la causa "correcta" de fallo en muchas preguntas de troubleshooting.

Virtual Network Gateway: la puerta de la VNet GatewaySubnet

El Virtual Network Gateway es el recurso que le da a una VNet una salida híbrida. Internamente son VMs gestionadas por Microsoft que Azure despliega en una subred especial de tu VNet. Vos no las ves ni las administrás.

Requisitos no negociables
  • Una subred llamada exactamente GatewaySubnet. Ese nombre es literal: no acepta gatewaysubnet, GW-Subnet ni nada parecido, y si no existe con ese nombre el deployment falla.
  • Tamaño: /27 o más grande es lo recomendado. Con /29 o /28 te podés quedar sin direcciones al escalar, al pasar a active-active o al agregar coexistencia VPN + ExpressRoute, que consumen más IPs.
  • Al menos una Public IP asociada al gateway (dos si es active-active). ExpressRoute Gateway también usa una Public IP para su gestión interna, aunque el tráfico del circuito no salga a internet.
  • Gateway type: Vpn o ExpressRoute. Se elige en la creación y no se puede cambiar después.
  • El despliegue tarda decenas de minutos (típicamente media hora o más). Cualquier respuesta del estilo "en segundos" es falsa.

Regla de cardinalidad: una VNet puede tener un gateway de tipo Vpn y un gateway de tipo ExpressRoute conviviendo (eso es la coexistencia), pero nunca dos del mismo tipo. "Agregá un segundo VPN Gateway a la misma VNet para redundancia" es siempre incorrecto: la redundancia se hace con active-active dentro del mismo gateway.
⚠️ Trampa del examen: no le pongas NSG ni Route Table (UDR) a la GatewaySubnet. Aplicar un NSG que bloquee el tráfico de control de Azure, o una UDR con default route, rompe el gateway y el circuito de ExpressRoute. Si una pregunta describe un túnel que "dejó de funcionar después de aplicar seguridad de red", mirá qué le colgaron a la GatewaySubnet.

SKUs de VPN Gateway

Cada SKU VpnGwN tiene su variante AZ (VpnGw1AZ … VpnGw5AZ), que es zone-redundant: las instancias se reparten en Availability Zones de la región. Si el escenario pide resiliencia a la caída de una zona, la respuesta es una SKU AZ.

Lo que Basic NO soporta (lista de memoria)
  • P2S con OpenVPN ni IKEv2 (solo SSTP) → tampoco autenticación con Entra ID ni RADIUS.
  • BGP, active-active, zone redundancy.
  • Coexistencia con ExpressRoute.
  • No se puede redimensionar (resize) hacia las SKUs modernas: hay que recrear el gateway. Entre SKUs VpnGw sí se puede hacer resize.
Active-active para alta disponibilidad
  • El gateway levanta dos instancias activas simultáneamente.
  • Necesita dos Public IPs.
  • Se arman dos túneles hacia on-prem; el dispositivo del otro extremo tiene que soportar múltiples túneles y, idealmente, BGP.
  • Si cae una instancia (falla o mantenimiento planificado), el tráfico sigue por la otra. Es la respuesta a "cómo minimizo la interrupción durante el mantenimiento del gateway".
Local Network Gateway (LNG) — el objeto más preguntado

Es la representación en Azure del sitio on-premises. No es un recurso de red real: es metadata. Contiene exactamente dos cosas que importan:

  • La IP pública (o FQDN) del VPN device on-prem.
  • Los address prefixes de la red on-premises (o la config de BGP, si usás BGP en vez de prefijos estáticos).
⚠️ Trampa del examen: si cambia el direccionamiento IP on-premises (agregan una subred, cambian el rango) o cambia la IP pública del router on-prem, lo que hay que actualizar es el Local Network Gateway — no el VPN Gateway, no la Connection, no la VNet. Es la pregunta clásica de "qué recurso modificás". Y no hace falta recrear ni reiniciar el VPN Gateway para eso.
✅ La shared key (PSK) del túnel IPsec tiene que ser idéntica en ambos extremos. "El túnel no levanta / queda en Not connected" con configuración aparentemente correcta = mismatch de shared key o de address prefixes en el LNG. Se puede rotar sin recrear nada, con az network vpn-connection shared-key update.

Point-to-Site: clientes individuales P2S

P2S conecta una computadora a la VNet, iniciando la conexión desde el cliente. No necesita hardware VPN ni IP pública del lado del usuario, así que sirve para trabajo remoto y para casos donde el usuario está detrás de NAT.

Address pool del cliente
  • Definís un rango del que Azure le asigna una IP a cada cliente conectado.
  • Ese rango no se puede solapar con el address space de la VNet, ni con on-premises, ni con ninguna VNet alcanzable por peering o por otros túneles.
  • El pool tiene que ser lo bastante grande para la cantidad de clientes concurrentes esperados.
Protocolo (tunnel type)TransporteSistemas operativosNotas de examen
OpenVPN SSL/TLS sobre TCP 443 Windows, macOS, Linux, iOS, Android El más flexible; atraviesa firewalls y proxies. Único que soporta autenticación con Entra ID
SSTP SSL sobre TCP 443 Solo Windows Atraviesa firewalls igual que OpenVPN, pero limitado a Windows. Es el único P2S de la SKU Basic
IKEv2 IPsec (UDP) macOS, Linux, Windows La opción para clientes Mac; puede quedar bloqueado por firewalls que solo dejan salir 443
Método de autenticaciónCómo funcionaRestricciones
Certificados de Azure Subís la clave pública del root certificate al gateway; cada cliente instala un client certificate emitido por esa raíz Funciona con los tres protocolos. Para revocar un cliente puntual se carga su thumbprint en la lista de certificados revocados
Microsoft Entra ID El usuario se autentica contra Entra ID; permite Conditional Access y MFA Solo con OpenVPN y con el Azure VPN Client. No funciona con SSTP ni IKEv2
RADIUS El gateway delega la autenticación en un servidor RADIUS (típicamente NPS contra AD DS on-prem) Requiere alcanzar el RADIUS server desde la VNet. No disponible en Basic
Requisitos y operación
  • El gateway tiene que ser route-based. Basic no sirve para nada más que SSTP con certificados.
  • Después de cualquier cambio en la configuración P2S (pool, protocolo, rutas, certificados), hay que descargar de nuevo el VPN client configuration package y redistribuirlo. Es una respuesta correcta muy común en troubleshooting.
  • Si además querés que los clientes P2S lleguen a on-prem a través del túnel S2S, necesitás propagación de rutas — típicamente con BGP.
⚠️ Trampa del examen: "los usuarios de Mac no pueden conectarse" → el gateway tiene habilitado solo SSTP (Windows-only); la solución es habilitar OpenVPN o IKEv2. Y "queremos MFA / Conditional Access en la VPN" → obliga a Entra ID, que a su vez obliga a OpenVPN. Las dos condiciones se preguntan encadenadas.

BGP: ruteo dinámico entre on-prem y Azure Route-based only

Border Gateway Protocol permite que Azure y on-premises se anuncien las rutas entre sí automáticamente, en lugar de que vos cargues a mano los prefixes en el Local Network Gateway cada vez que alguien crea una subred.

Qué te da BGP
  • Cero mantenimiento manual de prefijos: si on-prem agrega una red, se anuncia sola.
  • Múltiples túneles hacia el mismo sitio con failover automático (es lo que hace útil el active-active).
  • Transit routing: Azure puede reenviar tráfico entre sitios on-prem conectados por distintos túneles.
  • Convivencia limpia entre ExpressRoute y VPN en escenarios de coexistencia y failover.
Qué se configura
  • ASN de Azure en el VPN Gateway. El valor por defecto es 65515; se puede cambiar, pero hay ASNs reservados por Azure que no podés usar.
  • ASN del peer (el de on-premises) y sus address prefixes, en el Local Network Gateway.
  • Las BGP peering addresses de cada lado.
  • Hay que habilitar BGP en el gateway, en el LNG y en la connection. Si falta en alguno, la sesión no levanta.
⚠️ Trampa del examen: BGP requiere gateway route-based y una SKU que no sea Basic. Cualquier respuesta que combine "policy-based + BGP" o "Basic + BGP" es incorrecta por definición. Además, los ASNs de las dos puntas no pueden ser iguales.
✅ Cuando el enunciado se queja de "tenemos que actualizar los prefijos manualmente cada vez que cambia la red on-prem", la respuesta correcta es habilitar BGP, no "editar el Local Network Gateway más seguido".

ExpressRoute: circuito privado Sin internet

ExpressRoute es una conexión privada dedicada entre tu infraestructura y Microsoft, provista por un connectivity provider. La frase que hay que grabar: el tráfico no viaja por internet pública. Eso le da mayor confiabilidad, latencias más consistentes, más ancho de banda y un SLA de disponibilidad, a cambio de costo y de un tiempo de aprovisionamiento largo (semanas, no minutos).

Modelos de conexión
  • CloudExchange colocation: estás en un datacenter de colocation que ya tiene presencia de Microsoft; el proveedor te hace un cross-connect virtual.
  • Point-to-point Ethernet: un enlace Ethernet punto a punto desde tu sitio hasta Microsoft.
  • Any-to-any (IPVPN): integrás Azure como una sucursal más de tu WAN MPLS existente.
  • ExpressRoute Direct: te conectás directamente a la red global de Microsoft en un peering location, sin proveedor intermedio. Para escenarios de muy alta capacidad y aislamiento físico.
Peering typeA qué llegaDireccionamientoEstado
Private peering Tus VNets: VMs, servicios con private endpoint, todo lo que viva en la red virtual IPs privadas — es una extensión de tu red Vigente
Microsoft peering Servicios PaaS públicos (Storage, SQL Database) y Microsoft 365 / Dynamics 365 IPs públicas, con prefijos que tenés que poseer y validar; requiere route filters Vigente
Public peering Antecesor de Microsoft peering — Obsoleto / deprecated
Features que se preguntan por nombre
  • ExpressRoute Global Reach: conecta dos sitios on-premises entre sí usando el backbone de Microsoft como tránsito, uniendo dos circuitos ExpressRoute. Es la respuesta a "quiero que mi sucursal de Buenos Aires hable con la de Madrid sin contratar una WAN aparte".
  • FastPath: hace que el tráfico de datos saltee el ExpressRoute Gateway y vaya directo a las VMs de la VNet, mejorando latencia y packets-per-second. El gateway sigue existiendo para el control plane y el ruteo; FastPath requiere SKUs de gateway altas.
  • Redundancia incorporada: todo circuito ExpressRoute se entrega con dos conexiones hacia dos routers de Microsoft en el peering location. No hay opción de circuito "simple"; si el diseño on-prem usa un solo router, se pierde la redundancia que ya pagaste.
  • ExpressRoute Gateway: el Virtual Network Gateway de tipo ExpressRoute que hay que crear en cada VNet que quiera usar el circuito. Sus SKUs son distintas de las de VPN.
Modelo de facturaciónCómo se cobraCuándo conviene
Metered dataTarifa mensual del puerto + cargo por datos de salida (egress) transferidos. El ingress no se cobraVolumen de salida bajo o irregular
Unlimited dataTarifa mensual fija más alta, sin cargo por transferenciaVolumen de salida alto y sostenido; costo predecible
Coexistencia VPN + ExpressRoute
  • Una misma VNet puede tener un ExpressRoute Gateway y un VPN Gateway al mismo tiempo.
  • Uso típico: el S2S VPN queda como failover por si se cae el circuito ExpressRoute. Cuando ExpressRoute está arriba, es el camino preferido.
  • Requiere VPN Gateway route-based (nada de Basic ni policy-based) y una GatewaySubnet con espacio suficiente para los dos gateways.
  • También se puede usar el VPN para cifrar el tráfico que corre sobre private peering, si el compliance lo exige.
⚠️ Trampa del examen: ExpressRoute por sí solo no cifra el tráfico — es privado, no encriptado. Si el enunciado pide "conexión privada y cifrada", la respuesta es ExpressRoute más un VPN S2S encima (coexistencia), no ExpressRoute a secas. Otra confusión frecuente: Global Reach conecta sitios on-prem entre sí, mientras que para conectar VNets entre sí se usa peering o Virtual WAN.

Azure Virtual WAN Hub-and-spoke gestionado

Virtual WAN es un servicio de networking que empaqueta y administra por vos una topología hub-and-spoke a escala global. En lugar de armar a mano gateways, peerings y UDRs en cada región, creás virtual hubs y le colgás conexiones.

Componentes
  • Virtual WAN: el recurso paraguas, global.
  • Virtual hub: una VNet gestionada por Microsoft, uno por región. Adentro viven los gateways y el router del hub.
  • VNet connections: tus VNets spoke se conectan al hub (peering gestionado, no lo administrás vos).
  • VPN sites / Site-to-site VPN: cada sucursal se modela como un site y se conecta al hub.
  • User VPN (Point-to-site): clientes remotos contra el hub.
  • ExpressRoute: circuitos terminados en el hub.
  • Routing gestionado: el hub router hace el transit entre todo lo anterior — VNet a VNet, branch a VNet, branch a branch — sin que escribas UDRs.
  • Secured virtual hub: hub con Azure Firewall (Firewall Manager) para inspeccionar el tráfico.

Regla: Basic solo hace S2S VPN. En cuanto el escenario menciona ExpressRoute, P2S, varios hubs o transit routing, la respuesta es Standard. Un Virtual WAN Basic se puede upgradear a Standard, pero no al revés.
Cuándo el escenario pide Virtual WAN
  • Muchas sucursales (decenas o cientos) que hay que conectar y administrar de forma uniforme.
  • Topología hub-and-spoke multi-región que a mano sería inmanejable.
  • Se pide transit routing (branch↔VNet, branch↔branch, VNet↔VNet entre regiones) sin mantener UDRs ni NVAs de tránsito.
  • Se quiere onboarding automatizado de dispositivos de sucursal (partners de SD-WAN).
  • Contraejemplo: si es una sola VNet y una sola oficina, Virtual WAN es sobreingeniería — la respuesta es un VPN Gateway común.
ℹ️ En Virtual WAN no creás la GatewaySubnet ni los gateways a mano: los despliega el hub. Si una opción de respuesta dice "creá una GatewaySubnet dentro del virtual hub", está mal.

Errores que el examen castiga
  • Nombrar la subred distinto de GatewaySubnet, o hacerla demasiado chica.
  • Elegir policy-based y después pedir P2S, BGP, varios túneles o coexistencia.
  • Usar Basic para cualquier cosa moderna (OpenVPN, Entra ID, active-active, zone redundancy, coexistencia).
  • Modificar el VPN Gateway cuando lo que cambió es el direccionamiento on-prem (va en el Local Network Gateway).
  • Solapar el address pool de P2S con la VNet o con on-prem.
  • Creer que VNet peering alcanza a on-premises, o que es transitivo por sí solo.
  • Asumir que ExpressRoute cifra el tráfico.
  • Poner Virtual WAN Basic en un escenario que menciona ExpressRoute o P2S.
✅ Orden de lectura de un escenario: 1) ¿on-prem o solo Azure? 2) ¿un usuario o una red entera? 3) ¿hay una restricción de "no internet", de ancho de banda o de SLA? 4) ¿cuántos sitios? Con esas cuatro respuestas, la opción correcta queda sola.
