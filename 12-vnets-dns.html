Virtual Networks y subredes Fundamento

Una VNet es tu red privada dentro de Azure. Vive en una sola región y en una sola subscription, y no se puede mover de región. Se define con uno o más address spaces en notación CIDR (rangos privados RFC 1918 o públicos que te pertenezcan), y adentro se corta en subredes que no pueden solaparse entre sí ni salirse del address space.

Reglas de direccionamiento
  • Podés agregar address spaces a una VNet existente y quitarlos, siempre que no queden subredes dentro del rango que sacás.
  • Para cambiar el rango de una subred lo clásico es que la subred esté vacía: si tiene NICs, gateways o endpoints asociados, la operación falla.
  • Prefijo de subred más chico soportado: /29 (3 IPs utilizables). Prefijo más grande para el address space: /2. En la práctica el diseño típico es un /16 de VNet con subredes /24.
  • Los address spaces de VNets que vayas a peerear o conectar a on-premises no pueden solaparse. Planificá el IPAM antes, no después.

Subnet delegation

Delegar una subred es cederle el control a un servicio PaaS para que inyecte sus propios recursos ahí dentro. Se hace con el proveedor y el tipo de recurso, por ejemplo:

  • Microsoft.Web/serverFarms → VNet integration de App Service.
  • Microsoft.ContainerInstance/containerGroups → Azure Container Instances.
  • Microsoft.Sql/managedInstances → SQL Managed Instance.

Una subred delegada queda reservada para ese servicio: no le metés VMs comunes al lado.

az network vnet create -g rg-net -n vnet-prod --address-prefix 10.0.0.0/16 \
  --subnet-name snet-app --subnet-prefix 10.0.1.0/24

az network vnet subnet create -g rg-net --vnet-name vnet-prod \
  -n AzureBastionSubnet --address-prefix 10.0.250.0/26

az network vnet subnet update -g rg-net --vnet-name vnet-prod -n snet-aci \
  --delegations Microsoft.ContainerInstance/containerGroups
⚠️ Trampa del examen (Bastion / CIDR): VNet 10.3.2.0/23 + subnet existente 10.3.2.0/24. “IP address details” = el CIDR de AzureBastionSubnet → 10.3.3.0/26 (mitad libre del /23, /26 alineado). 10.3.2.0/26 solapa. /27 es chico. El detalle y los cmdlets están en 13 · Azure Bastion.
💡 Una VNet es un recurso regional, pero las subredes no están atadas a una zona de disponibilidad. Una misma subred abarca las tres AZ de la región: la zonalidad la definís en la VM o en la IP pública, no en la subred.

Direcciones IP privadas y públicas Muy preguntado
IP privada (en la NIC)
  • Dynamic (por defecto): Azure asigna la siguiente libre de la subred vía DHCP. Puede cambiar si la VM se deallocatea.
  • Static: la fijás vos dentro del rango de la subred y no cambia. Necesaria para DCs, DNS servers y appliances.
  • La IP privada sigue reservada mientras la VM esté detenida (deallocated), porque pertenece a la NIC y no a la VM.
  • Una NIC puede tener varias configuraciones IP (una primaria y varias secundarias).
⚠️ Trampa del examen: una IP privada estática se configura desde Azure (propiedades de la NIC), nunca desde el sistema operativo invitado. Si entrás al Windows/Linux y ponés la IP a mano en el adaptador, el guest y la plataforma se desincronizan y la VM pierde conectividad. La respuesta correcta siempre es "cambiar la asignación a Static en la IP configuration de la NIC" y dejar el SO en DHCP.

¿Con cuáles peerea VNet1-1? (otro tenant, otra sub)

Sub S1 (tenant A): VNet1-1, VNet1-2, VNet1-3. Sub S2 (tenant B): VNet2-1, VNet2-2. “Usá peering lo más posible.” ¿Con quién puede peerear VNet1-1?

Con las cuatro: VNet1-2, VNet1-3, VNet2-1 y VNet2-2. Distinta subscription y distinto tenant no bloquean el peering (sí hace falta permiso en ambos lados, típico CLI/PS).

Las 3 reglas que se preguntan: 1) el peering no es transitivo: si A↔B y B↔C, A no llega a C (hay que peerear A↔C, o usar hub-and-spoke con un NVA/Azure Firewall y UDRs). 2) los address spaces no pueden solaparse. 3) el peering se configura en los dos lados: hasta que ambos links estén en estado Connected no pasa tráfico.
⚠️ Trampa del examen: "creé el peering desde VNet1 y no hay conectividad". El estado del link queda en Initiated hasta que se cree el peering recíproco desde VNet2; recién ahí ambos pasan a Connected. Si el escenario menciona un solo peering creado, la acción correcta es crear el peering del otro lado, no tocar NSGs ni rutas.

Gateway vs forward: no son el mismo problema

El peering es un cable privado entre dos VNets. Por defecto, por ese cable solo pasa tráfico nacido en una de las dos. Hay dos checkboxes extra porque hay dos formas distintas de “usar al vecino como intermediario”.

1. Gateway transit = compartir la puerta a on-premises (VPN / ExpressRoute).

  • El gateway es un recurso de Azure (Virtual network gateway) en la GatewaySubnet del hub: túnel VPN o circuito ExpressRoute hacia el datacenter.
  • Allow gateway transit (solo hub): “mis spokes pueden usar mi puerta”. Se prende en el peering del lado de VN02.
  • Use remote gateways (solo spokes): “voy a usar la puerta del hub, no instalo la mía”. Se prende en VN01 y VN03. Una VNet no puede tener gateway propio y remoto a la vez.
  • Eso hace que una VM de VN01 llegue a on-prem por el hub. No hace, por sí solo, que VN01 hable con VN03: el peering sigue sin ser transitivo.

2. Forwarded traffic = aceptar paquetes que un router reenvió (NVA / Azure Firewall).

  • La NVA en VN02 es un cartero. Un paquete sale de VN01, entra a VN02, la NVA lo reenvía a VN03.
  • Cuando VN03 lo recibe, el origen IP es VN01, pero llegó por el cable de VN02. Azure, por defecto: “este cable es de VN02, descarto correo de VN01”.
  • Allow forwarded traffic en la VNet que recibe (las spokes): “acepto tráfico que mi peer reenvió desde otro lado”.
  • Por eso “solo en VN02” está mal: quien necesita el permiso es sobre todo VN01 y VN03 (y suele ir en ambos lados del peering). El hub también lo puede tener, pero no “only VN02”.
  • Además hace falta: IP forwarding en la NIC de la NVA, y UDRs en las subredes spoke (next hop Virtual appliance = IP de la NVA) para que el tráfico a la otra spoke no intente ir “directo” (el peering no es transitivo, no hay ruta).

El Service Endpoint solo aplica a tráfico que sale de una subred de la VNet — y se habilita en la subred de origen (la de la VM: appSubnet), no en una subred que se llame storageSubnet. Y si querés cerrar del todo el servicio, ponelo con Public network access = Disabled además del Private Endpoint.

Azure DNS público Zonas y registros

Azure DNS hostea tus dominios públicos. Ojo con el alcance: Azure DNS no registra dominios por sí mismo (eso lo hace un registrar o App Service Domains); lo que hace es alojar la zona y responder consultas con una red anycast global.

Qué es “delegar” (el concepto)

DNS es un árbol. La pregunta “¿cuál es la IP de company.com?” no llega directo a Azure: el resolver pregunta a la raíz → a .com → a los name servers que el registrar publicó para ese dominio. Delegar es cambiar esa flecha: decirle al registrar “a partir de ahora, los autoritativos son estos NS”. Hasta que no lo hagas, podés tener la zona y el registro A perfectos en Azure y el mundo sigue preguntándole al host viejo.

IP de App Service
  • Registrar = dónde compraste el dominio (GoDaddy, Namecheap, App Service Domains). Ahí viven los NS del apex.
  • Azure DNS = el servidor que responde A, MX, TXT… Azure no vende el dominio; solo lo hostea si lo delegás.
  • Hay dos delegaciones distintas: todo el dominio (cambiar NS en el registrar → esta pregunta) vs un subdominio (NS en la zona padre, más abajo).
Delegación del dominio al registrar (apex → Azure)
  1. Si el dominio no es tuyo: compralo en un registrar (GoDaddy, Namecheap, App Service Domains). Azure DNS no vende company1.com.
  2. Creás la DNS zone pública en Azure. Azure asigna 4 name servers y crea solo el SOA y los NS del apex — no los creás a mano.
  3. En el registrar, los NS apuntan a esos 4 azure-dns. Eso es delegar. El SOA no se toca en el registrar.
  4. Hasta que eso no propague, la zona existe pero nadie la consulta.
az network dns zone create -g RG -n company1.com
az network dns zone show -g RG -n company1.com --query nameServers -o tsv
New-AzDnsZone -Name company1.com -ResourceGroupName RG
Get-AzDnsZone -Name company1.com -ResourceGroupName RG |
  Select-Object -ExpandProperty NameServers

Delegación de un subdominio a otra zona Azure

Querés que development.company.com lo sirvan otros name servers (otra zona DNS, a menudo en otra suscripción o con otro equipo). Eso no se hace tocando el SOA.

  1. Creás la zona hija development.company.com. Azure le pone su propio SOA y sus 4 NS en @.
  2. En la zona padre company.com creás un record set NS llamado development (nombre relativo) apuntando a esos 4 NS de la hija.
# 1) Zona hija (Azure crea SOA + NS del apex sola)
New-AzDnsZone -Name development.company.com -ResourceGroupName RG
$childNs = (Get-AzDnsRecordSet -ZoneName development.company.com `
  -ResourceGroupName RG -Name "@" -RecordType NS).Records

# 2) Delegación: NS "development" EN company.com  ← la respuesta del examen
New-AzDnsRecordSet -Name "development" -ZoneName "company.com" `
  -ResourceGroupName RG -Ttl 3600 -RecordType NS -DnsRecords $childNs

# CLI
az network dns zone create -g RG -n development.company.com
az network dns record-set ns create -g RG -z company.com -n development --ttl 3600
az network dns record-set ns add-record -g RG -z company.com -n development \
  --nsdname ns1-01.azure-dns.com.
⚠️ Trampa del examen: “delegar development.company.com a otros DNS de Azure”. La respuesta es crear un NS record set llamado development en la zona company.com. No se modifica el SOA del padre, no se crea un SOA a mano en la hija (Azure ya lo crea), y no se pone el NS llamado development dentro de la zona hija — ahí el NS del apex ya existe como @.
TTL y record sets
  • El TTL se define por record set (no por registro individual) y determina cuánto cachean los resolvers. 1 hora = 3600 segundos (no 60, no 1).
  • Antes de una migración, bajá el TTL (por ejemplo a 300 s) con anticipación para que el cambio propague rápido.
  • Los registros SOA y NS del apex se crean automáticamente y no se pueden borrar.
  • El apex (root de la zona, company1.com sin prefijo) se nombra @. Un A en el apex es válido; un CNAME en el apex no.
  • Varios A en el mismo record set = round-robin DNS (Azure devuelve todas las IPs). No creás dos record sets llamados www.
Regla Set vs Config: New-AzDnsRecordSet crea el nombre en la zona (-Name, -ZoneName, -RecordType, -Ttl, -DnsRecords). New-AzDnsRecordConfig crea una IP (-IPv4Address) y se pasa al Set. Si el cmdlet lleva -IPv4Address, es Config; si lleva -Name / -ZoneName, es Set.
Script del examen: apex + www round-robin
New-AzDnsRecordSet -Name "@" -RecordType A -ZoneName "company1.com" `
  -ResourceGroupName "MyResourceGroup" -Ttl 3600 -DnsRecords `
  (New-AzDnsRecordConfig -IPv4Address "1.2.3.4")

$aRecords = @()
$aRecords += New-AzDnsRecordConfig -IPv4Address "2.3.4.5"
$aRecords += New-AzDnsRecordConfig -IPv4Address "3.4.5.6"
New-AzDnsRecordSet -Name "www" -ZoneName "company1.com" `
  -ResourceGroupName MyResourceGroup -Ttl 3600 -RecordType A -DnsRecords $aRecords

Alias records: la solución al apex

El estándar DNS prohíbe un CNAME en el apex (el root domain contoso.com, sin www), porque ahí ya conviven los registros SOA y NS. Los alias records resuelven eso: son record sets de tipo A, AAAA o CNAME que apuntan directo a un recurso de Azure.

Private DNS Zones Resolución interna

Una Private DNS zone resuelve nombres solo dentro de las VNets que le vinculás. No es visible desde internet, no necesita delegación en ningún registrar y podés usar cualquier nombre de dominio, incluso uno que no te pertenezca públicamente (por ejemplo corp.internal).

Virtual network links
  • La zona se conecta a una VNet mediante un virtual network link. Una zona puede tener links a muchas VNets, y una VNet puede estar linkeada a muchas zonas.
  • Los links cruzan regiones y subscriptions: la zona privada es un recurso global.
  • Sin link, las VMs de esa VNet no ven los registros de la zona, aunque la zona exista en la misma subscription.
Primera acción: zona privada nueva, VNet con VMs y zonas ya linkeadas

La VNet ya tiene VMs y Private DNS zones. Hay que soportar namespaces de una zona nueva.

AcciónPor qué
Linkear la zona nueva a la VNet existenteSíUna VNet admite muchos virtual network links. Es lo primero y alcanza
VNet nueva + mover las VMsNoOverkill. No hace falta otra red
Poner el DNS en el NIC / Windows de cada VMNoPrivate DNS se resuelve por el link de Azure, no por el guest
Sacar las VMs de la VNetNoRompe todo lo demás

Auto-registration sigue limitado a una zona. Los links extra van con registration off.

⚠️ Trampa del examen: “la VNet ya tiene zonas privadas” no impide sumar otra. Primera acción = virtual network link a la zona nueva. No creés otra VNet ni tocás el DNS del SO.
Auto-registration
  • Si activás auto-registration en el link, Azure crea y mantiene automáticamente el A record de cada VM de esa VNet, y lo borra cuando la VM se elimina.
  • Registra la IP privada primaria de la NIC de la VM. Otros recursos (Private Endpoints, LBs) no se autoregistran: esos records los creás vos o los crea la integración del endpoint.
  • Una VNet solo puede tener auto-registration habilitado en un único link, es decir, hacia una sola Private DNS zone. Podés tener más links a otras zonas, pero sin auto-registration.
az network private-dns zone create -g rg-net -n corp.internal

az network private-dns link vnet create -g rg-net -n link-vnet-prod \
  -z corp.internal -v vnet-prod --registration-enabled true

# zona para Private Endpoint: SIN auto-registration
az network private-dns link vnet create -g rg-net -n link-pe \
  -z privatelink.blob.core.windows.net -v vnet-prod --registration-enabled false
⚠️ Trampa del examen: las zonas privatelink.* de Private Endpoints se linkean con auto-registration DESACTIVADO. Si lo prendés, las VMs de la VNet empiezan a registrarse en esa zona y podés pisar la resolución del endpoint. Y recordá el límite conceptual: una VNet, un solo link con auto-registration.
✅ Escenario típico de hub-and-spoke: una sola Private DNS zone privatelink.blob.core.windows.net centralizada en el hub, con virtual network links a todas las spokes. No hace falta duplicar la zona por VNet.

Resolución de nombres en Azure Memorizar la IP
168.63.129.16 — la IP virtual "mágica" de Azure. Es la misma en todas las regiones y VNets, no se puede cambiar ni bloquear. Hace tres cosas: 1) DNS provisto por Azure; 2) origen de los health probes del Load Balancer y de Application Gateway; 3) canal de comunicación con la plataforma (agente de VM, heartbeat, DHCP). Si un NSG o un firewall del SO la bloquea, se rompen los probes y el agente.

Resolución entre VNets peereadas

El peering da conectividad IP, pero el DNS de Azure no resuelve nombres de host entre VNets distintas. Una VM de VNet-A puede hacer ping a la IP de una VM de VNet-B, pero no a su nombre. Soluciones:

  • Private DNS zone con auto-registration en una VNet y links a las demás (la más simple y la respuesta típica).
  • Custom DNS servers propios en el hub, apuntados desde todas las VNets.

Global peering West US ↔ East US. VMs de ambas tienen que resolver el FQDN de cualquier otra VM en Azure:

OpciónPor qué
Private DNS zone + links a las dos VNetsSíCloud-native. Auto-registration en una, link en la otra
Azure-provided DNS en cada VNetNoSolo nombres dentro de la misma VNet
Definir peering entre las VNetsNoDa IP privada, no FQDN. El ping por IP no implica resolución
VPN VNet-to-VNetNoConectividad (más cara que peering). Tampoco resuelve nombres
DNS servers propios en cada VNetNoFunciona, pero más admin (VMs que mantener)
Service endpointsNoSalida a PaaS (Storage/SQL), no DNS interno
⚠️ Trampa del examen: la pregunta es hostname resolution, no conectividad. Peering y VPN VNet-to-VNet no resuelven FQDN. Azure-provided DNS no cruza VNets. La respuesta es Private DNS zone + links. Service endpoints son carnada de PaaS.
Azure DNS Private Resolver (híbrido)

Servicio PaaS que reemplaza a las VMs con rol de DNS forwarder. Se despliega en una VNet con subredes dedicadas y delegadas a Microsoft.Network/dnsResolvers (mínimo /28):

  • Inbound endpoint: recibe consultas desde on-premises hacia Azure. Los DNS de on-prem apuntan a su IP privada para resolver zonas privadas y FQDNs privatelink.*.
  • Outbound endpoint + DNS forwarding ruleset: manda consultas de Azure hacia on-premises según reglas por dominio. El ruleset se vincula a las VNets que lo usan.
💡 Regla rápida: on-prem → Azure = inbound endpoint; Azure → on-prem = outbound endpoint + forwarding ruleset. Si la pregunta pide resolución híbrida sin administrar VMs de DNS, la respuesta es Azure DNS Private Resolver.

Rutas del sistema y User Defined Routes Resumen

Azure crea rutas del sistema en cada subred automáticamente; no se ven en una route table pero existen. El detalle fino de NSG, ASG y Azure Firewall va en el archivo de seguridad de red: acá queda lo que se cruza con VNets y DNS.

PrefijoNext hop typeCuándo aparece
Address space de la VNetVirtual networkSiempre: todas las subredes de una VNet se hablan por defecto
0.0.0.0/0InternetSiempre: salida a internet por defecto
Address space de la VNet remotaVNet peeringAl crear un peering
Prefijos anunciados por BGPVirtual network gatewayCon VPN Gateway o ExpressRoute
User Defined Routes (UDR)
  • Se agrupan en una route table que se asocia a una o varias subredes (no a NICs ni a VMs).
  • Una subred puede tener una sola route table asociada; una route table puede servir a varias subredes.
  • Primero gana el prefijo más específico (longest prefix match) entre todas las rutas; sólo cuando dos rutas tienen exactamente el mismo prefijo decide la precedencia UDR > rutas BGP > rutas del sistema.
  • Next hop types disponibles: Virtual appliance (le pasás la IP privada del NVA/Firewall), Virtual network gateway, Virtual network, Internet y None (descartar tráfico).
  • Patrón forced tunneling: UDR de 0.0.0.0/0 con next hop Virtual appliance apuntando a Azure Firewall, para inspeccionar todo el egress.
💡 Para el hub-and-spoke con inspección: en las spokes ponés un UDR hacia el Firewall del hub, y en el peering activás Allow forwarded traffic. Sin esa opción, la VNet destino descarta el tráfico que reenvió el NVA. Las dos piezas van juntas.
