Roles, scopes, herencia y roles custom
Dominio 1 · 20–25%
← Índice Anatomía del role assignment Scopes y herencia Roles built-in clave Control plane vs Data plane Roles custom (JSON) Deny assignments Azure RBAC vs Entra ID RBAC vs Azure Policy Operación, límites y CLI Flashcards
Qué se pregunta acá: el examen casi nunca te pide definir RBAC. Te da un escenario ("Fulano tiene X rol en Y scope, ¿puede hacer Z?") y te obliga a elegir el rol de menor privilegio que resuelve el caso. Las tres máquinas de matar son: Contributor no puede asignar roles, Contributor en una Storage Account no lee blobs con Entra ID, y Global Administrator no toca recursos de Azure hasta que alguien prende el toggle de elevación.
🧩

Role assignment
1 · Security principal
  • User — una identidad de Microsoft Entra ID.
  • Group — la forma recomendada: asignás al grupo, no a la persona.
  • Service principal — la identidad de una app registrada.
  • Managed identity — system-assigned o user-assigned, para que un recurso llame a otro sin secretos.
2 · Role definition

Una colección de permisos en JSON. Los verbos importan: Actions (control plane permitido), NotActions (se resta), DataActions / NotDataActions (plano de datos), AssignableScopes (dónde se puede usar el rol).

Permiso efectivo = Actions − NotActions. NotActions no es un deny: si el mismo principal recibe esa acción por otra role assignment, la tiene igual.
3 · Scope

Uno de cuatro niveles: Management Group Subscription Resource Group Resource. En el portal se hace desde la blade Access control (IAM) del objeto en ese nivel.

💡 El modelo es allow por defecto denegado: si no hay ninguna role assignment que te otorgue la acción, no la podés hacer. No existe "quitar" un permiso heredado con otra assignment.

Las tres reglas de la herencia
  • Baja, no sube. Lo que asignás en un MG aplica a todas las subscriptions, RGs y recursos de abajo. Nunca al revés: Owner en un RG no te da nada en la subscription.
  • Es aditiva (unión, no intersección). Si tenés Reader en la subscription y Contributor en un RG, dentro de ese RG sos Contributor. Los permisos se suman.
  • No se resta. No podés asignar un rol "más chico" en un scope hijo para recortar lo heredado. Para quitar permiso hay que eliminar la assignment del scope padre (o que exista un deny assignment).
⚠️ Trampa del examen: "El usuario tiene Contributor en la subscription y le asignás Reader en el RG-Producción para que solo lea ahí." No funciona. Sigue siendo Contributor en ese RG porque los permisos se acumulan. La única salida es sacar el Contributor de la subscription y reasignar más abajo.
🌳 Arriba de todo está el root management group (/), que tiene el mismo ID que el tenant. Todas las subscriptions y MGs cuelgan de él, y una role assignment ahí llega a absolutamente todo el tenant.

Least privilege: gestionar el acceso de otros

Un ingeniero nuevo debe administrar el acceso de otros a recursos de Azure, sin más privilegio del necesario.

az role assignment create --assignee <upn> --role "User Access Administrator" --scope /subscriptions/<id>
New-AzRoleAssignment -SignInName user@contoso.com -RoleDefinitionName "User Access Administrator"
⚠️ Trampa del examen: User Administrator ≠ User Access Administrator. El primero es Entra (cuentas). El segundo es Azure RBAC (quién toca recursos). Co-Administrator y Owner sobran privilegio. Contributor no da IAM.
Roles específicos que aparecen en escenarios
  • Virtual Machine Contributor — crea y administra VMs. No te da acceso a la vNet ni a la Storage Account a las que la VM se conecta, y no te da acceso al sistema operativo invitado.
  • Virtual Machine Administrator Login / Virtual Machine User Login — estos sí son login al SO (con Entra ID), como admin o como usuario común. Ojo: son roles de acceso a la VM, no de gestión del recurso.
  • Network Contributor — administra networking (vNets, NSGs, load balancers) pero no da acceso a los recursos conectados.
  • Storage Blob Data Contributor / Reader / Owner — plano de datos de blobs (ver la sección siguiente).
  • Backup Operator — opera backups (dispara jobs, restaura) pero no puede crear vaults ni quitar la protección de backup; eso es Backup Contributor. Backup Reader solo monitorea.
⚠️ Trampa del examen: cuando la pregunta dice "minimum required role / principio de menor privilegio", Owner y Contributor casi siempre son distractores. Si existe un rol específico del servicio (Virtual Machine Contributor, Network Contributor, Backup Operator, Storage Blob Data Reader), ese es el correcto.

⚠️ Trampa del examen: un usuario con Contributor sobre una Storage Account y autenticación con Microsoft Entra ID abre el container en el portal y ve AuthorizationPermissionMismatch: no puede listar ni leer blobs. Contributor da control plane, no DataActions. La solución es Storage Blob Data Reader (leer) o Storage Blob Data Contributor (leer/escribir/borrar).
🔑 El matiz que separa a los que estudiaron: Contributor sí puede hacer listKeys, así que puede acceder a los datos usando la account key o un SAS. Lo que no puede es acceder con su identidad de Entra ID. Por eso la mitigación real es desactivar el acceso por shared key y forzar Entra ID + roles de datos.
Otros servicios con roles de data plane
  • Key Vault — con el modelo de permisos RBAC: Key Vault Secrets User (leer secretos), Key Vault Secrets Officer, Key Vault Administrator. Alternativa histórica: access policies del propio vault (los dos modelos son excluyentes: se elige uno).
  • Storage Queue / File / Table Data — mismo patrón que Blob, un set de roles por servicio.

Roles custom JSON

Se crean cuando ningún built-in encaja. Se pueden armar desde el portal (clonando un built-in o desde cero), con JSON, CLI o PowerShell.

{
  "Name": "VM Operator",
  "IsCustom": true,
  "Description": "Puede arrancar, parar y reiniciar VMs, pero no crearlas ni borrarlas.",
  "Actions": [
    "Microsoft.Compute/*/read",
    "Microsoft.Compute/virtualMachines/start/action",
    "Microsoft.Compute/virtualMachines/restart/action",
    "Microsoft.Compute/virtualMachines/deallocate/action",
    "Microsoft.Authorization/*/read",
    "Microsoft.Resources/subscriptions/resourceGroups/read"
  ],
  "NotActions": [],
  "DataActions": [],
  "NotDataActions": [],
  "AssignableScopes": [
    "/subscriptions/00000000-0000-0000-0000-000000000000"
  ]
}
Reglas que se preguntan
  • Permiso efectivo = Actions − NotActions (y DataActions − NotDataActions para datos). Se calculan por separado: un wildcard en Actions nunca otorga DataActions.
  • AssignableScopes define dónde se puede asignar el rol, no qué permisos da. Admite management group, subscription o resource group; no admite un recurso individual y no admite el root scope /.
  • No se permiten wildcards en AssignableScopes. Si querés que el rol sirva en varias subscriptions, o las listás todas, o usás un management group que las contenga.
  • Para crear un rol custom necesitás Microsoft.Authorization/roleDefinitions/write en ese scope: lo tienen Owner y User Access Administrator. Contributor no.
  • Límite: 5000 roles custom por tenant (en Azure China 21Vianet, 2000).
  • Los roles custom se guardan en el tenant, así que un rol creado en una subscription puede compartirse con otras del mismo tenant agregándolas a AssignableScopes. Entre tenants distintos, no.
⚠️ Trampa del examen: confundir AssignableScopes con el scope de la assignment. El rol de arriba tiene AssignableScopes = una subscription; eso no significa que quien lo reciba tenga permisos sobre toda la subscription: significa que ese rol solo puede asignarse dentro de ella (a la sub, a un RG o a un recurso de adentro).
✅ Truco práctico: la forma rápida de armar un rol custom es clonar un built-in y sacarle acciones. Para descubrir el string exacto de una operación, az provider operation show --namespace Microsoft.Compute.
⛔
Deny assignments Precedencia
Qué son
  • Bloquean acciones específicas a principals determinados en un scope, aunque una role assignment se las otorgue.
  • Precedencia absoluta: deny gana siempre sobre cualquier allow. El motor evalúa primero los deny.
  • No se crean a mano — no hay botón en la blade IAM para agregarlas. Las crea Azure: Deployment Stacks (deny settings), Azure Managed Applications (RG gestionado por el publisher) y, en legado, Azure Blueprints (en retiro el 31 ene 2027).
  • Se pueden leer: pestaña Deny assignments en Access control (IAM), o az role assignment list no las muestra — usá Get-AzDenyAssignment en PowerShell.
  • Se heredan hacia abajo igual que las role assignments (salvo que la deny assignment tenga marcado que no aplique a scopes hijos).

🔒 No confundas deny assignments con resource locks (CanNotDelete / ReadOnly). Los locks aplican a todos los principals por igual y son parte de ARM, no de RBAC; incluso un Owner queda bloqueado hasta que borre el lock (y borrar un lock requiere Microsoft.Authorization/locks/*, que tienen Owner y User Access Administrator).

Azure RBAC vs roles de Microsoft Entra ID Muy preguntado

Son dos sistemas de permisos separados que no se hablan entre sí.

Azure RBACRoles de Entra ID
ControlaRecursos de Azure (VMs, storage, redes)Objetos del directorio (usuarios, grupos, apps, licencias)
ScopesMG / Subscription / RG / RecursoTodo el tenant (o unidades administrativas / app scope)
Dónde se veBlade Access control (IAM) del recursoEntra ID → Roles and administrators
Roles típicosOwner, Contributor, ReaderGlobal Administrator, User Administrator, Billing Administrator
CustomSí, con JSON y AssignableScopesSí, pero es otro motor (requiere licencia P1/P2)
⚠️ Trampa del examen: un Global Administrator no tiene acceso a los recursos de Azure por defecto. Puede administrar todo el directorio y no ver ni una VM. Para arreglarlo: Entra ID → Properties → "Access management for Azure resources" → Yes. Eso le asigna User Access Administrator en el root scope (/), desde donde puede darse a sí mismo o a otros los roles que necesite. Es un cambio auditado y conviene revertirlo cuando termina la tarea.
Detalles del "elevate access"
  • El toggle otorga User Access Administrator, no Owner: te deja repartir acceso, no administrar recursos directamente.
  • Solo lo puede activar un Global Administrator, y solo aplica a esa cuenta.
  • El permiso detrás es Microsoft.Authorization/elevateAccess/action, que está en las NotActions de Contributor.
  • Se revierte apagando el toggle o borrando la assignment en el root scope: az role assignment delete --assignee <objectId> --scope "/" --role "User Access Administrator".
🧠 Regla mnemotécnica: Global Administrator manda en el directorio; Owner manda en los recursos. Y para gestionar management groups (crear, mover subscriptions) hace falta permiso de Azure RBAC en el MG, no un rol de Entra.
⚖️
RBAC vs Azure Policy No se confunden
RBAC responde "¿quién puede hacer qué?". Azure Policy responde "¿qué configuraciones son válidas?". Policy no mira quién sos: aplica a todos por igual, incluido un Owner.
Azure RBACAzure Policy
Objeto de controlIdentidades y accionesPropiedades del recurso
Ejemplo"Ana puede crear VMs en RG-Dev""Ninguna VM puede crearse fuera de West Europe"
Aplica a OwnerOwner tiene todo permitidoSí — un Deny de Policy frena también al Owner
EfectosAllow (y deny assignments internas)Deny, Audit, Append, Modify, DeployIfNotExists
ScopesMG / Sub / RG / RecursoMG / Sub / RG (con exclusions)
🔗 Se cruzan en un punto: las policies con efecto DeployIfNotExists o Modify necesitan una managed identity y una role assignment para poder remediar. Por eso al asignar ese tipo de policy el portal te pide elegir un rol y una ubicación para la identidad.

Operación: límites, propagación y CLI Números
Check access

En Access control (IAM) → Check access elegís un usuario, grupo o service principal y Azure te muestra los permisos efectivos en ese scope, distinguiendo las assignments directas de las heredadas (te dice de qué scope vienen) y las que llegan por pertenencia a grupos. Es la herramienta correcta cuando la pregunta dice "¿cómo verificás por qué un usuario puede/no puede hacer algo?".

LímiteValor
Role assignments por subscription4.000 (incluye las de sub, RG y recursos)
Role assignments por management group500
Roles custom por tenant5.000
Niveles de scope4 (MG → Sub → RG → Recurso)
⚠️ Trampa del examen: el límite de role assignments es la razón por la que se asigna a grupos y no a usuarios. Si un escenario dice "estamos cerca del límite de role assignments en la subscription", la respuesta no es "pedir aumento de cuota": es consolidar en grupos de Entra ID (o usar roles custom que agrupen permisos).
⏱️ Propagación: una role assignment no aplica instantáneamente — contá unos minutos (el material de referencia habla de hasta ~5 minutos). Azure Resource Manager cachea, así que si el usuario sigue viendo el permiso viejo, que cierre sesión y vuelva a entrar para refrescar el token (los cambios de pertenencia a grupos solo se reflejan con un token nuevo).
Comandos que hay que reconocer
# Listar roles built-in y custom disponibles
az role definition list --output table
az role definition list --name "Storage Blob Data Reader"
az role definition list --custom-role-only true

# Ver quién tiene qué, incluyendo herencia y grupos
az role assignment list --scope /subscriptions/<subId>/resourceGroups/RG-Prod \
  --include-inherited --include-groups --output table

# Asignar y quitar
az role assignment create --assignee ana@contoso.com \
  --role "Virtual Machine Contributor" \
  --scope /subscriptions/<subId>/resourceGroups/RG-Prod
az role assignment delete --assignee ana@contoso.com --role Reader --scope <scope>

# Roles custom
az role definition create --role-definition @vm-operator.json
az role definition update --role-definition @vm-operator.json

Equivalentes en PowerShell: Get-AzRoleDefinition, Get-AzRoleAssignment, New-AzRoleAssignment, Remove-AzRoleAssignment, New-AzRoleDefinition, Get-AzDenyAssignment.
