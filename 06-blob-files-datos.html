  • El container es el único nivel de agrupación real dentro del servicio Blob. No hay containers anidados.
  • El nombre del container va en minúsculas, letras/números/guiones, y forma parte de la URL: https://<cuenta>.blob.core.windows.net/<container>/<blob>.
  • El container $root permite servir blobs sin nombre de container en la URL.
Las "carpetas" son mentira (salvo con HNS)

En una cuenta flat namespace (Blob Storage clásico), un blob llamado 2024/enero/reporte.csv no está en dos carpetas: el nombre del blob es literalmente 2024/enero/reporte.csv, barras incluidas. El portal y Storage Explorer dibujan un árbol simulando directorios a partir del delimitador /, pero es una ilusión de UI.

  • Consecuencia: no podés renombrar ni mover una "carpeta" en una operación atómica. Renombrar implica copiar cada blob al nombre nuevo y borrar el viejo.
  • Con hierarchical namespace (HNS) habilitado — o sea Azure Data Lake Storage Gen2 — los directorios son objetos reales: rename y delete de directorio son operaciones atómicas y hay ACLs POSIX por directorio.
  • HNS se habilita al crear la cuenta y afecta qué features podés usar (por ejemplo, deshabilita algunas como point-in-time restore).
Metadata, properties e index tags
  • Metadata: pares clave-valor definidos por vos, en el blob o en el container. Son nombres válidos de identificador C#, no se pueden buscar de forma nativa: los tenés que enumerar y filtrar del lado del cliente.
  • System properties: las pone Azure (Content-Type, ETag, Last-Modified, tier). Algunas son de solo lectura.
  • Blob index tags: pares clave-valor indexados y consultables con Find Blobs by Tags. Sirven como filtro en reglas de lifecycle y para RBAC condicional. Son distintos de metadata.

Protección de datos de Blob Alta frecuencia
Soft delete — de blob y de container
  • Blob soft delete: al borrar un blob (o al sobrescribirlo, si además hay versioning/snapshots) el dato queda en estado soft-deleted y se puede hacer Undelete durante el período de retención. Retención configurable, típicamente entre 1 y 365 días.
  • Container soft delete: es una feature separada, con su propio switch y su propia retención (también en el rango de 1 a 365 días). Recupera el container entero con su contenido.
  • Ninguno de los dos es retroactivo: si el blob se borró antes de habilitar soft delete, no lo recuperás.
  • El reloj de retención se cuenta desde el borrado, y se aplica la retención vigente en ese momento.
⚠️ Trampa del examen: blob soft delete no te salva si te borran el container entero (con la cuenta plana, borrar un container elimina sus blobs sin pasar por el estado soft-deleted individual). Para eso necesitás container soft delete, que es un toggle distinto. Si el escenario dice "alguien borró el container por accidente", la respuesta no es blob soft delete.
Versioning
  • Se habilita a nivel cuenta y aplica a todos los containers.
  • No es “cualquier write”: el examen lista cuatro operaciones REST que crean versión. Put Page, Append Block y Put Blob From URL no.
  • Al borrar el blob "actual" con versioning activo, las versiones previas siguen existiendo: la restauración es promover una versión a current (copiándola sobre el blob base).
  • Costo: cada versión se factura como datos almacenados. Un workload que sobrescribe mucho puede multiplicar la factura.
  • Se combina con lifecycle: hay filtros/acciones específicas para versiones (por ejemplo, borrar o mover a cool las versiones con cierta antigüedad desde su creación, distintas del blob current).
Elegí varias: qué operación crea una versión

Versioning habilitado. ¿Cuáles disparan un version ID nuevo? Memorizá las cuatro del overview de Microsoft; el resto son el cebo.

Snapshots
  • Copia manual, de solo lectura, de un blob en un punto del tiempo. Vos la disparás; nada la crea sola.
  • Comparte los bloques no modificados con el blob base: solo pagás el delta de los bloques que cambian después.
  • El snapshot se identifica por el blob base + un timestamp de snapshot.
  • Para restaurar: se copia el snapshot sobre el blob base (o a otro nombre).

Point-in-time restore (PITR)

Restaura un conjunto de block blobs (uno o varios containers, con filtros de prefijo) al estado que tenían en un instante pasado. Es la única feature que devuelve "todo el container como estaba el martes a las 14:00".

Prerrequisitos (los pregunta en combo): blob versioning + change feed + blob soft delete, los tres habilitados. Además: cuenta GPv2 estándar, solo block blobs, y no soportado con hierarchical namespace.
  • El período de restauración que definas debe ser menor que la retención de soft delete.
  • Solo podés restaurar a un punto posterior al momento en que habilitaste PITR.
  • Es una operación destructiva sobre el estado actual: sobreescribe con lo que había en el punto elegido.
💡 Cómo decidir rápido: "un blob puntual borrado por error" → soft delete. "Necesito el contenido de ayer de un archivo que se sobrescribe seguido" → versioning. "Quiero un punto de restauración antes de correr un batch" → snapshot. "Un ransomware/script me pisó cientos de blobs, devolveme todo el container al martes" → point-in-time restore.

Immutable storage (WORM) Compliance
WORM: Write Once, Read Many

Mientras una política inmutable esté activa, el dato no se puede borrar ni sobrescribir — ni por vos, ni por el Owner de la suscripción, ni por Microsoft. Se aplica a nivel de container o a nivel de versión de blob. Sirve para escenarios regulatorios (SEC 17a-4, retención legal, auditoría financiera, historia clínica).

PolíticaTiene fechaCómo terminaUso típico
Time-based retention Sí — definís un intervalo de retención en días Vence sola. Mientras corre, el intervalo se puede extender pero no acortar una vez que la política está locked "Guardar los registros 7 años"
Legal hold No — no tiene fecha de fin Solo se levanta manualmente, quitando el tag del hold Litigio en curso, investigación: no sabés cuándo termina
  • Una política time-based empieza en modo unlocked (para probar: se puede acortar o borrar) y al pasarla a locked se vuelve irreversible.
  • Pueden coexistir: si hay un legal hold activo, el dato queda protegido aunque la retención por tiempo ya haya vencido.
  • Con la política activa sí podés seguir agregando blobs nuevos al container; lo que no podés es modificar ni eliminar los existentes protegidos.
  • No se puede borrar el container mientras contenga blobs protegidos, y la cuenta tampoco.
⚠️ Trampa del examen: si el escenario dice "no sabemos cuánto va a durar la investigación" o "hasta que el departamento legal lo autorice", la respuesta es legal hold, no time-based retention. Y al revés: "conservar exactamente 5 años" es time-based retention. Otra variante: preguntan si el Storage Account Owner puede borrar un blob bajo policy locked — la respuesta es no, ningún rol puede.

Lifecycle management Optimización de costo
Cómo funciona
  • Es una policy en JSON a nivel de storage account, con un conjunto de reglas. Se configura en el portal (form o JSON), CLI, PowerShell o ARM.
  • Cada regla tiene un filterSet (a qué aplica) y un actionSet (qué hace).
  • Aplica a block blobs (y append blobs solo para la acción delete). No mueve de tier a page blobs ni a Azure Files.
Filtros disponibles
  • prefixMatch: prefijo del nombre, empezando por el container — ej. logs/2024/.
  • blobTypes: blockBlob / appendBlob.
  • blobIndexMatch: por blob index tags (ej. Project == Alpha).
  • Se puede apuntar a baseBlob, a snapshot y a version por separado dentro del actionSet.
Acciones y condiciones
AcciónQué haceCondición típica

tierToArchiveMueve el blob a Archive (offline, hay que hacer rehydrate para leerlo). No funciona en cuentas ZRS/GZRS/RA-GZRSdaysAfterModificationGreaterThan

La condición alternativa daysAfterLastAccessTimeGreaterThan se basa en el último acceso en lugar de la última modificación, y requiere habilitar last access time tracking en la cuenta (tiene costo de transacciones extra).

Drop-down PowerShell: Hot → Cool a los 30 días

Orden: Action → Filter → Rule → Set en la cuenta. Prefijos ef,gh, block blobs.

$action = Add-AzStorageAccountManagementPolicyAction `
  -BaseBlobAction TierToCool -daysAfterModificationGreaterThan 30
$filter = New-AzStorageAccountManagementPolicyFilter `
  -PrefixMatch ef,gh -BlobType blockBlob
$rule  = New-AzStorageAccountManagementPolicyRule `
  -Name test-rule -Action $action -Filter $filter
Set-AzStorageAccountManagementPolicy -ResourceGroupName $rgName `
  -StorageAccountName $accountName -Rule $rule
CmdletPor qué
Add-AzStorageAccountManagementPolicyActionSíEl action es Add-, no New-
New-AzStorageAccountManagementPolicyFilterSíPrefijo + blob type
New-AzStorageAccountManagementPolicyRuleSíUne action + filter

⚠️ Trampa del examen: el action es Add-AzStorageAccountManagementPolicyAction (no New-). El cierre es Set-…ManagementPolicy sobre la cuenta. La condición del enunciado es modification 30 días, no creation ni last access.
⚠️ Trampa del examen: el motor de lifecycle corre una vez por día y la evaluación no es instantánea — después de crear o modificar una policy puede pasar bastante hasta que se vea el efecto. Si la pregunta plantea "creé la regla de 30 días y el blob que tiene 45 días sigue en Hot, ¿qué pasa?", la respuesta correcta es esperar: la policy se ejecuta en el ciclo diario, no "la regla está mal". Y ojo: mover a Cool/Cold/Archive no cambia la fecha de última modificación, pero sí puede haber cargos de early deletion si sacás el blob antes del mínimo del tier (Cool 30 · Cold 90 · Archive 180). Si te piden el default access tier de la cuenta para datos estáticos ~100 días, la respuesta es Cold (ver 04 · Access tiers), no Archive.
✅ Para el examen: si te muestran un JSON, mirá primero prefixMatch (¿incluye el container?) y después el orden lógico de los días: Cool < Archive < Delete. Un JSON donde tierToArchive tiene menos días que tierToCool es la respuesta incorrecta plantada.

Object replication Distribución
Qué es

Copia asíncrona de block blobs desde un container de una cuenta source a un container de una cuenta destination, según reglas de prefijo. Vos elegís origen, destino y qué se replica.

Cuenta source
versioning + change feed
→
Replication policy
reglas por container y prefijo
→
Cuenta destination
versioning
Requisitos (memorizalos)
  • En la cuenta origen: blob versioning y change feed habilitados. El change feed es lo que le dice al servicio qué cambió.
  • En la cuenta destino: blob versioning habilitado.
  • Las reglas se definen a nivel de container (origen → destino), con filtros de prefijo opcionales y un timestamp opcional para replicar solo lo creado/modificado desde entonces.
  • Origen y destino pueden estar en regiones, suscripciones o tenants distintos.
  • En el container destino no se permiten escrituras directas de usuarios (responden 409 Conflict). Lectura y delete sí. Solo la policy de replicación escribe blobs.
Drop-down del examen: mínimo para object replication

Enunciado: replicar entre cuentas de dos regiones y minimizar cambios. No es PITR: no hace falta soft delete.

Blob versioning Both source and destination Cada write genera una versión; OR replica versiones. El destino también tiene que tener versioning o la policy no se crea.

Update-AzStorageBlobServiceProperty -ResourceGroupName RG -StorageAccountName origen `
  -IsVersioningEnabled $true -ChangeFeed $true
# Destino: solo versioning

  -IsVersioningEnabled $true

  --enable-versioning true --enable-change-feed true
az storage account blob-service-properties update -n destino -g RG \
  --enable-versioning true
⚠️ Trampa del examen: object replication ≠ PITR. OR = change feed solo origen + versioning en las dos. PITR pide versioning + change feed + blob soft delete en la misma cuenta. Habilitar change feed en el destino o soft delete “por las dudas” viola minimize configuration changes. Tampoco es GRS: acá vos elegís la cuenta y la región destino.

Azure Files: shares, protocolos y tiers SMB / NFS
Protocolos
  • SMB 3.x: el caso general. Montable desde Windows, Linux y macOS. Soporta cifrado en tránsito y es el único que admite autenticación basada en identidad (AD).
  • NFS 4.1: solo en Premium file shares (cuentas FileStorage). Autenticación/autorización estilo POSIX basada en red — no soporta identidad de AD ni access key para el montaje, así que se protege con service endpoints / private endpoints y restricción de red. Cifrado en tránsito no aplica igual que en SMB.
  • Un share es SMB o NFS; el protocolo se elige al crear el share y no se cambia después.

Tamaño del share
  • Un share standard llega hasta 100 TiB (en cuentas nuevas ese techo ya viene habilitado; el toggle legacy de large file shares era el que subía el default de 5 TiB).
  • Los 100 TiB aplican también con GRS y GZRS en shares standard: ya no es un combo exclusivo de LRS/ZRS.
  • Los shares premium soportan hasta 100 TiB sin ese toggle; el rendimiento escala con el tamaño provisionado.
Protección de datos del share
  • Share snapshots: copias de solo lectura, incrementales, a nivel de share entero. Se disparan manualmente, por script, o automáticamente si usás Azure Backup para Azure Files. El usuario final las ve como "Versiones anteriores" en Windows: recupera un archivo que alguien pisó, sin restaurar el share entero.
  • Soft delete de file share: recupera un share eliminado durante el período de retención (1–365 días). Es una propiedad del servicio File, no del servicio Blob — son switches distintos en la misma cuenta GPv2; en FileStorage solo existe el de Files.
  • Azure Backup para Azure Files orquesta snapshots con políticas de retención y da restore granular. Cumple las dos protecciones, pero suma vault, policy y costo: no es “reducir overhead”.
  • Azure Files no tiene blob versioning, lifecycle de blobs ni point-in-time restore (eso es Blob).

  --enable-delete-retention true --delete-retention-days 14

Montaje SMB on-premises: el puerto 445

Montar el share directamente desde la oficina por SMB 3.x (Premium FileStorage o Standard) es tráfico TCP 445 saliente hacia <cuenta>.file.core.windows.net. El 443 es HTTPS/REST (portal, AzCopy, FileREST), no el protocolo de montaje.

# ¿El 445 llega a Azure?
Test-NetConnection <cuenta>.file.core.windows.net -Port 445

# Windows: guardar credencial y mapear
cmdkey /add:<cuenta>.file.core.windows.net /user:localhost\<cuenta> /pass:<key>
net use Z: \\<cuenta>.file.core.windows.net\<share>

# Persistente (PowerShell)
New-SmbMapping -LocalPath 'Z:' -RemotePath '\\cuenta.file.core.windows.net\share' -Persistent $true

# Linux (CIFS / SMB 3)
sudo mount -t cifs //cuenta.file.core.windows.net/share /mnt/share \
  -o vers=3.1.1,username=cuenta,password=<key>,sec=ntlmssp,serverino

Error 67 al mapear el share en Windows Server

VM Windows + Azure Files SMB. net use / Map Network Drive tira System error 67 (The network name cannot be found). El verbo del examen es desbloquear TCP 445 (NSG, Windows Firewall o el ISP). Los otros tres ítems existen en troubleshooting, pero no con este código.

Opción¿Tiene validez?
Unblock port 445SíError 53 o 67 cuando el 445 saliente está tapado. Microsoft lo lista como cause 1.
Check permissions / IAMNoVálido para Error 5 (Access is denied) o “No Access”. El 67 es conectividad: ni siquiera llegás a autenticar.
Unblock port 2049NoEs NFS 4.1 (Premium FileStorage, típico Linux). Windows mapea SMB, nunca 2049.
Enable NTLMv1NoAl revés: Azure Files solo NTLMv2 (o Kerberos). Activar v1 empeora. Microsoft lo asocia a Error 53 o 87, no al 67. Fix: LmCompatibilityLevel = 3.

# TcpTestSucceeded : True  → el 445 llega; si es False, NSG/firewall/ISP

# Si TcpTestSucceeded es True y sigue el 67: typo en el nombre del share

  • Nivel share (Azure RBAC): roles como Storage File Data SMB Share Reader, … Contributor y … Elevated Contributor (este último es el único que permite modificar ACLs NTFS). Se asignan sobre el share, el resource group o la suscripción.
  • Nivel directorio/archivo (NTFS): las ACL de Windows de siempre, gestionadas con icacls o el Explorador desde una máquina unida al dominio.
  • El permiso efectivo es la intersección: el más restrictivo gana. RBAC Contributor + NTFS Read = solo lectura. RBAC Reader + NTFS Full Control = solo lectura.
  • La access key sortea todo esto: quien la tiene es superusuario del share, sin importar RBAC ni NTFS. Por eso, cuando hay identity-based auth, lo correcto es deshabilitar el acceso por key.
⚠️ Trampa del examen: te dan un usuario con el rol Storage File Data SMB Share Contributor y ACL NTFS de Read, y preguntan si puede escribir. No. El permiso efectivo es la intersección de ambos, nunca la unión. Variante: preguntan quién puede cambiar las ACL NTFS desde una VM — solo Elevated Contributor (o quien monte con la access key).

Azure File Sync Híbrido
Los componentes, en orden de creación
  1. Storage Sync Service: el recurso de Azure que gobierna todo. Vive en un resource group y es el "top level".
  2. Registered server: un Windows Server con el agente de Azure File Sync instalado y registrado contra el Storage Sync Service.
  3. Sync group: define el ámbito de sincronización. Contiene exactamente un cloud endpoint y uno o varios server endpoints.
  4. Cloud endpoint: un Azure file share. Uno solo por sync group.
  5. Server endpoint: una ruta específica en un servidor registrado (un volumen o una carpeta). Un mismo servidor puede tener server endpoints en varios sync groups.

Cloud tiering
  • Se habilita por server endpoint. Los archivos "fríos" se suben a Azure y en el disco local queda un puntero.
  • Ese puntero es un reparse point: ocupa unos pocos KB, el usuario ve el archivo con su tamaño real, y al abrirlo se hace recall transparente desde el share.
  • Dos políticas, combinables:
    • Volume free space policy: mantené X% del volumen libre — File Sync va tirando a la nube lo menos usado hasta cumplirlo.
    • Date policy: mantené en local solo lo accedido en los últimos N días.
  • Si conviven ambas, la de espacio libre tiene prioridad: primero se garantiza el espacio.
Casos de uso que el examen premia
  • Centralizar file servers de sucursales: cada sucursal con su cache local, un único share como fuente de verdad.
  • Reducir footprint on-prem sin comprarle discos al file server: cloud tiering.
  • Backup / DR: si el server muere, instalás el agente en uno nuevo, lo registrás y el namespace se rehidrata rápido (primero los reparse points, después el contenido bajo demanda).
  • Migración lift-and-shift: sincronizás, verificás, y después apuntás a Azure Files.
⚠️ Trampa del examen: el agente de Azure File Sync corre solo en Windows Server (no en Windows 10/11 cliente ni en Linux) y el server endpoint requiere un volumen NTFS — cloud tiering no funciona sobre ReFS ni sobre el volumen de sistema. Otra: un sync group tiene un único cloud endpoint; si necesitás dos file shares distintos, necesitás dos sync groups. Y no confundas File Sync (sincroniza y cachea, es bidireccional y continuo) con AzCopy sync (copia puntual, unidireccional, se corre a mano o por schedule).

AzCopy: los dos verbos que preguntan
# copy: copia todo lo que matchee (no borra nada en el destino)
azcopy copy "C:\datos\*" "https://cuenta.blob.core.windows.net/cont?<SAS>" --recursive

# sync: deja el destino IGUAL al origen (puede BORRAR en el destino)
azcopy sync "C:\datos" "https://cuenta.blob.core.windows.net/cont?<SAS>" --recursive

# server-to-server: los datos NO pasan por tu máquina
azcopy copy "https://origen.blob.core.windows.net/c1?<SAS>" \
            "https://destino.blob.core.windows.net/c2?<SAS>" --recursive

# autenticación con Entra ID en vez de SAS
azcopy login
azcopy login --identity     # con managed identity, desde una VM
  • Autenticación: token SAS pegado en la URL, o azcopy login con Entra ID / managed identity. Con Entra ID necesitás el rol de datos correspondiente (ej. Storage Blob Data Contributor) — ser Owner del recurso no alcanza para el plano de datos.
  • copy vs sync: sync compara y puede eliminar en el destino lo que no está en el origen; copy nunca borra. Si la pregunta dice "espejo exacto" → sync. Si dice "agregar sin tocar lo existente" → copy.
  • Server-to-server: si origen y destino son URLs de Azure, los datos viajan dentro de Azure y no consumen tu ancho de banda.
