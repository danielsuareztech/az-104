Azure Resource Manager como capa de control Fundamento

ARM es la única puerta de entrada al control plane de Azure. No importa por dónde entres: portal, Azure CLI, Azure PowerShell, un SDK o una llamada REST cruda. Todo termina en el mismo endpoint de ARM, que autentica contra Microsoft Entra ID, autoriza contra RBAC, evalúa Azure Policy y recién ahí le pasa la operación al resource provider correspondiente.

Consecuencias prácticas
  • Un RBAC role assignment, un resource lock o una Azure Policy se aplican igual sin importar la herramienta: no hay "puerta trasera" por CLI.
  • Las operaciones de data plane (leer un blob, consultar una base) NO pasan por ARM. Por eso un rol de control plane como Contributor no te da automáticamente lectura de datos de un blob.
  • Los resource locks (CanNotDelete, ReadOnly) son evaluados por ARM, así que también bloquean despliegues de plantillas.
Resource providers

Cada familia de servicios vive en un resource provider con formato Microsoft.<Servicio>: Microsoft.Compute, Microsoft.Storage, Microsoft.Network, Microsoft.KeyVault. El provider define los tipos de recurso, las operaciones y las API versions disponibles.

El registro es por subscription. Si el provider no está registrado, el despliegue falla con NoRegisteredProviderFound o MissingSubscriptionRegistration.

az provider list --query "[?registrationState=='Registered'].namespace" -o tsv
az provider register --namespace Microsoft.Insights
az provider show --namespace Microsoft.Insights --query registrationState

# PowerShell
Register-AzResourceProvider -ProviderNamespace Microsoft.Insights

Resource ID: el identificador completo
/subscriptions/{subscriptionId}
  /resourceGroups/{rgName}
  /providers/Microsoft.Storage/storageAccounts/{nombre}
  • Es único en todo Azure y lo usás en plantillas, scripts, role assignments y diagnósticos.
  • Un recurso hijo extiende el ID del padre: .../storageAccounts/st01/blobServices/default/containers/logs.
  • En plantillas lo construís con resourceId(); nunca lo concatenes a mano.

Anatomía de un ARM template (JSON) Estructura

Un ARM template es un archivo JSON declarativo: describís el estado final deseado, no los pasos. ARM se encarga del orden y del paralelismo.

Sección¿Obligatoria?Para qué sirve
$schemaSíURL del esquema JSON. Determina el scope: deploymentTemplate.json# (resource group) vs subscriptionDeploymentTemplate.json#.
contentVersionSíVersión que definís vos (típicamente 1.0.0.0). ARM no la interpreta; sirve para trazabilidad.
resourcesSíQué se despliega. Puede estar vacío ([]), pero el elemento debe existir.
parametersNoValores que se pasan en tiempo de despliegue. Admiten defaultValue, allowedValues, minLength/maxLength, type: securestring.
variablesNoValores calculados dentro de la plantilla para no repetir expresiones. No se pueden pasar desde afuera.
functionsNoUser-defined functions con namespace propio, para reutilizar expresiones.
outputsNoValores que devuelve el deployment (IPs, FQDNs, resource IDs) y que consumen las linked/nested templates.
Ejemplo mínimo válido
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "storageName": {
      "type": "string",
      "minLength": 3,
      "maxLength": 24
    },
    "sku": {
      "type": "string",
      "defaultValue": "Standard_LRS",
      "allowedValues": [ "Standard_LRS", "Standard_GRS", "Premium_LRS" ]
    }
  },
  "variables": {
    "location": "[resourceGroup().location]"
  },
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "2023-01-01",
      "name": "[parameters('storageName')]",
      "location": "[variables('location')]",
      "sku": { "name": "[parameters('sku')]" },
      "kind": "StorageV2",
      "properties": { "supportsHttpsTrafficOnly": true }
    }
  ],
  "outputs": {
    "storageId": {
      "type": "string",
      "value": "[resourceId('Microsoft.Storage/storageAccounts', parameters('storageName'))]"
    }
  }
}

Fijate que todo recurso necesita mínimamente type, apiVersion y name. Las expresiones van entre corchetes y comillas: "[expresión]".

Parameter files (.parameters.json)

Separan los valores del código. Un mismo azuredeploy.json con dev.parameters.json y prod.parameters.json es el patrón canónico de "despliegue consistente entre entornos".

{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentParameters.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "storageName": { "value": "stprodweu001" },
    "sku":         { "value": "Standard_GRS" }
  }
}
az deployment group create \
  --resource-group rg-prod \
  --template-file azuredeploy.json \
  --parameters @prod.parameters.json \
  --parameters sku=Standard_ZRS      # este inline pisa al del archivo

# PowerShell
New-AzResourceGroupDeployment -ResourceGroupName rg-prod `
  -TemplateFile azuredeploy.json `
  -TemplateParameterFile prod.parameters.json
⚠️ Trampa del examen: ojo con el @ en CLI. --parameters @archivo.json lee un parameter file; sin el @, Azure CLI lo interpreta como un string literal o como JSON inline y el despliegue falla o toma el valor equivocado. Y el orden importa: los parámetros inline sobrescriben a los del archivo.

Funciones, expresiones y dependencias Sintaxis
FunciónQué devuelveUso típico
parameters('x')Valor del parámetro xTodo lo que viene de afuera.
variables('x')Valor de la variable xExpresiones repetidas o nombres compuestos.
resourceGroup()Objeto del RG: .location, .id, .name, .tags"location": "[resourceGroup().location]" — el patrón recomendado para heredar la región.
subscription().subscriptionId, .tenantId, .displayNameConstruir IDs o etiquetar.
concat()Concatena strings o arrays[concat('vm-', parameters('env'))].
uniqueString()Hash determinístico de 13 caracteresNombres globalmente únicos: [concat('st', uniqueString(resourceGroup().id))]. Mismo input ⇒ mismo output, así que es idempotente.
resourceId()El resource ID completoReferenciar otro recurso en dependsOn o en properties.
reference()Estado runtime del recurso (sus properties)Leer la IP pública, el FQDN o el endpoint de un storage. Crea dependencia implícita.
listKeys()Claves de un recursoKeys de storage. Nunca las pongas en outputs.
copy / copyIndex()Bucle de recursosCrear N discos, N NICs o N VMs desde un solo bloque.
dependsOn: explícito vs implícito
  • Explícito: array dependsOn con los resource IDs o nombres de los recursos que deben existir primero. Es la forma clásica en JSON.
  • Implícito: si usás reference() sobre otro recurso de la misma plantilla, ARM infiere la dependencia solo. resourceId() por sí solo no crea dependencia: es solo construcción de string. En Bicep, referenciar el símbolo (PrimaryDnsZone.properties.nameServers) es implícito; el array dependsOn es explícito.
  • Sin dependencias, ARM despliega en paralelo. Con ellas, arma un grafo y serializa lo necesario.
{
  "type": "Microsoft.Network/networkInterfaces",
  "apiVersion": "2023-05-01",
  "name": "nic-web01",
  "location": "[resourceGroup().location]",
  "dependsOn": [
    "[resourceId('Microsoft.Network/virtualNetworks', 'vnet-prod')]",
    "[resourceId('Microsoft.Network/publicIPAddresses', 'pip-web01')]"
  ],
  "properties": {
    "ipConfigurations": [{
      "name": "ipconfig1",
      "properties": {
        "subnet": { "id": "[resourceId('Microsoft.Network/virtualNetworks/subnets', 'vnet-prod', 'web')]" },
        "publicIPAddress": { "id": "[resourceId('Microsoft.Network/publicIPAddresses', 'pip-web01')]" }
      }
    }]
  }
}
⚠️ Trampa del examen: si el escenario dice "el despliegue falla intermitentemente porque la NIC se crea antes que la VNet", la causa es un dependsOn faltante, no un problema de permisos ni de región. Y al revés: encadenar dependsOn de más serializa todo y hace el despliegue lento sin necesidad.
💡 uniqueString() es determinístico, no aleatorio. Si lo alimentás con resourceGroup().id, el nombre generado se mantiene idéntico en cada redespliegue sobre ese mismo RG — que es exactamente lo que querés para que la plantilla sea idempotente.

Modos de despliegue: Incremental vs Complete ⭐ Lo más preguntado

Este es el tema de ARM que cae sí o sí. La diferencia no es cómo se crean los recursos de la plantilla (eso es igual en ambos modos), sino qué pasa con los recursos del resource group que NO figuran en la plantilla.

SituaciónIncremental (default)Complete
Recurso en la plantilla, no existe en AzureSe creaSe crea
Recurso en la plantilla, existe en Azure con otras propertiesSe actualiza al estado del templateSe actualiza al estado del template
Recurso en el RG que NO está en la plantillaSe deja intactoSE BORRA
Property que existe en Azure pero se omite en la plantillaPuede quedar tal cual (no se resetea automáticamente)Puede quedar tal cual (no se resetea automáticamente)
Uso típicoAgregar o modificar sin romper lo existente. Despliegues parciales.Forzar que el RG sea exactamente lo que dice la plantilla (drift eliminado).
Flag CLI--mode Incremental (implícito)--mode Complete
Scopes soportadosRG, subscription, management group, tenantSolo resource group
 
az deployment group create \
  --resource-group rg-prod \
  --template-file main.json \
  --mode Complete

# PowerShell
New-AzResourceGroupDeployment -ResourceGroupName rg-prod `
  -TemplateFile main.json -Mode Complete
⚠️ Trampa del examen: el escenario clásico. Un RG tiene una VM, una VNet y un storage account creados a mano. Alguien despliega una plantilla que solo define la VNet, en modo Complete. Resultado: la VM y el storage account se eliminan. La respuesta correcta a "cómo evitarlo" es desplegar en modo Incremental (el default) — o correr what-if antes. No es "agregar un lock" salvo que la pregunta lo pida explícitamente.
¿Por qué el RG quedó solo con el storage nuevo?

Plantilla ARM sin nested/linked. New-AzResourceGroupDeployment terminó OK y borró todo lo demás.

CausaPor qué
Usaste -Mode Complete en el cmdletSíComplete borra del RG lo que no está en la plantilla
No usaste -ModeNoDefault = Incremental: no borra lo extra
La plantilla trae mode: IncrementalNoEl JSON no tiene mode. Es del deployment, no del template
La plantilla trae mode: CompleteNoIdem: no es una property del ARM
⚠️ Trampa del examen: el modo va en New-AzResourceGroupDeployment -Mode Complete / az deployment group create --mode Complete, nunca dentro del JSON. Sin -Mode = Incremental = no se borra nada.
⚠️ Trampa del examen: el modo Complete solo existe a nivel de resource group. Los despliegues de scope subscription, management group y tenant son siempre Incremental. Si una opción dice "desplegar en modo Complete a nivel de subscription para limpiar resource groups viejos", es falsa.
Regla mnemotécnica: Incremental = "sumá lo mío y no toques lo demás". Complete = "el resource group tiene que quedar idéntico a mi plantilla, borrá el resto".
Matices que conviene tener
  • Complete respeta los resource locks: un recurso con CanNotDelete hace fallar el intento de borrado.
  • Ambos modos son idempotentes respecto de los recursos declarados: redesplegar la misma plantilla sin cambios no rompe nada.
  • El modo se define por deployment, no por plantilla. El mismo JSON puede correr en un modo u otro.
  • Complete no es un "borrar el resource group": el RG en sí sobrevive, se vacía de lo que no esté declarado.

Scopes de despliegue Comandos

El scope define dónde se ancla el deployment y, por lo tanto, qué podés crear. Cambiar de scope implica cambiar el $schema y el comando.

ScopeComando CLIPowerShellQué se despliega ahí
Resource group az deployment group create -g <rg> New-AzResourceGroupDeployment El 90% de los casos: VMs, VNets, storage, NSGs, App Services. El RG ya debe existir.
Subscription az deployment sub create -l <region> New-AzSubscriptionDeployment Crear resource groups, policy definitions y assignments, role assignments a nivel sub, Deployment Stacks (Blueprints se retiran el 31 ene 2027).
Management group az deployment mg create -m <mg> -l <region> New-AzManagementGroupDeployment Policies y roles que bajan a varias subscriptions, subscription aliases, MGs anidados.
Tenant az deployment tenant create -l <region> New-AzTenantDeployment Management groups de raíz y asignaciones a nivel tenant. Poco frecuente.
⚠️ Trampa del examen: no podés crear un resource group desde un deployment con scope de resource group — es el huevo y la gallina. Si la plantilla incluye un recurso de tipo Microsoft.Resources/resourceGroups, tenés que usar az deployment sub create (o New-AzSubscriptionDeployment) con el schema de subscription. Los scopes que no son RG exigen además --location, porque el registro del deployment tiene que guardarse en alguna región.

El JSON está en un container privado. ARM tiene que bajarlo por HTTPS, así que necesitás un SAS de lectura y pasarle la URL completa al deployment. -FullUri concatena blob + token; sin eso $templateuri sería solo el token y el deploy falla.

Schema por scope
// Resource group
"$schema": ".../2019-04-01/deploymentTemplate.json#"

// Subscription
"$schema": ".../2018-05-01/subscriptionDeploymentTemplate.json#"

// Management group
"$schema": ".../2019-08-01/managementGroupDeploymentTemplate.json#"

En Bicep no tocás el schema: declarás targetScope = 'subscription' (o 'managementGroup', 'tenant') en la primera línea. Si no ponés nada, el default es 'resourceGroup'.

targetScope = 'subscription'

param location string = 'eastus'

resource rg 'Microsoft.Resources/resourceGroups@2021-04-01' = {
  name: rgName
  location: location

💡 Un deployment puede cruzar scopes: desde una plantilla de subscription podés desplegar recursos dentro de un RG con un módulo/nested deployment apuntando a ese scope. Patrón típico: crear el RG y poblarlo en un solo comando.

Bicep DSL moderno

Bicep es un DSL declarativo que transpila a ARM JSON. No es un motor nuevo: al desplegar, la herramienta compila el .bicep a una plantilla ARM y la manda al mismo endpoint de siempre. Por eso hay paridad 1:1: todo lo que se puede hacer en ARM JSON se puede hacer en Bicep, y los recursos y API versions nuevas están disponibles el día cero.

main.bicep
→
transpile
az bicep build
→
main.json
ARM template
→

Ventajas frente a JSON crudo
  • Sintaxis mucho más limpia: sin comillas por todos lados, sin corchetes de expresión, sin [concat(...)] — se usa string interpolation.
  • Dependencias automáticas: si referenciás el símbolo de otro recurso (sa.id o PrimaryDnsZone.properties.nameServers), Bicep genera el dependsOn solo. Eso es implícito. El bloque dependsOn escrito a mano es explícito.
  • Modules: descomponés la infra en archivos reutilizables y los invocás con module, incluyendo scope distinto.
  • Tipado y validación en el editor: IntelliSense, tipos de recurso, autocompletado de properties y errores antes de desplegar.
  • Sin estado externo: el "estado" es Azure mismo. No hay state file que mantener, bloquear ni versionar.
  • Es gratis y soportado por Microsoft, incluido en Azure CLI moderno.
Yes/No: implícito vs dependsOn vs paralelo

ARM no arranca un recurso hasta que sus dependencias (implícitas o explícitas) estén listas. Sin ninguna dependencia, sí van en paralelo.

resource PrimaryDnsZone 'Microsoft.Network/dnszones@2018-05-01' = {
  name: 'myZone'
  location: 'global'
}
resource otherResource 'Microsoft.Example/examples@2023-05-01' = {
  name: 'example1'
  properties: {
    nameServers: PrimaryDnsZone.properties.nameServers  // implícito
  }
}
resource otherZone 'Microsoft.Network/dnszones@2023-06-01' = {
  name: 'demoZone2'
  location: 'global'
  dependsOn: [ PrimaryDnsZone ]  // explícito
}
Afirmación
otherResource depende implícitamente de PrimaryDnsZoneYes — usa una property del símbolo
otherZone depende implícitamente de PrimaryDnsZoneNo — es dependsOn (explícito)
ARM despliega PrimaryDnsZone y otherZone en paraleloNo — el dependsOn las serializa
 
az deployment group create -g RG --template-file main.bicep
New-AzResourceGroupDeployment -ResourceGroupName RG -TemplateFile main.bicep
⚠️ Trampa del examen: “implícito” = referenciás el símbolo (.id, .properties.nameServers). “Explícito” = bloque dependsOn. Si hay cualquiera de las dos, no van en paralelo con el recurso padre. otherResource y otherZone sí pueden ir en paralelo entre sí, después de que exista PrimaryDnsZone.

sortNoReordena; sigue siendo array
⚠️ Trampa del examen: “array de objetos → un JSON con las keys custom” = toObject. map deja array. No es reduce aunque en teoría se pueda.
⚠️ Trampa del examen: cuidado con la dirección de build y decompile. az bicep build = Bicep → JSON (compilar). az bicep decompile = JSON → Bicep (migrar plantillas existentes). El decompile es best effort: suele dejar warnings y nombres de variables genéricos que hay que limpiar a mano, así que no lo pongas como "conversión perfecta y automática".
✅ No hace falta compilar antes de desplegar: az deployment group create --template-file main.bicep transpila en el momento. az bicep build se usa para inspeccionar el JSON generado o para pipelines que necesitan el artefacto.

Validación, historial y reutilización Operación
what-if: ver el impacto antes de aplicar

La operación what-if hace un dry run contra ARM y devuelve los cambios previstos con símbolos: + Create ~ Modify - Delete = NoChange e * Ignore.

az deployment group what-if \
  --resource-group rg-prod \
  --template-file main.bicep \
  --mode Complete

# confirmación interactiva integrada al deploy
az deployment group create -g rg-prod --template-file main.bicep --confirm-with-what-if

# PowerShell
New-AzResourceGroupDeployment -ResourceGroupName rg-prod -TemplateFile main.bicep -WhatIf

Si vas a correr modo Complete, what-if te muestra explícitamente las líneas - Delete de los recursos que van a desaparecer. Es la mitigación esperada en las preguntas de escenario.

validate: chequeo de sintaxis y permisos
az deployment group validate \
  --resource-group rg-prod \
  --template-file main.json \
  --parameters @prod.parameters.json
  • validate verifica que la plantilla sea sintácticamente válida, que los parámetros estén completos y que el deployment sea aceptable. No te dice qué recursos se van a borrar.
  • what-if sí compara contra el estado real y te lista los cambios. Cuando la pregunta dice "ver el impacto / qué recursos se modifican o eliminan", la respuesta es what-if, no validate.
Historial de deployments
  • Cada deployment queda registrado en el resource group (Portal → Resource group → Deployments) con nombre, estado, timestamp, parámetros usados y recursos tocados. Sirve para auditar y para reintentar.
  • El historial guarda hasta 800 deployments por resource group; al acercarse al límite, ARM borra automáticamente las entradas más viejas.
  • Un deployment sin --name toma el nombre del archivo de plantilla, así que se pisan entre corridas. En pipelines conviene nombrarlos con fecha o build ID.
  • Borrar entradas del historial no borra recursos: es solo metadata del deployment.
az deployment group list -g rg-prod -o table
az deployment group show -g rg-prod -n mainDeploy --query properties.outputs
Exportar plantillas
  • Desde un resource group o un recurso individual: Portal → Export template, o az group export --name rg-prod / Export-AzResourceGroup.
  • También existe la opción de exportar la plantilla desde el historial de un deployment — esa versión suele estar más limpia porque es la que efectivamente se usó.

Yes/No: 20 Linux VMs copiando la config de VM1

RG1 tiene VM1 (Linux). Hay que automatizar 20 VMs más basadas en la configuración de VM1.

Solución propuesta: guardar las properties de la VM en una plantilla y desplegar las demás editando los parámetros (nombre, IP) en cada corrida.

¿Cumple el objetivo? Yes.

Camino¿Cumple?Por qué
Export template de VM1 → parametrizar → az deployment group createYesClona tamaño, NIC, discos, extensiones. VM1 sigue viva. Distintos parámetros = distintas VMs
Capture / generalize + imagenTambién Yes, otra preguntaClona el disco. En Linux: waagent -deprovision; la origen suele quedar inutilizable
“Solo VMSS / solo snapshot sirven”NoVMSS es un set escalable, no es el único modo. Snapshot es un disco, no despliega 20 VMs solas
 
# Portal: VM1 → Export template → bajar JSON y parametrizar name / IP
az deployment group create -g RG1 --template-file vm.json --parameters @vm.parameters.json

# 20 veces (o un loop) con parámetros distintos
for i in $(seq 1 20); do
  az deployment group create -g RG1 --template-file vm.json \
    --parameters vmName=vm$i
done
⚠️ Trampa del examen: Yes/No “plantilla ARM + cambiar parámetros por cada VM extra”. La respuesta es Yes. El “No” aparece porque pensás que hace falta imagen, snapshot o VMSS. Esos también pueden servir en otras propuestas; esta solución igual cumple. Export: VM o RG → Export template.
Template specs
  • Un template spec es un recurso de Azure (Microsoft.Resources/templateSpecs) que guarda una plantilla ARM/Bicep versionada dentro de una subscription.
  • Se comparte con RBAC: le das Reader al equipo y despliegan sin acceder al archivo ni a un repo. Nadie puede modificar la plantilla sin permisos de escritura sobre el spec.
  • Cada versión es inmutable y podés desplegar una versión concreta, lo que da despliegues repetibles y auditables.
az ts create --name webapp-spec --version 1.0 \
  --resource-group rg-shared --template-file main.bicep

az deployment group create -g rg-app \
  --template-spec "/subscriptions/<subId>/resourceGroups/rg-shared/providers/Microsoft.Resources/templateSpecs/webapp-spec/versions/1.0"
