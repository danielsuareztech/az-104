Anatomía de una VM: qué se crea con ella Fundamentos
Una VM no es un recurso, son varios

Cuando creás una VM desde el portal, Azure te arma un combo de recursos independientes que se facturan y se borran por separado:

  • Virtual machine — el recurso de cómputo en sí (CPU/RAM).
  • Managed disk (OS disk) — obligatorio, uno por VM.
  • Network interface (NIC) — obligatoria, al menos una. La IP privada vive acá.
  • Public IP address — opcional, recurso aparte. Sin ella la VM no es alcanzable desde Internet de forma entrante.
  • Network Security Group — el portal crea uno por defecto asociado a la NIC.
  • Virtual network + subnet — si no elegiste una existente.
  • Data disks — opcionales, 0..N según el tamaño de VM.
Qué se borra y qué queda huérfano

Históricamente, borrar la VM solo borraba la VM: discos, NIC, IP pública y NSG quedaban colgados generando costo. Hoy cada recurso asociable tiene un deleteOption ("Delete with VM") que se define al crear la VM o se puede cambiar después sobre la VM existente.

Recurso¿Tiene "Delete with VM"?Si no lo marcaste
OS diskSí (marcado por defecto en el portal)Queda como managed disk suelto, se sigue facturando
Data disksSí (desmarcado por defecto)Quedan sueltos con los datos intactos
NICSíQueda huérfana, bloquea el borrado de la subnet
Public IPSíQueda reservada y facturando (si es Standard/Static)
NSGNoSiempre sobrevive a la VM
VNet / SubnetNoSiempre sobrevive a la VM
⚠️ Trampa del examen: "borré la VM pero me siguen cobrando". Lo que factura son los managed disks huérfanos y la Public IP estática reservada, no la VM. Borrar el resource group completo sí se lleva todo; borrar la VM sola, no.
No se puede cambiar después de crear la VM: el nombre, la región, la VNet, la availability zone y la pertenencia a un availability set. Si te preguntan "cómo muevo una VM a otra zona / a otro availability set", la respuesta es recrearla (snapshot o imagen del disco y desplegar de nuevo). Lo que sí podés cambiar en caliente: tamaño, discos, NIC adicionales, extensiones.
ℹ️ Una VM puede tener varias NICs, pero la cantidad máxima la define el tamaño de VM, y agregar o quitar NICs exige la VM deallocada.

Discos gestionados: cuál va en cada escenario Storage
Lo primero: son discos de bloque

Un managed disk es block storage montado como volumen dentro del SO — no es Blob ni un file share, no se accede por HTTP ni se monta por SMB desde otra máquina. Azure administra la storage account por vos: vos elegís tipo y tamaño, y el resto es transparente.

TipoEscenario típicoIOPS / throughputPuede ser OS disk
Standard HDD Backup, archivos fríos, cargas no críticas con acceso poco frecuente. Lo más barato. Escala con el tamaño del disco. El piso del catálogo. Sí
Standard SSD Web servers, dev/test, apps ligeras que necesitan latencia más predecible que HDD sin pagar Premium. Escala con el tamaño (tiers E). Mejor consistencia que HDD. Sí
Premium SSD Producción, bases de datos, cargas sensibles a latencia. Requerido para el SLA de VM de instancia única. Escala por tier (P10, P30, P50...). Para más IOPS tenés que agrandar el disco. Sí
Premium SSD v2 Cargas transaccionales que necesitan mucha performance sin sobredimensionar el tamaño. Sale más barato que Ultra. IOPS y throughput configurables independientemente del tamaño. Baseline incluida y ajuste fino desde ahí. No (solo data disk)
Ultra Disk El techo: SAP HANA, SQL de misión crítica, NoSQL con latencia sub-milisegundo. Solo cuando el escenario dice "máximo IOPS" o "latencia más baja posible". IOPS y throughput configurables independientemente del tamaño y ajustables en caliente. No (solo data disk)

Restricciones de Ultra Disk (esto es lo que preguntan)
  • La VM tiene que estar en una Availability Zone de una región que soporte Ultra, y hay que habilitar la compatibilidad Ultra en la VM.
  • ✗ No sirve como disco de OS.
  • ✗ No soporta host caching (obligatoriamente None).
  • ✗ No es compatible con availability sets ni con Azure Disk Encryption (ADE).
  • No todas las features de disco (imágenes, algunas rutas de backup/replicación) están disponibles: si el escenario pide "backup con Azure Backup" o "réplica con Site Recovery", Ultra es sospechoso.
Tamaños máximos: OS disk ≠ data disk
  • OS disk: hasta 4 TiB (4.095 GiB). Para superar los 2 TiB la VM tiene que ser Generation 2 (UEFI/GPT); una Gen 1 con MBR se queda en 2 TiB.
  • Data disks: hasta 32 TiB en Standard HDD / Standard SSD / Premium SSD, y hasta 64 TiB en Premium SSD v2 y Ultra Disk.
  • La cantidad de data disks adjuntables la define el tamaño de la VM, no el tipo de disco. Si necesitás más capacidad total y ya llegaste al límite, agrandás la VM o hacés striping (Storage Spaces / LVM / RAID 0) sobre varios discos.
El disco temporal: la trampa clásica
  • Windows: se monta como D: · Linux: /dev/sdb montado en /mnt.
  • No es un managed disk. Es almacenamiento local del host físico, no se factura aparte, no se puede snapshotear ni respaldar.
  • Su contenido se pierde al deallocar, al resizear, al hacer mantenimiento del host o si la VM cae y se recupera en otro host. Un reboot desde adentro del SO normalmente lo conserva; un deallocate, nunca.
  • Uso legítimo: pagefile / swap, tempdb, archivos scratch. Nunca datos que importen.
⚠️ Trampa del examen: no confundas temporary disk con Ephemeral OS disk. El temp disk es un volumen extra efímero que viene con ciertos tamaños. El Ephemeral OS disk es una opción del disco de sistema: vive en el almacenamiento local del host, es gratis y reimagina rapidísimo, pero no soporta snapshots ni Azure Backup, y se pierde entero al deallocar. Un resize de VM sí está soportado, pero borra el contenido del OS disk y lo reprovisiona. Se elige al crear la VM y no se puede convertir después.
⚡
Host caching: None / ReadOnly / ReadWrite Performance
Qué es

El host caching usa la RAM y el SSD local del host donde corre la VM como caché del managed disk. No lo pagás aparte, pero el techo de "cached IOPS" lo define el tamaño de la VM. Elegir mal el modo puede hacer que una base de datos ande peor que sin caché.

ModoQué cacheaCuándo se usa
NoneNada. Lecturas y escrituras van directo al disco.Cargas de escritura intensiva: log files de bases de datos, colas, append-only. Obligatorio en Ultra Disk y en shared disks.
ReadOnlySolo lecturas. Las escrituras pasan derecho al disco.Data files de bases de datos y cualquier carga read-heavy. Mejora latencia de lectura sin riesgo de consistencia.
ReadWriteLecturas y escrituras.Default del disco de OS. Para data disks, solo si la app maneja su propio flush de escrituras. ✗ Nunca para logs de DB.
La receta que preguntan (SQL Server en una VM): disco de OS → ReadWrite · discos de datos → ReadOnly · discos de log → None.
ℹ️ Cambiar el caching de un data disk lo desadjunta y readjunta (corte breve de I/O). Cambiar el caching del OS disk reinicia la VM. No es un cambio gratis en producción.

Operaciones sobre discos Día a día
Expandir un disco
  • ✓ Se puede agrandar en cualquier momento.
  • ✗ Nunca se puede achicar. Si necesitás un disco más chico: creás uno nuevo del tamaño deseado y copiás los datos.
  • Algunas expansiones exigen la VM deallocada — típicamente el disco de OS y cualquier salto que cruce el umbral de 4 TiB. Los data disks suelen admitir expansión en caliente.
  • Agrandar el disco no agranda el volumen: después hay que extender la partición y el filesystem dentro del SO (Disk Management / diskpart en Windows, growpart + resize2fs o xfs_growfs en Linux).
  • Ojo con el costo: al pasar de tier (ej. P10 → P30) subís de precio aunque uses poco espacio.
⚠️ Trampa del examen: "expandí el disco a 1 TB pero Windows sigue mostrando 128 GB". No es un bug: falta extender el volumen dentro del sistema operativo. Y si te preguntan cómo achicar un disco, la única respuesta correcta es migrar los datos a un disco nuevo.
Script del examen: crear y adjuntar un data disk

El disco se crea vacío y aparte y después se adjunta a la VM. Add-AzVMDataDisk solo muta el objeto en memoria: sin Update-AzVM Azure no se entera.

$rgName = 'UKRG01'; $vmName = 'HRVM01'; $location = 'UK South'
$storageType = 'Premium_ZRS'; $dataDiskName = 'HRDisk05'

$diskConfig = New-AzDiskConfig -SkuName $storageType -Location $location `
  -CreateOption Empty -DiskSizeGB 1024
$dataDisk1 = New-AzDisk -DiskName $dataDiskName -Disk $diskConfig -ResourceGroupName $rgName

$vm = Get-AzVM -Name $vmName -ResourceGroupName $rgName
$vm = Add-AzVMDataDisk -VM $vm -Name $dataDiskName -CreateOption Attach `
  -ManagedDiskId $dataDisk1.Id -Lun 4
Update-AzVM -VM $vm -ResourceGroupName $rgName

CreateOption y SKU que hay que reconocer
  • Al crear el disco: Empty (en blanco), Copy / Import / FromImage / Restore / Upload.
  • Al adjuntar: Attach (disco managed ya existente). Si creás el disco junto con la VM en un solo paso, el Add puede ir con Empty y sin ManagedDiskId — no es este escenario.
  • SKU: Premium_LRS, Premium_ZRS, Standard_LRS, StandardSSD_LRS, StandardSSD_ZRS, UltraSSD_LRS, PremiumV2_LRS. El enunciado “Premium ZRS” es Premium_ZRS.
  • El LUN es el número SCSI del data disk (único por VM). El OS disk no usa ese LUN.
  • Después de adjuntar, el disco está raw: hay que inicializar, particionar y formatear dentro del SO (Initialize-Disk / Disk Management / parted).

# Desadjuntar (el disco managed sigue existiendo y facturando)

Update-AzVM -VM $vm -ResourceGroupName $rgName

Snapshot vs Image vs copia de disco
ArtefactoAlcancePara qué sirveDetalle de examen
Snapshot Un solo disco, point-in-time, solo lectura Rollback rápido, clonar un disco puntual, mover datos entre regiones Los incrementales facturan solo el delta contra el snapshot anterior. Un snapshot por disco no garantiza consistencia entre varios discos de la misma VM → para eso, Azure Backup.
Image (VM image) Toda la VM: OS disk + data disks + config Desplegar nuevas VMs iguales, alimentar VM Scale Sets Puede ser generalized (pasó por sysprep) o specialized (conserva identidad).

Shared disks (clusters)
  • Se habilita con el atributo maxShares del disco: define a cuántas VMs se puede adjuntar al mismo tiempo.
  • Casos: Windows Server Failover Clustering, SQL Server Failover Cluster Instance, SAP ASCS/SCS, clusters de Linux con Pacemaker.
  • Necesita un cluster manager que coordine el acceso con SCSI Persistent Reservations — Azure no serializa las escrituras por vos.
  • Restricciones: ✗ no sirve como disco de OS · ✗ host caching debe ser None · no está disponible en Standard HDD.
OS disk swap

Podés reemplazar el disco de sistema de una VM existente por otro (por ejemplo, uno restaurado de un snapshot) sin recrear la VM: conservás nombre, NIC, IP privada, NSG y extensiones. Requisito: la VM tiene que estar deallocada, y el disco nuevo debe ser del mismo tipo de SO y estar en la misma región y suscripción.

az vm stop --resource-group RG --name VM1
az vm deallocate --resource-group RG --name VM1
az vm update --resource-group RG --name VM1 --os-disk disco-restaurado

Cifrado de discos: SSE, CMK, ADE y encryption at host Seguridad
Las cuatro capas y qué resuelve cada una
  • SSE con platform-managed keys (PMK) — cifrado en reposo de todos los managed disks, snapshots e imágenes. Siempre activo, no se puede desactivar, sin costo ni impacto de performance. Azure administra las claves.
  • SSE con customer-managed keys (CMK) — misma capa, pero la clave la ponés vos vía Disk Encryption Set (DES), que apunta a una clave de Key Vault. Respuesta correcta cuando el escenario dice "la organización debe controlar y rotar sus propias claves".
  • Azure Disk Encryption (ADE) — cifrado dentro del guest OS usando BitLocker (Windows) o dm-crypt (Linux). Se implementa como una extensión de VM. En retiro el 15 sep 2028: para VMs nuevas el outline pide encryption at host.
  • Encryption at host — el host cifra los datos antes de que salgan hacia el storage. Es la única opción que cubre además el disco temporal y las cachés de disco end-to-end. Hay que habilitar la feature a nivel de suscripción y el tamaño de VM tiene que soportarla.

Requisitos que caen en preguntas
  • ADE: el Key Vault tiene que estar en la misma región y suscripción que la VM y tener marcada la política "Enabled for disk encryption" (EnabledForDiskEncryption). Sin eso, la extensión falla.
  • ADE no es compatible con Ultra Disk, Premium SSD v2 ni ephemeral OS disks, y no se combina con encryption at host sobre el mismo disco.
  • CMK / DES: el Key Vault necesita soft delete y purge protection habilitados, y el DES usa una managed identity a la que hay que darle permiso sobre la clave (get / wrap / unwrap). El DES vive en la misma región que los discos.
Script ADE del examen (PowerShell drop-down)

El vault y la VM suelen estar en resource groups distintos. El orden es fijo: traer el vault → extraer URI e ID → instalar la extensión sobre la VM.

$keyVaultRG = 'myKeyVaultResourceGroup'
$vmRG       = 'myVirtualMachineResourceGroup'
$vmName     = 'mySecureVM'
$keyVaultName = 'mySecureVault'

$keyVault = Get-AzKeyVault -VaultName $keyVaultName -ResourceGroupName $keyVaultRG
$diskEncryptionKeyVaultUrl = $keyVault.VaultUri
$keyVaultId = $keyVault.ResourceId

Set-AzVMDiskEncryptionExtension `
  -ResourceGroupName $vmRG `
  -VMName $vmName `
  -DiskEncryptionKeyVaultUrl $diskEncryptionKeyVaultUrl `
  -DiskEncryptionKeyVaultId $keyVaultId

Palanca de ahorro
  • Auto-shutdown — propiedad de la VM (heredada de DevTest Labs): programás una hora diaria de apagado con su zona horaria y notificación previa opcional por webhook o mail. Deallocca la VM. No existe auto-start equivalente en una VM suelta.
  • Azure Spot VMs — capacidad sobrante con descuento fuerte, sin SLA. Azure puede desalojarlas cuando necesita la capacidad o cuando el precio supera tu max price (-1 = pagás hasta el precio on-demand y solo te desalojan por capacidad). Aviso de desalojo corto.
    • Eviction policy = Deallocate: la VM se deallocca, los discos quedan (y se pagan) y podés reiniciarla cuando haya capacidad.
    • Eviction policy = Delete: se borra la VM junto con sus discos. Nada que reiniciar.
    Solo para cargas interrumpibles (batch, CI, render farms). No se puede convertir una VM normal en Spot ni al revés, y no van en availability sets.
  • Reserved Instances — te comprometés a 1 o 3 años de un tamaño en una región a cambio de un descuento grande. Cubre el cómputo, no la licencia del SO ni el software. El scope puede ser shared, single subscription o single resource group. Se combina con Azure Hybrid Benefit (licencias Windows Server / SQL propias) para bajar todavía más.
Acceso administrativo: el orden de preferencia
  • Azure Bastion — RDP/SSH desde el browser por TLS (443) contra el portal; la VM no necesita IP pública y no exponés 3389/22. Requiere una subnet llamada exactamente AzureBastionSubnet, de /26 o más grande, en la misma VNet (o peered).
  • Just-in-Time VM access (JIT) — feature de Microsoft Defender for Cloud: los puertos de administración quedan cerrados en el NSG y se abren bajo pedido, por una ventana de tiempo y desde una IP origen específica, con auditoría.
  • RDP 3389 / SSH 22 abiertos a Internet — nunca es la respuesta correcta en un escenario de seguridad.
  • Si perdiste la contraseña o la clave: extensión VMAccess ("Reset password" en el portal), que resetea credenciales sin recrear la VM.
💡 Regla rápida de escenarios: "sin IP pública y sin cliente instalado" → Bastion. "Necesito RDP puntual pero cerrado el resto del tiempo" → JIT. "Quiero que se apague sola todas las noches" → Auto-shutdown. "Carga batch que tolera cortes" → Spot. "Servidor 24×7 previsible por 3 años" → Reserved Instance.

Mover VMs: resource group, subscription y región Movilidad
Son tres operaciones distintas, no una

El examen mezcla a propósito tres cosas que se parecen en la pregunta pero no comparten ni herramienta ni resultado. Antes de elegir la respuesta, fijate qué cambia en cada caso: el resource group, la subscription o la región física.

La distinción que define la pregunta: az resource move NO cambia la región del recurso. Mueve la VM de contenedor lógico (resource group / subscription) y nada más: los bits siguen en el mismo datacenter. Si el escenario dice "la VM tiene que quedar en West Europe en vez de East US", ninguna variante de move sirve → Azure Resource Mover.
⚠️ Trampa del examen: "moví la VM al resource group nuevo, ¿ahora está en otra región?" No. Mover ≠ migrar. Y en la otra dirección: la región de una VM no se puede editar — no hay propiedad para cambiarla. La respuesta a "cambiar de región" siempre es replicar o recrear (Resource Mover, Site Recovery, o snapshot → disco en la región destino → VM nueva), nunca un move.
Qué se mueve junto con la VM

Una VM no viaja sola: el move falla con MissingMoveDependentResources si dejás alguna dependencia atrás.

  • Managed disks (OS y data) — Microsoft.Compute/disks.
  • NIC(s) — y en un move cross-subscription, todas las NICs de esa VNet, no solo la de tu VM.
  • Public IP address y Network Security Group.
  • Virtual network — para cambiar de subscription, la VNet y todos sus recursos dependientes tienen que moverse también.
  • Load balancer y demás recursos de red asociados.
  • Solo se listan los recursos padre: los recursos hijos se mueven solos y no se pueden mover por separado.

Si las dependencias están repartidas en varios resource groups, el patrón de Microsoft es: 1) consolidarlas primero en un mismo RG, 2) mover todo junto a la subscription destino, 3) redistribuirlas en RGs distintos ya del otro lado.

Cómo se hace (CLI) y el paso de validación
# Validar ANTES de mover (misma API que el botón "Validate" del portal)
az resource invoke-action --action validateMoveResources \
  --ids "/subscriptions/<sub>/resourceGroups/RG-origen" \
  --request-body "{ \"resources\": [\"<id-vm>\",\"<id-disco>\",\"<id-nic>\"], \
                    \"targetResourceGroup\": \"/subscriptions/<sub>/resourceGroups/RG-destino\" }"

# Mover a otro resource group
az resource move --destination-group RG-destino --ids $vm $disco $nic $pip $nsg

# Mover a otra subscription
az resource move --destination-group RG-destino \
  --destination-subscription-id <sub-destino> --ids $vm $disco $nic $pip $nsg

Equivalente en PowerShell: Move-AzResource -DestinationResourceGroupName RG-destino -ResourceId $ids, con -DestinationSubscriptionId para cruzar suscripción.

Checklist previo (lo que valida el portal antes de dejarte mover)
  • Ambas subscriptions activas y en el mismo Microsoft Entra tenant. Si están en tenants distintos, primero hay que transferir la subscription al tenant correcto.
  • El resource provider del recurso tiene que estar registrado en la subscription destino (az provider register --namespace Microsoft.Compute).
  • Cuota suficiente en el destino (vCPUs, IPs públicas, etc.).
  • Permisos: Microsoft.Resources/subscriptions/resourceGroups/moveResources/action en el origen y .../resourceGroups/write en el destino.
  • Read-only locks en el RG o la subscription (origen o destino) bloquean el move: sacalos antes.
  • Ningún recurso ni dependencia en estado failed (MoveCannotProceedWithResourcesNotInSucceededState) y ninguna Azure Policy que impida crear el recurso en el destino (RequestDisallowedByPolicy).
  • Máximo 800 recursos por operación de move.
⚠️ Trampa del examen: durante el move, el resource group origen y el destino quedan bloqueados hasta 4 horas — no se puede crear, borrar ni modificar propiedades de nada ahí adentro. Los recursos siguen funcionando (no hay downtime), pero cualquier pipeline de deploy que apunte a esos RGs falla mientras dure la operación.
ℹ️ Como el resource ID cambia, todo lo que lo referencie por ID queda roto: scripts, plantillas ARM/Bicep, dashboards, alertas y automatizaciones. Además, las asignaciones RBAC heredadas del scope viejo no viajan con el recurso — hay que rehacerlas en el destino.
Qué NO se puede mover (respuestas "ninguna de las anteriores")
  • ✗ Una VM que está en un availability set, individualmente: se mueve el availability set completo con sus VMs.
  • ✗ Spot / low-priority VMs y scale sets low-priority: ni entre resource groups ni entre subscriptions.
  • ✗ VMs con scheduled patching configurado.
  • ✗ VMs creadas desde una imagen de Marketplace con plan adjunto, cross-subscription (workaround: clonar el OS disk, aceptar los términos del Marketplace en la subscription destino y recrear la VM con la info del plan).
  • ✗ Cualquier recurso asociado a una Public IP Standard SKU, cross-subscription: hay que desasociar la IP primero.
  • ✗ Snapshots incrementales (solo se mueven los full), restore point collections y dedicated hosts / host groups.
  • Una VNet con peering se mueve, pero hay que deshabilitar el peering antes y rehacerlo después.
Casos especiales de VM: cifrado y backup
  • Azure Disk Encryption + Key Vault → a otro resource group se puede, pero con la VM deallocada. A otra subscription hay que deshabilitar el cifrado primero: az vm encryption disable --resource-group RG --name VM1 --volume-type all.
  • Azure Backup → hay que borrar las restore point collections (los snapshots que el vault deja en AzureBackupRG_*) antes de mover, y reconfigurar el backup después. Si el vault tiene soft delete activo y hay restore points retenidos, o lo deshabilitás o esperás 14 días desde que los borraste.
Cambio de región: Azure Resource Mover

Es el servicio dedicado a mover recursos entre regiones, con detección automática de dependencias. Soporta VMs y sus discos (no Spot), VMs cifradas, NICs, availability sets, VNets, NSGs, Public IPs, load balancers internos y públicos, y Azure SQL databases / elastic pools. También permite aterrizar las VMs en availability zones de la región destino. El servicio no tiene costo propio; pagás lo de abajo (replicación tipo Site Recovery, storage de las réplicas y transferencia de datos).
