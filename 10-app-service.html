App Service Plan: el hardware detrás de la app Base
Qué es un plan realmente
  • Un App Service Plan es el conjunto de VMs (instancias) donde corren tus apps. Vos no ves las VMs, pero pagás por ellas: pagás el plan, no la app.
  • Varias apps pueden compartir un mismo plan. Si lo hacen, comparten las mismas instancias, la misma CPU, la misma RAM y el mismo disco. Una app que se come el CPU degrada a todas las demás del plan.
  • El escalado es una propiedad del plan, no de la app individual. No podés escalar una sola app dentro de un plan compartido: si necesitás aislarla, la movés a otro plan.
  • El plan define region, sistema operativo (Windows/Linux) y tier. Una app solo se puede mover a otro plan si ambos planes comparten el mismo webspace: la combinación de región + sistema operativo + resource group con el que se creó el plan. Mover el plan a otro RG después no cambia el webspace — dos planes en el mismo RG hoy pueden no ser intercambiables.
  • El límite de deployment slots, el máximo de instancias y el storage disponible también son del plan.

Anatomía de una regla de autoscale
  • Métrica: CPU Percentage, Memory Percentage, Http Queue Length, Data In/Out, o una métrica de otro recurso (por ejemplo la longitud de una Service Bus queue).
  • Operador y umbral: por ejemplo CPU Percentage > 70.
  • Duración (time grain / duration): cuánto tiempo tiene que sostenerse la condición antes de disparar. Evita reaccionar a un pico de 10 segundos.
  • Agregación: Average, Minimum, Maximum, Total.
  • Acción: increase/decrease count by N, o increase/decrease to N.
  • Cool down: tiempo de espera después de una acción de escalado antes de volver a evaluar. Sirve para que las instancias nuevas alcancen a tomar carga antes de decidir otra vez.
  • Instance limits del perfil: mínimo, máximo y default. El máximo lo topa el tier del plan.
Perfiles y prioridad
  • Scale based on a metric: reglas dinámicas como las de arriba.
  • Scale to a specific instance count: valor fijo.
  • Podés tener perfiles recurrentes (días/horas fijos, por ejemplo días hábiles de 8 a 20) o de fecha específica (un evento puntual). Los perfiles de fecha/recurrencia tienen prioridad sobre el perfil default durante su ventana.
⚠️ Trampa del examen: una regla de scale-out sin su regla de scale-in nunca vuelve para atrás — la app se queda para siempre en el máximo de instancias y la factura explota. Siempre hay que definir las dos reglas en pares. Y ojo con el umbral: si escalás out con CPU > 70 y escalás in con CPU < 70, provocás flapping (agrega/quita sin parar); dejá un margen, por ejemplo out > 70 e in < 30.
💡 Cuando varias reglas de scale-out se cumplen a la vez, autoscale ejecuta la que produce más instancias. Para scale-in, todas las reglas tienen que cumplirse y aplica la que menos reduce. Autoscale privilegia la disponibilidad por sobre el ahorro.

Deployment Slots Estrella del examen
Qué es un slot
  • Un slot es una app viva y separada, con su propio hostname (miapp-staging.azurewebsites.net), pero corre en el mismo App Service Plan y consume sus mismas instancias.
  • El swap no es un redeploy: es un cambio de routing entre los dos slots. Por eso es prácticamente instantáneo y no hay downtime en frío.
  • Antes de intercambiar, Azure hace warm-up del slot destino: aplica la configuración del slot de producción, reinicia los workers y espera a que respondan. Recién cuando el slot está caliente, invierte el routing.
  • Rollback = otro swap. Volvés a intercambiar y la versión anterior, que quedó en staging, vuelve a producción. No hay que redeployar nada.
  • Requiere Standard (5 slots) o Premium/Isolated (20 slots). Ese número incluye el slot de producción: en Standard son 4 staging + producción. Si tenés más de 5 slots, no podés bajar el plan a Standard.

Sticky (slot settings): qué se intercambia y qué no

Un app setting o connection string marcado como "deployment slot setting" queda pegado al slot: no viaja en el swap. Es el mecanismo para que staging siga apuntando a la base de datos de staging y producción a la de producción, aunque el código se intercambie.

⚠️ Trampa del examen: el enunciado clásico dice "después del swap, producción quedó apuntando a la base de datos de test". La causa es que la connection string no estaba marcada como deployment slot setting, entonces viajó con el swap. La solución no es cambiar el código: es tildar el checkbox de slot setting en ambos slots. Y ojo: los custom domains y las Access Restrictions nunca se intercambian.
Swap with preview (multi-phase swap)
  1. Fase 1: Azure aplica la configuración del slot de producción sobre el slot de staging (incluidos los slot settings de producción) y lo reinicia, pero todavía no cambia el routing. Podés probar staging con la config real de producción en su propio hostname.
  2. Fase 2: si la prueba sale bien hacés Complete swap y recién ahí se invierte el routing. Si sale mal, Cancel swap y staging vuelve a su configuración original.

Es la respuesta cuando la pregunta pide "validar la app con la configuración de producción antes de exponerla a usuarios".

Switch-AzWebAppSlot -ResourceGroupName myRG -Name myApp `
  -SourceSlotName source -DestinationSlotName production `
  -SwapWithPreviewAction ApplySlotConfig

Switch-AzWebAppSlot -ResourceGroupName myRG -Name myApp `
  -SourceSlotName source -DestinationSlotName production `
  -SwapWithPreviewAction CompleteSlotSwap

# cancelar: -SwapWithPreviewAction ResetSlotSwap
# CLI: az webapp deployment slot swap --action preview|swap|reset

Traffic routing (A/B testing y canary)
  • Podés enrutar un porcentaje del tráfico de producción a un slot sin hacer swap. Ideal para canary releases y pruebas A/B.
  • Azure le asigna al cliente la cookie x-ms-routing-name para que quede pegado al mismo slot durante toda su sesión (client affinity).
  • Se puede forzar el destino por query string: ?x-ms-routing-name=staging manda al slot staging, y ?x-ms-routing-name=self devuelve al slot de producción.
  • Un slot con porcentaje 0% sigue siendo alcanzable a mano con ?x-ms-routing-name=<slot>: sirve para beta opt-in.
✅ Para que el warm-up sea real y no un simple ping, se usan los app settings WEBSITE_SWAP_WARMUP_PING_PATH y WEBSITE_SWAP_WARMUP_PING_STATUSES, que le dicen a Azure qué ruta consultar y qué códigos HTTP considerar válidos antes de completar el swap.

Networking outbound: salir de la app Salida
VNet Integration (regional)
  • Permite que la app alcance recursos privados dentro de una VNet: una VM, una SQL Managed Instance, un Private Endpoint de Storage, un balanceador interno.
  • Es solo tráfico de salida (outbound). No hace que la app sea accesible desde la VNet ni le da IP privada de entrada. Para eso está Private Endpoint.
  • Requiere una subred vacía y delegada a Microsoft.Web/serverFarms. Clásicamente esa subred la usaba un solo App Service Plan; con multi plan subnet join hoy varios planes de la misma suscripción pueden compartirla, y en ese caso el mínimo pasa a ser /26.
  • Tamaño de subred: mínimo /28, recomendado /26 — Azure consume IPs de esa subred por cada instancia, y durante un scale out o un cambio de tier necesita direcciones extra.
  • La VNet tiene que estar en la misma región que el App Service Plan.
Route All: forzar todo el tráfico por la VNet
  • Por defecto, con VNet Integration solo va por la VNet el tráfico dirigido a rangos privados RFC 1918. El tráfico a internet sale directo por la infraestructura de App Service.
  • El app setting WEBSITE_VNET_ROUTE_ALL = 1 (o la propiedad vnetRouteAllEnabled en Configuration → Networking) fuerza que todo el tráfico de salida pase por la VNet.
  • Recién con Route All activo tienen efecto sobre la app las NSG y las UDR de la subred — por ejemplo para forzar el tráfico a un Azure Firewall.
  • Combinado con un NAT Gateway en la subred de integración, la app sale a internet con una IP pública fija y predecible. Es la respuesta cuando un tercero pide que le declares las IPs de origen para su allow-list.
Hybrid Connections
  • Da acceso a un recurso on-premises (o en otra nube) sin VNet, sin VPN y sin ExpressRoute.
  • Va por Azure Relay: se instala el Hybrid Connection Manager (HCM) en un servidor Windows de la red on-prem, y ese agente hace la conexión saliente al Relay. No hace falta abrir puertos entrantes en el firewall.
  • Cada Hybrid Connection apunta a un host y un puerto TCP específicos — es 1 a 1, no da acceso a toda la red.
  • Requiere Basic o superior (no está en Free/Shared). El número de Hybrid Connections por plan sube con el tier.
⚠️ Trampa del examen: "la app tiene que llegar a un SQL Server on-premises y no hay VPN ni ExpressRoute" → la respuesta es Hybrid Connections, no VNet Integration. VNet Integration por sí sola solo te lleva hasta la VNet de Azure; para saltar a on-prem desde ahí necesitás además un Site-to-Site VPN Gateway o ExpressRoute.
💡 VNet Integration sin Route All + Service Endpoints en la subred es el patrón económico para llegar a un Storage Account o a Azure SQL con firewall cerrado. Si además necesitás inspeccionar o filtrar la salida a internet, ahí sí prendés Route All.

Networking inbound: proteger la entrada Entrada
Access Restrictions
  • Lista de reglas allow / deny evaluadas por prioridad numérica: el número más bajo se evalúa primero, y gana la primera regla que matchea.
  • Tipos de regla:
    • IPv4 / IPv6 en notación CIDR.
    • Virtual Network (subred), que usa Service Endpoint Microsoft.Web en esa subred.
    • Service Tag, por ejemplo AzureFrontDoor.Backend para que solo Front Door pueda pegarle al origen.
    • Filtro por http header (X-Forwarded-For, X-Azure-FDID, etc.) como condición adicional de una regla.
  • Regla implícita: si existe al menos una regla allow, se agrega automáticamente un deny all al final. Si solo hay reglas deny, todo lo demás sigue permitido.
  • El sitio SCM/Kudu (<app>.scm.azurewebsites.net) tiene su propio conjunto de reglas, con la opción de heredar las del sitio principal ("same restrictions as main site"). Si lo dejás abierto, cerraste la puerta pero dejaste la ventana.
⚠️ Trampa del examen: agregar una sola regla de tipo allow para la red corporativa bloquea al resto del mundo automáticamente por la deny implícita — incluidos monitores, webhooks y pipelines. Y a la inversa: agregar solo reglas deny no restringe nada más allá de lo denegado. Además, restringir el sitio principal no restringe SCM/Kudu: eso se configura aparte.
Private Endpoint
  • Le da a la app una IP privada dentro de tu VNet; el acceso público queda deshabilitado. Es entrada, no salida.
  • Necesita resolución DNS privada: la zona privatelink.azurewebsites.net vinculada a la VNet. Sin eso, el nombre sigue resolviendo a la IP pública y falla.
  • No está disponible en Free/Shared. Se combina habitualmente con VNet Integration: Private Endpoint para entrar, VNet Integration para salir.
App Service Environment (ASE) · tier Isolated
  • Deployment single-tenant de App Service dentro de tu propia VNet: la infraestructura no se comparte con ningún otro cliente.
  • Puede ser externo (VIP pública) o interno con Internal Load Balancer (ILB), que deja la app accesible solo desde la VNet y requiere DNS propio para el dominio del ASE.
  • Es el tier Isolated: el más caro, con la escala más alta y el aislamiento de red más fuerte. Se elige por requisitos de compliance o aislamiento total, no por performance.
💡 VNet Integration ≠ ASE. VNet Integration inyecta el tráfico de salida de una app multi-tenant en tu VNet; la app sigue corriendo en infraestructura compartida y con endpoint público. Un ASE despliega toda la infraestructura de App Service dentro de tu VNet. Si la pregunta pide "aislamiento completo / single-tenant / dedicated hardware", es ASE + Isolated. Si pide "que la app llegue a una VM privada", es VNet Integration.

Límites del managed certificate: no es exportable, no sirve como certificado de cliente, no se puede usar para dominios que no resuelven públicamente, no soporta wildcard ni apex/naked domain (solo subdominios), un certificado gratis por custom domain, y no está soportado en App Service Environment. Wildcard o exportable → App Service Certificate o .pfx.

Endurecer el transporte
  • HTTPS Only: redirige cualquier request HTTP a HTTPS. Se prende en Configuration → General settings / TLS-SSL settings.
  • Minimum TLS version: se fija la versión mínima aceptada (1.0, 1.1, 1.2, 1.3). Para compliance normalmente se exige 1.2 o superior.
Drop-down ARM: TLS mutual authentication (client certs)

Exigir certificado de cliente en un App Service, con una ruta exceptuada. Las tres properties van en Microsoft.Web/sites → properties, al mismo nivel que siteConfig, no adentro.

PropertyValor del escenarioQué hace
clientCertEnabledtruePrende mTLS. Default false: si está apagado, clientCertMode se ignora
clientCertMode"Required"Required = obligatorio. También: Optional, OptionalInteractiveUser
clientCertExclusionPaths"/sample1"Paths (separados por coma) que no piden cert. El resto sí
clientAffinityEnabledNoCookie ARR / session affinity. No es mTLS

{
  "type": "Microsoft.Web/sites",
  "apiVersion": "2020-06-01",
  "name": "[parameters('myWebApp')]",
  "properties": {
    "serverFarmId": "[resourceId('Microsoft.Web/serverfarms', variables('plan'))]",
    "siteConfig": { "linuxFxVersion": "[parameters('linuxFxVersion')]" },
    "clientCertEnabled": true,
    "clientCertMode": "Required",
    "clientCertExclusionPaths": "/sample1"

}

az webapp update -g RG -n myapp --set clientCertEnabled=true \
  clientCertMode=Required clientCertExclusionPaths=/sample1
Set-AzWebApp -ResourceGroupName RG -Name myapp -ClientCertEnabled $true
⚠️ Trampa del examen: mTLS = las tres clientCert* en properties del site, no en siteConfig. clientAffinityEnabled es sticky session. Required vs Optional: el escenario “required client certificates” es Required. Una exclusion path no apaga el mTLS del resto del sitio.
⚠️ Trampa del examen: para el apex/root domain no alcanza con el A record — Azure exige además el TXT de verificación asuid.<dominio> con el Custom Domain Verification ID, o el binding falla. Y no confundas: SNI SSL es gratis y es el default; IP-Based SSL cuesta plata, se usa solo para clientes viejos sin SNI y cambia la IP entrante de la app.

Key Vault sin secretos en el código
  1. Prendés una Managed Identity en la app (Settings → Identity).
  2. Le das permiso de lectura de secretos en el Key Vault: rol Key Vault Secrets User si el vault usa RBAC, o una access policy con Get si usa el modelo de policies.
  3. En vez de guardar el valor, ponés una Key Vault reference como app setting: 
    @Microsoft.KeyVault(SecretUri=https://mivault.vault.azure.net/secrets/DbPassword/)

@Microsoft.KeyVault(VaultName=mivault;SecretName=DbPassword)
  4. App Service resuelve la referencia en runtime y la app lee un app setting común y corriente. En el portal aparece el estado Resolved si funcionó.
⚠️ Trampa del examen: una Key Vault reference que no resuelve casi siempre es por falta de permisos de la managed identity sobre el vault (o porque el vault tiene el firewall cerrado a la app). No se arregla cambiando la sintaxis. Y recordá: si borrás la app, la system-assigned identity desaparece junto con todas sus asignaciones de rol — si necesitás que los permisos sobrevivan, usás user-assigned.
Easy Auth (App Service Authentication)
  • Módulo de autenticación que corre fuera del código, delante de la app: no hay que tocar la aplicación ni instalar librerías.
  • Proveedores soportados: Microsoft Entra ID, Facebook, Google, X, Apple y cualquier proveedor OpenID Connect genérico.
  • Para requests no autenticados elegís la acción: "Allow unauthenticated access" (deja pasar y que la app decida) o "Require authentication", que redirige al login del proveedor (HTTP 302) o devuelve 401/403 — esto último es lo correcto para APIs.
  • Inyecta claims e info del usuario en headers y expone el endpoint /.auth/me.

Deployment y contenedores CI/CD
Deployment Center · fuentes
  • GitHub Actions: Azure genera el workflow YAML en el repo y configura las credenciales.
  • Azure Repos / Azure DevOps Pipelines.
  • Bitbucket.

⚠️ Trampa del examen: fuentes nativas de Deployment Center = GitHub, Azure DevOps/Repos, Bitbucket, Local Git, FTP, ZIP. AWS CodeCommit no.

Backup de App Service: automático vs custom

Hay dos tipos. Automático corre solo si el plan es Basic+. Custom hay que configurarlo (storage + schedule). En Basic solo se respalda el slot de producción.

TiersBasic, Standard, Premium, IsolatedBasic, Standard, Premium, Isolated

Linked databasesNoSí (SQL, MySQL, PostgreSQL, MySQL in-app). Flexible Server no. Deprecado 31/3/2028

DescargableNoSí, como blobs

Yes/No: 6 GB de sitio + MySQL 3 GB, Premium, 1/día, retención indefinida
AfirmaciónPor qué
Los backups automáticos incluyen las linked databasesNoAutomático = config + filesystem. La DB no entra
Los backups custom soportan retención indefinidaYes0–30 días o never delete. Automático no: siempre 30

6 + 3 = 9 GB: entra en el tope custom de 10 GB (DB ≤ 4 GB). Para incluir MySQL + 1/día + retención infinita + storage Premium, es custom.

# Custom: 1/día, retención indefinida, incluir MySQL
az webapp config backup update -g RG -n APP \
  --container-url $SAS --frequency 1d --retention 0 \
  --db-type MySql --db-name db1 --db-connection-string "$CS"

# On-demand
az webapp config backup create -g RG -n APP --container-url $SAS --backup-name b1

# Snapshots automáticos (no incluyen DB)
az webapp config snapshot list -g RG -n APP
⚠️ Trampa del examen: automático no incluye linked databases — eso es solo custom. Retención indefinida = custom (--retention 0); automático está clavado en 30 días. “Premium storage pricing tier” no es Isolated ni un SKU de Azure Backup: custom corre en Premium (plan y/o storage account que vos pongas). Flexible Server no entra en el backup custom.

Always On
  • Sin Always On, una app que no recibe requests durante 20 minutos se descarga de memoria, y el próximo request paga el arranque en frío.
  • Es obligatorio para WebJobs continuos y para timers que tienen que seguir corriendo sin tráfico entrante.
  • Está disponible desde Basic en adelante; no existe en Free/Shared.

ASP.NET Core en App Service Windows. Logs de aplicación ≥ 1 semana, solo Warning o superior.

Escala (de más a menos): Verbose → Information → Warning → Error → Critical. Elegís el piso y entra todo lo más grave.

az webapp log config -g RG -n APP --application-logging azureblobstorage \
  --level warning --retention-period 7
⚠️ Trampa del examen: “al menos una semana” mata Filesystem (12 h). Blob es el que retiene días. Warning = Warning y más graves, no “solo Warning”. Linux no tiene el mismo toggle Filesystem/Blob de Windows: esta pregunta es Windows.
Herramientas de troubleshooting
  • Log Stream: consola en vivo con los logs de la app y del web server. Requiere tener el logging habilitado.
  • Application Insights: telemetría de aplicación — requests, dependencias, excepciones, live metrics, application map y profiler. Se puede habilitar sin tocar el código (instrumentación automática).
  • Kudu / Advanced Tools: https://<app>.scm.azurewebsites.net. Da consola de comandos, explorador de archivos, process explorer, environment, deployment logs y los endpoints de deploy.
  • Diagnose and solve problems: detectores guiados para caídas, uso de memoria, reinicios y problemas de performance.
  • Health check: se define una ruta y App Service saca de rotación las instancias que no responden — solo tiene sentido con dos o más instancias.
✅ Regla rápida de operación: Log Stream para ver qué está pasando ahora, Application Insights para entender por qué la app está lenta, Diagnostic Settings + Log Analytics cuando el requisito dice "retener y consultar los logs a largo plazo", y Kudu cuando necesitás mirar el filesystem o las variables de entorno reales del worker.
