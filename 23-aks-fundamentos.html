Conexión y contexto kubeconfig

kubectl no “se conecta a Azure”. Habla con el API server de Kubernetes usando un archivo de kubeconfig. En AKS, Azure te genera ese archivo; en un cluster sobre VMs, lo copiás vos del control plane.

az aks get-credentials
az aks get-credentials -g rg-aks-lab -n aks-lab
# escribe / mergea en ~/.kube/config y deja ese cluster como contexto actual

az aks get-credentials -g rg-aks-lab -n aks-lab --overwrite-existing
# pisa una entrada previa del mismo cluster

az aks get-credentials -g rg-aks-lab -n aks-lab --admin
# credencial de cluster admin (bypass de Entra ID / Kubernetes RBAC de usuarios)
  • Sin --admin: autenticás con tu identidad de Entra (si el cluster tiene integración). Con --admin: usás el certificado de administrador del cluster. Para un lab personal, cualquiera sirve; en un cluster compartido, --admin es un privilegio que no deberías tener de default.
  • El comando mergea en ~/.kube/config. Si ya tenías otro cluster (minikube, otro AKS), no lo borra: suma un contexto y te deja parado en el nuevo.
  • Necesitás el rol Azure Azure Kubernetes Service Cluster User Role (o Admin) sobre el cluster. Sin eso, get-credentials falla aunque seas Contributor de las VMs.
Contextos: en qué cluster estás parado

Un kubeconfig tiene clusters (API servers), users (credenciales) y contexts (la dupla cluster+user, a veces con namespace). kubectl usa el contexto actual para todo.

kubectl config get-contexts
kubectl config current-context
kubectl config use-context <nombre>
kubectl cluster-info          # URL del API server y del DNS interno
kubectl get nodes             # primera prueba de que la auth funciona
  • El nombre típico del contexto AKS es <cluster> o algo tipo clusterUser_rg-aks-lab_aks-lab.
  • Si un comando “no encuentra recursos” que vos sabés que existen, mirá primero el contexto y el namespace (-n / --all-namespaces). Es el error de operador #1.
En VMs sería: instalás kubeadm (o k3s, RKE) en VMs, el API server escucha en la IP del control plane, y copiás /etc/kubernetes/admin.conf a tu ~/.kube/config. No hay az aks get-credentials: el archivo es el mismo formato, otra forma de obtenerlo. kubectl config y cluster-info no cambian.

ObjetoPara qué existeLo operás vos?
Pod La unidad que corre. Uno o más contenedores que comparten red y volúmenes (igual que un container group de ACI). Es efímero: si el nodo se muere, el Pod se va. No tiene IP estable a lo largo del tiempo. Casi nunca — un Pod “suelto” no se recrea solo. En producción siempre hay un controlador arriba.
ReplicaSet Garantiza que haya N Pods con el mismo template y las mismas labels. Si matás un Pod, levanta otro. No — el Deployment lo crea y lo reemplaza en cada rolling update. Si lo editás a mano, el Deployment te lo pisa.
Deployment El objeto de aplicación. Declara imagen, réplicas, labels y la estrategia de update. Debajo deja ReplicaSets viejos para poder hacer rollback. Sí — kubectl apply, scale, set image, rollout.
Service Una IP virtual (ClusterIP) y un nombre DNS estables. Elige Pods por selector de labels, no por nombre. Cuando un Pod se recrea y cambia de IP, el Service sigue apuntando a “los que matchean”. Sí — es independiente del Deployment. Los une el label, no un parent.
Por qué no se toca el ReplicaSet: el Deployment es el que sabe “esta es la revisión 3, la 2 queda por si hay rollback”. Si hacés kubectl scale replicaset/… o le cambiás el selector, el Deployment reconcilia y deshace tu cambio — o peor, dejás dos ReplicaSets peleando por los mismos Pods. Escalá el Deployment. Borrá Pods si querés forzar recreación; el ReplicaSet los vuelve a crear.
Namespace
  • Caja de nombres. default, kube-system (CoreDNS, metrics-server: no toques) y los que creés vos.
  • Un Service en prod no “ve” Pods de dev aunque las labels coincidan: el selector es dentro del namespace.
  • kubectl get pods sin -n lista solo el namespace del contexto (casi siempre default). -A es todos.
En VMs sería: exactamente los mismos objetos y la misma API. AKS no te da un “Deployment de Azure”. La diferencia es que en VMs vos corrés kube-apiserver, etcd, scheduler y kubelet. El YAML no cambia.

Publicar / desplegar una app apply + rolling

Manifiesto mínimo de un Deployment. Lo que no puede faltar: imagen, réplicas, containerPort, y labels = selector (si no matchean, el ReplicaSet no adopta los Pods y ves 0 ready para siempre).

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web          # tiene que coincidir con el selector de arriba
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web              # tiene que coincidir con las labels del Pod
  ports:
  - port: 80
    targetPort: 80
  type: ClusterIP         # default; solo visible dentro del cluster
kubectl apply y el rolling update
kubectl apply -f web.yaml
kubectl get deploy,rs,pods,svc -l app=web
kubectl rollout status deployment/web
  • apply es declarativo: Kubernetes deja el objeto como dice el archivo. Si cambias la imagen o las réplicas y volvés a apply, hace un rolling update: levanta Pods nuevos, espera a que estén Ready, baja los viejos. Default: maxUnavailable=25%, maxSurge=25%.
  • No hay downtime si hay al menos 2 réplicas y el probe de readiness está bien (o, sin probe, si el contenedor arranca rápido).
  • kubectl create -f falla si el objeto ya existe. En el día a día usá apply.
⚠️ Trampa real de operador: el selector del Deployment y las labels del template tienen que ser el mismo set. Si el Service dice app: web y el Pod dice app: nginx, el Deployment está “sano” (Pods Running) y el Service tiene 0 endpoints. La app “no responde” y el YAML “está aplicado”. El diagnóstico está en la sección de Endpoints.
En VMs sería: el mismo kubectl apply -f. La imagen tiene que ser reachable desde los workers (registry privado + imagePullSecrets, o un registry local). AKS te resuelve el pull a ACR con --attach-acr; en VMs eso no existe — configurás auth del kubelet o un Secret kubernetes.io/dockerconfigjson.

Para quéConfig no sensible: URLs, feature flags, nginx.conf, nivel de log.Passwords, connection strings, certificados, tokens.
AlmacenamientoTexto plano en etcd.Base64 en etcd (eso no es cifrado; es encoding). En AKS se puede envolver con encryption at rest / KMS.
Cómo se consumeVariables de entorno o archivos en un volumen montado. Misma mecánica en los dos.
Env var vs volumen montado
  • Env var: se inyecta al crear el contenedor. Es un snapshot. Cambiar el ConfigMap/Secret no reinicia el Pod y no actualiza la variable. El proceso sigue con el valor viejo hasta que el contenedor se recree.
  • Volumen: kubelet actualiza los archivos en el mount (con delay, orden de segundos). El proceso tiene que releer el archivo: nginx no se entera solo; una app que lee la config una vez al boot tampoco. Para que tome el cambio: kubectl rollout restart deployment/web.
⚠️ La trampa que te come en producción: actualizás el ConfigMap, kubectl get configmap ya muestra el valor nuevo, y la app sigue con el viejo. No es un bug de Kubernetes: las env vars no son live. El fix es kubectl rollout restart deployment/<nombre> (recrea Pods, el ReplicaSet nuevo lee el ConfigMap actual). Algunos usan un checksum del ConfigMap como annotation en el Pod para forzar el rolling al hacer apply. 
# envFrom: todas las keys del ConfigMap como variables
envFrom:
- configMapRef:
    name: web-config

# una sola key
env:
- name: LOG_LEVEL
  valueFrom:
    configMapKeyRef:
      name: web-config
      key: logLevel

# como archivos en /etc/config
volumeMounts:
- name: cfg
  mountPath: /etc/config
volumes:
- name: cfg
  configMap:
    name: web-config
En VMs sería: igual. etcd lo corrés vos: protegé el acceso al API server y considerá encryption at rest para Secrets. AKS ya cifra el disco de etcd; el Base64 en kubectl get secret -o yaml se sigue viendo si tenés permiso de leer el objeto.

Actualizar la versión de una app set image · undo

Tres formas de cambiar la imagen: editar el YAML y apply, kubectl edit deploy/web, o el atajo kubectl set image. Las tres disparan un rolling update y dejan una revisión en el historial.

kubectl set image deployment/web nginx=nginx:1.27.1
kubectl rollout status deployment/web
kubectl rollout history deployment/web
kubectl rollout history deployment/web --revision=3   # qué cambió en esa rev
kubectl rollout undo deployment/web                   # vuelve a la anterior
kubectl rollout undo deployment/web --to-revision=2   # a una específica
Qué está pasando debajo
  • El Deployment crea un ReplicaSet nuevo con el template nuevo y escala el viejo a 0. El RS viejo no se borra de inmediato: por eso el undo es instantáneo (vuelve a escalar el RS anterior).
  • rollout status se queda esperando hasta que las réplicas nuevas estén Ready, o hasta timeout. Si un Pod nuevo no pasa readiness, el rolling se frena y los viejos siguen sirviendo — es el comportamiento que querés.
  • kubectl rollout restart deployment/web recicla Pods sin cambiar la imagen. Sirve para tomar un ConfigMap nuevo o para “apagar y prender” después de un secret rotado.
ℹ️ El historial tiene un límite (revisionHistoryLimit, default 10). Si hacés undo y “no hay revisión”, es que los ReplicaSets viejos ya se garbage-collectearon. No es un backup de la app: es solo el historial de templates del Deployment.
En VMs sería: idéntico. kubectl set image / rollout son API de Kubernetes, no de Azure. Lo que AKS suma es az aks upgrade (versión del cluster y de los nodos), que es otro plano: no actualiza tu app.

Networking interno y Endpoints El Service no es magia
TipoAlcanceCómo se exponeUso típico
ClusterIP default Solo dentro del cluster IP virtual interna + DNS. Nada en internet. Front → API → DB. Siempre el punto de partida. Si no hace falta entrar de afuera, quedate acá.
NodePort Cada nodo abre un puerto alto (30000–32767) <IP-de-cualquier-nodo>:<nodePort> Labs, o clusters sin cloud load balancer. En AKS casi no se usa: sale más limpio un LoadBalancer. En VMs on-prem es común (o MetalLB).
LoadBalancer Internet (o red interna, con annotation) El cloud-controller de AKS crea un Azure Load Balancer y una Public IP. El campo EXTERNAL-IP tarda 1–2 min en dejar de ser <pending>. Una app, un LB, una IP. Simple. Caro e inmanejable cuando hay muchas apps (una IP pública por Service).
Ingress no es un type de Service HTTP/S desde afuera, con ruteo por host/path Un Ingress Controller (él sí suele ser un Service LoadBalancer) lee objetos Ingress y rutea L7. Varias apps, un solo IP/FQDN, TLS, path /api vs /app. Es el patrón de producción.
Ingress no es un cuarto type de Service. El type es ClusterIP / NodePort / LoadBalancer. Ingress es otro objeto que necesita un controller corriendo en el cluster. Sin controller, el manifiesto Ingress se aplica y no hace nada. En AKS el controller no viene instalado de default (salvo que habilites el add-on de application routing o AGIC).
Endpoints / EndpointSlice — por qué el Service “no rutea”

Un Service no manda tráfico a “el Deployment”. Manda tráfico a un objeto Endpoints (y su versión moderna, EndpointSlice) que lista IPs de Pods Ready cuyo label matchea el selector. Si el selector no matchea, ese objeto existe pero está vacío.

kubectl get svc web
kubectl get endpoints web
kubectl get endpointslices -l kubernetes.io/service-name=web
kubectl describe svc web
# mirá las líneas Selector y Endpoints
# Endpoints: <none>  →  el selector no pega con ningún Pod Ready
  • Causas clásicas de Endpoints: <none>: typo en el label (app: web vs app: nginx), el Pod está en otro namespace, el Pod no está Ready (readiness probe fallando: el Pod existe, no entra al pool), o el Service es type: ExternalName / sin selector (caso especial).
  • El Deployment puede estar 2/2 Running y el Service igual muerto. Son objetos desacoplados. Siempre cruzá kubectl get pods --show-labels con el selector del Service.
⚠️ Diagnóstico de oro: “el LoadBalancer tiene IP pero la app no responde”. No empieces por el NSG. Primero kubectl get endpoints <svc>. Si está vacío, el Azure LB está sano y no tiene a quién mandar el tráfico. Arreglá labels / readiness, no la red de Azure.
DNS interno del cluster

CoreDNS (Pods en kube-system) resuelve nombres de Service:

<nombre-del-service>.<namespace>.svc.cluster.local
# ejemplo: web.default.svc.cluster.local

# atajos que también funcionan:
web                        # desde el mismo namespace
web.default                # desde otro namespace
web.default.svc            # forma intermedia
  • Ese FQDN apunta a la ClusterIP, no a un Pod puntual. kube-proxy (o eBPF en CNIs modernas) hace el NAT a una de las IPs del EndpointSlice.
  • Para probarlo: kubectl run tmp --rm -it --image=busybox --restart=Never -- wget -qO- http://web.default.svc.cluster.local
Ingress Controller: NGINX vs AGIC vs LoadBalancer directo
  • LoadBalancer directo: un Azure LB por app. Cero ruteo HTTP. Lo más simple de entender y lo más caro de operar cuando hay 10 APIs.
  • NGINX Ingress Controller: un Deployment + un Service LoadBalancer. Los objetos Ingress los interpreta NGINX. Es el mismo controller que pondrías en Kubernetes sobre VMs. Portable. En AKS se instala con Helm o un manifiesto; el add-on “application routing” es una variante gestionada.
  • AGIC (Application Gateway Ingress Controller): el Ingress no termina en un Pod de NGINX, termina en Application Gateway (L7 de Azure, WAF opcional). El controller traduce objetos Ingress a config de App Gateway. Más “Azure”, menos portable a VMs. Útil si ya exigís WAF / App Gateway en el diseño de red.
Pregunta de diseñoRespuesta
Una sola app, lab, quiero una IP yaService type: LoadBalancer
Varias apps HTTP, un FQDN, paths / hostsIngress + controller (NGINX si querés portable; AGIC si el estándar de la empresa es App Gateway)
Tráfico no HTTP (Redis, MQTT, gRPC crudo sin L7)LoadBalancer (o Ingress TCP si el controller lo soporta). Ingress HTTP no aplica.
Solo habla API↔API dentro del clusterClusterIP. No gastes una Public IP.
En VMs sería: ClusterIP y DNS interno no cambian. NodePort es más común. LoadBalancer no existe a menos que instales un cloud-controller o MetalLB (IPs de un pool on-prem). Ingress NGINX es el mismo chart. AGIC no existe fuera de Azure: en VMs el equivalente de “WAF adelante” es un reverse proxy / appliance delante del NodePort o de MetalLB.

Comandos de diagnóstico básico Orden de ataque
1. Qué hay y en qué estado
kubectl get pods -o wide
kubectl get svc,endpoints
kubectl get deploy,rs
kubectl get ingress
kubectl get pods -A --field-selector=status.phase!=Running
  • CrashLoopBackOff / Error: el contenedor arranca y se muere → logs.
  • ImagePullBackOff: no baja la imagen → ACR / AcrPull / tag mal escrito. En AKS, az aks update --attach-acr.
  • Pending: el scheduler no encontró nodo (CPU/memoria, taint, o falta de IPs en Azure CNI).
  • Service con EXTERNAL-IP <pending> eterno: cuota de Public IP, o el identity del cluster no puede crear el LB en el RG MC_*.
2. kubectl describe — eventos, no adivinanzas
kubectl describe pod web-7d9c8-xk2f
kubectl describe svc web
kubectl describe ingress web

Al final de describe está Events: FailedScheduling, FailedMount, Pulling/Failed, Unhealthy. Es la fuente #1. get te dice el síntoma; describe te dice el evento.

3. kubectl logs y exec
kubectl logs deploy/web
kubectl logs -f pod/web-7d9c8-xk2f
kubectl logs pod/web-7d9c8-xk2f --previous   # el contenedor que crasheó recién

# entrar al Pod
kubectl exec -it deploy/web -- sh

# probar conectividad a otro Service desde adentro (el test que importa)
kubectl exec -it deploy/web -- wget -qO- http://api.default.svc.cluster.local:8080/health
  • Si desde tu laptop no llega pero desde un Pod sí: el problema es exposición (Service type / Ingress / NSG), no la app.
  • Si desde un Pod tampoco llega: el problema es selector/endpoints, DNS, o la app no escucha en targetPort.
  • Un Pod con distroless no tiene sh ni wget: levantá un Pod debug (busybox / nicolaka/netshoot) en el mismo namespace.
Orden que evita vueltas: get pods (está Running?) → describe (eventos) → logs (la app) → get endpoints (el Service apunta a alguien?) → exec + wget al DNS interno (red de cluster) → recién ahí mirar Azure (LB, NSG, Public IP).
En VMs sería: los mismos cuatro comandos. Lo que cambia después: en vez de “el identity no puede crear el Azure LB”, vas a mirar kube-proxy, iptables/ipvs, MetalLB speaker, o el firewall de la VM. El corte “¿funciona dentro del cluster?” se hace igual, con exec.

Mapa AKS ↔ Kubernetes en VMs Misma API, otro dueño

Cuando te pidan “esto mismo, pero no en AKS”, no reescribís la app. Reubicás el plano de control y los plugins de cloud.

En AKSEn Kubernetes sobre VMs (kubeadm / k3s)
Control plane gestionado (no lo ves, no hay SSH)VMs de control plane: kube-apiserver, etcd, scheduler, controller-manager. Las operás vos (HA, backups de etcd, certificados).
System / user node pools (VMSS)Worker VMs. kubelet + container runtime (containerd). El “system pool” no existe: vos decidís taints para los daemons.
RG MC_* (NICs, discos, NSG, LB)Los mismos recursos, creados a mano o por tu cloud-controller. O VMs on-prem, sin RG.
az aks get-credentialsCopiar /etc/kubernetes/admin.conf (o un kubeconfig de un usuario).
--attach-acr / AcrPull en la kubelet identityimagePullSecret, o config de containerd / cri-o contra el registry. ACR sigue pudiendo ser el registry: la auth es tuya.
Service LoadBalancer → Azure LB + Public IPMetalLB, kube-vip, o un LB externo (HAProxy, F5) delante de NodePorts. Sin cloud-controller, el Service queda <pending> para siempre.
NGINX Ingress ControllerEl mismo. Portable 1:1.
AGIC → Application GatewayNo aplica. App Gateway es Azure. En VMs: NGINX / Traefik / HAProxy + WAF si hace falta.
Azure CNI (pod = IP de la VNet) vs kubenetCalico, Cilium, Flannel. “Pod con IP de la LAN” es Calico/Cilium en modo BGP o routed; el análogo de kubenet es un overlay (VXLAN) con NAT de salida.
az aks upgrade / node-image-onlykubeadm upgrade + patch del SO de las VMs, drain por nodo. Misma idea (control plane primero, workers después, nunca workers > control plane).
Cluster Autoscaler (suma VMs del VMSS)Cluster Autoscaler contra tu cloud, o no hay: agrandás el worker pool a mano. HPA (réplicas) es igual en los dos.
Workload Identity / EntraService account de Kubernetes + kubeconfig, o un issuer OIDC que armes vos (SPIFFE, Keycloak). No hay managed identity mágica.
💡 Frase para la conversación: “El YAML se lleva. El cloud-controller no.” Deployments, Services ClusterIP, Ingress NGINX, ConfigMaps y el flujo de rollout son portables. LoadBalancer de Azure, AGIC, --attach-acr y node pools son el wrapping de AKS.

Ruta de práctica hands-on Suscripción sponsored
⚠️ Costo: el control plane Free no se cobra; el nodo sí (VM + disco + LB + Public IP). Este lab usa 1 nodo chico, kubenet (menos IPs) y se borra al final. No lo dejes prendido el fin de semana. Si el tamaño de VM no tiene cuota, probá Standard_D2s_v3 o Standard_B2s en otra región.
Paso 0 — Prerrequisitos
az login
az account show                           # confirmá que es la sponsored
az account set --subscription "<id>"     # si tenés más de una

# kubectl y la CLI de Azure, en local
az aks install-cli                        # si todavía no tenés kubectl
Paso 1 — Cluster chico
az group create -n rg-aks-lab -l eastus

az aks create -g rg-aks-lab -n aks-lab \
  --node-count 1 \
  --node-vm-size Standard_B2s \
  --network-plugin kubenet \
  --tier free \
  --generate-ssh-keys

az aks get-credentials -g rg-aks-lab -n aks-lab --overwrite-existing
kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide

Esperá a que el nodo esté Ready. La creación tarda 5–10 min. Si B2s no está disponible, cambialo antes de seguir: recrear el cluster es más barato que pelear con el SKU.

Paso 2 — Deploy de nginx (todavía sin exponer afuera)
kubectl create deployment web --image=nginx:1.27 --replicas=2
kubectl get deploy,rs,pods --show-labels
kubectl describe deploy web          # mirá el selector y el RS

Deberías ver un ReplicaSet y dos Pods Running. No crees Pods sueltos. Si querés el YAML que Kubernetes infirió: kubectl get deploy web -o yaml.

Paso 3 — Exponer como ClusterIP y probar desde adentro
kubectl expose deployment web --port=80 --target-port=80 --name=web --type=ClusterIP
kubectl get svc web
kubectl get endpoints web            # dos IPs, una por Pod Ready

# DNS interno + HTTP desde un Pod throwaway
kubectl run curl --rm -it --image=curlimages/curl --restart=Never -- \
  curl -sS http://web.default.svc.cluster.local | head

Si el HTML de nginx aparece, el Service y el DNS funcionan. Todavía no hay nada publicado a internet, y está bien.

Paso 4 — Subir a LoadBalancer
kubectl patch svc web -p '{"spec":{"type":"LoadBalancer"}}'
kubectl get svc web -w
# esperá a que EXTERNAL-IP deje de ser <pending>

curl -sS http://<EXTERNAL-IP> | head

Eso crea un Azure Load Balancer + Public IP en el RG MC_rg-aks-lab_aks-lab_eastus. Es el wrapping de AKS: en VMs este paso no existiría. Cuando termines el paso 5, volvé el Service a ClusterIP o borralo para no dejar la IP pública cobrando.

Paso 5 — Ingress con dos apps (una sola IP, dos paths)

Instalá el Ingress Controller NGINX (el portable; el mismo que usarías en VMs). Después dos Deployments y un Ingress.

helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm repo update
helm install ingress-nginx ingress-nginx/ingress-nginx \
  --namespace ingress-nginx --create-namespace
# si no tenés helm:
# kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.11.3/deploy/static/provider/cloud/deploy.yaml

kubectl -n ingress-nginx get svc -w
# anotás la EXTERNAL-IP del Service ingress-nginx-controller → es TU IP de entrada

kubectl create deployment app1 --image=nginx:1.27
kubectl create deployment app2 --image=httpd:2.4
kubectl expose deployment app1 --port=80
kubectl expose deployment app2 --port=80
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: dos-apps
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /app1
        pathType: Prefix
        backend:
          service:
            name: app1
            port:
              number: 80
      - path: /app2
        pathType: Prefix
        backend:
          service:
            name: app2
            port:
              number: 80
EOF

kubectl get ingress dos-apps
curl -sS http://<IP-DEL-INGRESS>/app1 | head
curl -sS http://<IP-DEL-INGRESS>/app2 | head

app1 (nginx) y app2 (httpd) deberían responder distinto en la misma IP. Eso es L7. El Service web del paso 4 ya no hace falta: kubectl delete svc web para soltar esa Public IP extra.

Paso 6 — Romper el selector a propósito

Este es el ejercicio que más enseña. Vas a dejar la app “Running” y el Service muerto, y diagnosticarlo como en producción.

kubectl get svc app1 -o yaml | grep -A2 selector
kubectl get pods -l app=app1 --show-labels
kubectl get endpoints app1
# anotá: hay IPs

# rompés el selector (ya no matchea las labels de los Pods)
kubectl patch svc app1 -p '{"spec":{"selector":{"app":"no-existo"}}}'

kubectl get endpoints app1
# Endpoints vacíos / <none>
kubectl describe svc app1
# Selector: app=no-existo
# Endpoints: <none>
kubectl get pods -l app=app1
# los Pods siguen Running. El Deployment no se enteró de nada.

curl -sS -m 5 http://<IP-DEL-INGRESS>/app1
# timeout o 502/503 — el Ingress llega a un Service sin backends

# arreglo
kubectl patch svc app1 -p '{"spec":{"selector":{"app":"app1"}}}'
kubectl get endpoints app1
curl -sS http://<IP-DEL-INGRESS>/app1 | head

La lección: Service sano ≠ Pods sanos ≠ Endpoints poblados. El objeto que une a los dos es el selector, y se inspecciona con get endpoints.

Paso 7 — Bonus de rollout (si te queda tiempo)
kubectl set image deployment/app1 nginx=nginx:1.27.1
kubectl rollout status deployment/app1
kubectl rollout history deployment/app1
kubectl rollout undo deployment/app1
Paso 8 — Apagar todo (no es opcional)
az group delete -n rg-aks-lab --yes --no-wait

Borra el cluster, el RG MC_*, los LB y las Public IPs. Confirmá en el portal que no quedó un LB huérfano cobrando. En una sponsored, un cluster de 1 nodo olvidado se come el crédito en silencio.

💡 Si el objetivo es practicar YAML y no pagar nodos, Kind o minikube en tu máquina cubren los pasos 2, 3, 5 (sin LoadBalancer cloud) y 6. El paso 4 es lo único que es “AKS de verdad”. Para el mapa a VMs, Kind es más honesto que AKS: no hay cloud-controller regalado.
