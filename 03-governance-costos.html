Reglas duras de la jerarquía
  • El Root Management Group se crea solo, su ID es el tenant ID de Entra ID. No se puede borrar ni renombrar el ID; el display name sí se cambia.
  • Profundidad: hasta 6 niveles de management groups sin contar el root MG ni el nivel de subscription.
  • Hasta 10.000 management groups por directorio (tenant).
  • Un MG o una subscription tiene exactamente un padre. Un MG puede tener muchos hijos (MGs y/o subscriptions).
  • Una subscription pertenece a un solo tenant de Entra ID. Se puede transferir a otro tenant, pero no estar en dos a la vez.
  • Todas las subscriptions nuevas del directorio caen por defecto bajo el root MG.
  • Las asignaciones de RBAC y de Policy hechas en un MG se heredan hacia abajo a todos los MGs, subscriptions, RGs y recursos descendientes.
Hierarchy protection: quién puede crear MGs

Por defecto cualquier usuario del tenant puede crear management groups. Hierarchy protection (o “require authorization”) lo apaga: hace falta Microsoft.Management/managementGroups/write en el root.

az account management-group hierarchy-settings create \
  --name <tenantId> --require-authorization-for-group-creation true
# PS: New-AzManagementGroupHierarchySetting -RequireAuthorizationForGroupCreation

Resource Groups y mover recursos Ciclo de vida
Lo que hay que tener grabado
  • Un recurso vive en exactamente un resource group a la vez. No hay recursos "sueltos" ni compartidos entre RGs.
  • El RG tiene su propia región porque almacena la metadata del grupo. Esa región puede ser distinta de la de los recursos que contiene: podés tener un RG en West Europe con VMs en East US.
  • Si la región del RG está caída, la metadata puede quedar no disponible aunque los recursos sigan funcionando — por eso conviene alinear la región del RG con la de la carga.
  • Borrar el RG borra todo lo que hay adentro, en el orden que ARM decida. Es la forma canónica de limpiar un entorno de prueba.
  • El RG no limita la región de los recursos: dentro de un mismo RG puede haber recursos de varias regiones.
  • Los recursos pueden interactuar entre RGs distintos sin problema (una VM en RG-A usando una VNet en RG-B).
Mover recursos entre RG o entre subscriptions
# mover a otro resource group (misma subscription)
az resource move --destination-group RG-Destino \
  --ids /subscriptions/<subId>/resourceGroups/RG-Origen/providers/Microsoft.Compute/virtualMachines/VM1

# mover a otra subscription
az resource move --destination-group RG-Destino \
  --destination-subscription-id <subIdDestino> --ids <resourceId>
  • Mover no cambia la región del recurso. Mover ≠ migrar de región (para eso, Azure Resource Mover o redeploy).
  • El resource ID cambia: el ID incluye /subscriptions/{id}/resourceGroups/{nombre}/..., así que al mover se rompe todo lo que apunte al ID viejo (scripts, RBAC asignado directo al recurso, alertas, templates).
  • Durante la operación, el RG de origen y el de destino quedan bloqueados: no se pueden agregar, borrar ni actualizar recursos en ninguno de los dos hasta que termine.
  • Origen y destino deben tener registrados los resource providers involucrados.
  • Para mover entre subscriptions, ambas deben estar en el mismo tenant de Entra ID.
  • Necesitás permisos de escritura/borrado sobre el origen y de escritura sobre el destino.

Resource Locks: CanNotDelete vs ReadOnly Protección
Tipo de lockPortalImpidePermiteEquivale a
CanNotDeleteDeleteBorrar el recursoLeer y modificarRol Contributor sin delete
ReadOnlyRead-onlyBorrar y modificarSolo lecturaRol Reader
Cómo se comportan
  • Se pueden aplicar en subscription, resource group o recurso individual. No existen locks a nivel management group.
  • Se heredan hacia abajo: un lock en el RG protege a todos los recursos de adentro.
  • Si hay varios locks en la cadena, gana el más restrictivo (ReadOnly le gana a CanNotDelete).
  • Aplican a todos los usuarios y roles, incluido el Owner y el Global Administrator. No es RBAC: no distingue identidades, es una barrera sobre el control plane.
  • Para crear o borrar un lock necesitás la acción Microsoft.Authorization/locks/* → la traen los roles Owner y User Access Administrator. Contributor no puede.
  • Solo afectan el control plane (operaciones ARM), no el data plane: un CanNotDelete en una Storage Account no impide borrar blobs adentro, ni un lock en una SQL DB impide un DROP TABLE.
  • Un lock CanNotDelete dentro de un RG impide borrar el RG entero, aunque el lock esté en un solo recurso.
⚠️ Trampa del examen: un lock ReadOnly sobre una Storage Account bloquea "List Keys". Parece una lectura, pero listKeys es una operación POST y ARM la clasifica como escritura → falla. Mismo patrón: Storage Explorer (“Unable to list resources… list containers or list account keys”). CanNotDelete no bloquea listKeys.

Tags: metadata para costos y organización Cost reporting
Mecánica y límites
  • Son pares nombre/valor aplicables a subscriptions, resource groups y recursos.
  • Límite: 50 tags por recurso / RG / subscription.
  • Nombre de tag: hasta 512 caracteres. Valor: hasta 256 caracteres. (En Storage Accounts el nombre se limita a 128.)
  • Los nombres de tag son case-insensitive para las operaciones; los valores son case-sensitive.
  • Algunos tipos de recurso no soportan tags (por ejemplo los recursos del modelo classic). Si el recurso no soporta tags, no aparece desglosado por tag en cost reporting.
  • Son la base del cost reporting: en Cost Analysis podés agrupar/filtrar por tag para imputar gasto a un centro de costo, proyecto o entorno.
  • Un Contributor puede editar tags de un recurso; el rol específico Tag Contributor permite gestionar tags sin poder tocar el recurso en sí (pero desde el portal no puede aplicar tags a recursos ni a resource groups — solo a subscriptions; para recursos y RGs tiene que usar PowerShell, CLI o la REST API).
Aplicar y propagar
# CLI: agrega/actualiza sin borrar los existentes
az tag update --resource-id <resourceId> --operation Merge --tags CostCenter=1001 Env=Prod

# ojo: --operation Replace pisa TODOS los tags existentes
  • En PowerShell, Update-AzTag -Operation Merge agrega; Set-AzResource -Tag reemplaza el set completo.
  • Para heredar de verdad hay que usar Azure Policy: la definición built-in "Inherit a tag from the resource group" usa effect Modify y una remediation task para aplicarlo a lo existente.
  • Append agrega el tag al momento de crear/actualizar; Modify puede agregar, reemplazar o borrar tags y sí sirve para remediar recursos existentes.
⚠️ Trampa del examen: los tags NO se heredan. Un tag puesto en la subscription o en el resource group no aparece automáticamente en los recursos hijos. Si la pregunta es "cómo garantizo que todos los recursos tengan el tag CostCenter del RG", la respuesta es Azure Policy con effect Modify + remediation task — nunca "poner el tag en el RG y listo".

Datos operativos que caen en el examen
  • Los scopes de asignación son management group, subscription o resource group. Se pueden definir exclusiones de sub-scopes dentro de la asignación.
  • Policy no es retroactivo: Deny no borra ni apaga lo que ya existía, solo bloquea cambios y creaciones nuevas. Lo viejo aparece como non-compliant.
  • Después de crear o cambiar una asignación, los resultados de compliance de los recursos existentes tardan hasta ~30 minutos en aparecer.
  • El ciclo de evaluación estándar corre aproximadamente cada 24 horas; se puede forzar un scan on-demand.
  • Para Modify y DeployIfNotExists, la asignación necesita una managed identity con el rol adecuado (típicamente Contributor) sobre el scope, y hay que lanzar una remediation task para corregir lo ya desplegado.
  • Las Initiatives (policy sets) permiten asignar decenas de definiciones de una y reportar compliance agrupado. Azure Blueprints era el paquete de nivel superior — hoy en camino de reemplazo por Deployment Stacks / Template Specs.
  • Definition scope = dónde vive y es visible. Assignment scope = dónde se aplica. Una definition guardada en una subscription no se puede asignar a un management group: para más alcance, guardala en el MG.
  • Las definitions built-in y static no se editan (son de Microsoft). Cambiar el JSON de una custom no actualiza sola los assignments: hay que editarlos o reasignar.
  • mode: Indexed evalúa solo recursos que soportan tags y location.

Cost Management, Budgets y Advisor Costos
Cost Analysis
  • Vista de gasto acumulado y proyectado, con agrupación y filtro por subscription, resource group, resource type, location, service name y tag.
  • Se puede exportar de forma programada a una Storage Account (diario / semanal / mensual) para análisis externo.
  • Los datos de costo pueden tardar en consolidarse; no es facturación en tiempo real.
Budgets
  • Scope: management group, subscription o resource group (también scopes de facturación en EA/MCA).
  • Período de reset: mensual, trimestral o anual, con fecha de expiración.
  • Umbrales de alerta: se definen como % del monto del budget, y pueden dispararse sobre el costo actual o el forecast (previsto). Hasta 5 condiciones de alerta por budget.
  • Las alertas notifican por email y/o vía Action Group — lo que habilita automatizar (webhook, Logic App, Automation runbook, Azure Function) para, por ejemplo, apagar VMs.
  • El Action Group usado por un budget debe estar configurado con el esquema común de alertas para recibir el payload correctamente.

Modelos de ahorro: cuál pide cada escenario Optimización
ModeloCompromisoRequisitoPalabra clave en el enunciado
Reserved Instances 1 o 3 años de capacidad reservada Carga estable y predecible que corre 24/7, atada a familia/región/tamaño "workload constante", "no va a cambiar de tamaño", "24/7"
Azure Savings Plans 1 o 3 años de gasto horario (USD/hora) Cómputo elegible que cambia de familia, región o servicio "compromiso de gasto", "flexibilidad entre tamaños/regiones"
Azure Hybrid Benefit Ninguno temporal Licencias de Windows Server o SQL Server con Software Assurance (o suscripciones RHEL/SUSE) "ya tenemos licencias on-premises", "Software Assurance"
Spot VMs Ninguno — desalojables La carga tolera interrupción y reinicio "batch", "render", "puede interrumpirse", "sin SLA"
Dev/Test pricing Ninguno Subscription Enterprise Dev/Test o Pay-As-You-Go Dev/Test; solo cargas de no producción "entorno de desarrollo/QA", "no productivo"
Detalles finos
  • Reservations: se compran por 1 o 3 años, con pago upfront o mensual (el mensual no cuesta más). Aplican a VMs, SQL DB, Cosmos DB, Storage reservado, etc. Se pueden intercambiar o cancelar (con condiciones), y el scope es shared (toda la billing account), single subscription o single resource group.
  • La reserva cubre el costo de cómputo, no la licencia de Windows: por eso RI + Azure Hybrid Benefit se combinan y es la respuesta cuando el escenario pide máximo ahorro con licencias propias.
  • Savings Plans: compromiso de $/hora por 1 o 3 años, flexible entre familias, regiones y servicios de cómputo elegibles. Menos descuento que una RI atada, más flexibilidad. Si el enunciado dice "la carga cambia de tamaño/región pero podemos comprometernos", es Savings Plan, no RI.
  • Spot VMs: Azure las desaloja cuando necesita la capacidad o cuando el precio supera tu máximo. Política de desalojo: Deallocate (se conserva el disco, podés reiniciarla) o Delete. No tienen SLA, no soportan Availability Sets ni la serie B; sí pueden ir a Availability Zones.
  • Auto-shutdown de VMs y el right-sizing que sugiere Advisor son las respuestas "baratas" cuando el escenario dice "sin compromiso a largo plazo y sin cambiar de suscripción".
  • Frenar una VM desde el SO no corta la facturación de cómputo: hay que deallocate (Stop desde el portal/CLI). El disco se sigue pagando igual.
⚠️ Trampa del examen: si el escenario dice "la carga es crítica y no puede interrumpirse", Spot queda descartado sí o sí aunque sea la opción más barata. Si dice "sin comprometerse por adelantado", quedan fuera RI y Savings Plan. Si dice "la carga varía de tamaño/región pero hay compromiso de gasto", la respuesta es Savings Plan, no Reserved Instances.

Azure Resource Manager y resource providers Control plane
ARM es la única puerta
  • Todo pasa por ARM: portal, Azure CLI, Azure PowerShell, SDKs y la REST API terminan hablando con el mismo endpoint. Por eso el resultado es idéntico sin importar la herramienta.
  • ARM aplica de forma consistente RBAC, Policy, locks y tags, y maneja el orden de dependencias en los despliegues.
  • Un despliegue de template puede ser Incremental (default: agrega/actualiza y deja intacto lo que no está en el template) o Complete (borra del RG lo que no esté declarado en el template).
Resource providers
  • Un resource provider es el servicio que aporta los tipos de recurso: Microsoft.Compute (VMs), Microsoft.Network, Microsoft.Storage, Microsoft.Web, Microsoft.KeyVault, Microsoft.OperationalInsights (Log Analytics workspace), Microsoft.App (Container Apps). Tabla completa en 11 · ARM.
  • Se registran por subscription. Hasta que un provider no está Registered, no se pueden crear recursos de sus tipos en esa subscription.
  • Muchos se registran automáticamente al crear el primer recurso desde el portal, pero desde CLI/PowerShell o al mover recursos a otra subscription puede hacer falta registrarlo a mano.
  • El resource ID completo tiene esta forma: /subscriptions/{subId}/resourceGroups/{rg}/providers/{namespace}/{tipo}/{nombre}.
az provider list --query "[?registrationState=='Registered'].namespace" -o table
az provider register --namespace Microsoft.Compute
az provider show --namespace Microsoft.Compute --query registrationState
⚠️ Trampa del examen: si el escenario dice que la creación de un tipo de recurso falla en una subscription nueva pero funciona en otra, la causa más probable es que el resource provider no está registrado en esa subscription — no un problema de RBAC ni de cuota. Y ojo con el otro clásico: un despliegue en modo Complete borra los recursos del RG que no figuran en el template.
