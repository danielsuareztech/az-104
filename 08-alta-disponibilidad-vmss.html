Qué se pregunta acá: el examen te tira un escenario y te pide el SLA más alto, o protección contra la caída de un datacenter entero, o actualizar 50 instancias sin downtime. Casi siempre la respuesta se decide en tres bifurcaciones: Availability Set vs Availability Zone (rack vs datacenter), Uniform vs Flexible (idénticas vs mezcladas), y Manual / Automatic / Rolling (control vs velocidad vs cero downtime). Cambio de OS/Data disk Profile a instancias existentes: Set-AzVmssVM (Rolling no lo aplica; Update-AzVmssInstance tampoco). Drop-down de AS: planned maintenance = UD (8 VMs en grupos de 2 → 4 UD), separación física = FD al máximo (3), Aligned. Escalera de SLA: 99,99 / 99,95 / 99,9 / 99,5 / 95.

  • Geography: agrupación discreta que define el límite de residencia de datos y de cumplimiento. Es el concepto que aparece cuando la pregunta habla de "los datos no pueden salir del país / de la UE".
  • Region: conjunto de datacenters desplegados dentro de un perímetro con red de baja latencia. Es la unidad que elegís al crear cualquier recurso.
  • Availability Zone: una o más instalaciones físicamente separadas dentro de la región, con energía, refrigeración y red independientes. Las regiones habilitadas tienen un mínimo de 3 zonas.
  • Datacenter / rack: el nivel más bajo. Los fault domains de un Availability Set viven acá.
Region pairs
  • Cada región está emparejada con otra dentro de la misma geography. La excepción clásica es Brazil South ↔ South Central US (el par sale de Brasil).
  • Separación física de al menos 300 millas (≈480 km) donde sea posible, para que un desastre regional no toque a las dos. No es 300 km.
  • Las actualizaciones de plataforma son escalonadas: Azure nunca actualiza las dos regiones de un par al mismo tiempo.
  • En una interrupción amplia, Azure prioriza la recuperación de al menos una región de cada par.
  • Es el fundamento de GRS / RA-GRS en Storage: la copia secundaria va a la región emparejada y no la elegís vos.

Availability Sets: fault domains y update domains Dentro de un datacenter
Los dos ejes
  • Fault Domain (FD) = grupo de racks que comparten fuente de energía y switch de red. Protege contra fallas no planificadas de hardware. Las VMs del AS se reparten entre FDs para que un rack caído no se lleve todas.
  • Update Domain (UD) = grupo lógico que Azure reinicia junto durante mantenimiento planificado. Azure actualiza un UD a la vez y espera antes de pasar al siguiente, así nunca se reinician todas tus VMs simultáneamente.
  • Las VMs se asignan a FD y UD de forma round-robin a medida que las vas creando dentro del set. Si configurás más FDs que VMs, los FDs de más quedan vacíos (no se “rellenan” solos).
  • El Availability Set vive en un solo datacenter (una zona). No cruza AZs: por eso no te salva si se cae el edificio.
  • Los discos administrados también se alinean con el fault domain de la VM cuando el AS es "aligned" (lo estándar hoy).

Drop-down: 8 VMs, 6 arriba en mantenimiento, máxima separación física

Traducción del enunciado: “planned maintenance / restart in groups of two / at least six available” = Update domains. “Physically separated as much as possible” = Fault domains al máximo. Azure reinicia un UD por vez.

az vm availability-set create -g RG -n AS1 --location centralus \
  --platform-fault-domain-count 3 --platform-update-domain-count 4

New-AzAvailabilitySet -ResourceGroupName RG -Name AS1 -Location centralus `

⚠️ Trampa del examen: “planned maintenance” es Update Domain, no Fault Domain. “Physical separation” es Fault Domain (máx. 3). No dejes los defaults (2 FD / 5 UD): 5 UD no da grupos de 2 exactos. Aligned / managed disks = Yes. Esto no sube el SLA: sigue 99,95 %.
Regla de oro: un Availability Set reparte VMs entre fault domains (racks) y update domains. Te cubre falla de rack y mantenimiento planificado, pero no te protege si se cae el datacenter o la zona entera. Para eso necesitás Availability Zones. Maxear a 3 FD y 3 UD no cambia el SLA: sigue siendo 99,95 %.
Restricciones que el examen ama
  • La VM tiene que crearse dentro del Availability Set. No podés agregar una VM ya existente a un AS: hay que borrarla (conservando los discos) y recrearla dentro del set, o recrearla desde una imagen/snapshot.
  • Tampoco podés sacar una VM de un AS ni moverla a otro AS sin recrearla.
  • El Availability Set es un recurso por región y no se puede mover a otra región.
  • Todas las VMs de un AS deberían estar en el mismo resource group y misma región que el AS.
  • Una VM no puede estar en un Availability Set y en una Availability Zone al mismo tiempo: son mutuamente excluyentes.
  • Buena práctica: cada capa de la aplicación (web, app, datos) en su propio Availability Set.
⚠️ Trampa del examen: el escenario dice "ya tenés dos VMs corriendo en producción y querés SLA del 99,95%: ¿qué hacés?". La respuesta no es "agregarlas a un Availability Set" — eso es imposible sobre VMs existentes. La opción correcta implica recrear las VMs dentro del set (o directamente redesplegarlas en Availability Zones). La gemela Yes/No: Availability Set (aunque sea 3 FD + 3 UD) + Basic LB = No si piden datacenters separados o el SLA más alto.

Availability Zones: zonal vs zone-redundant Dentro de la región
Qué son
  • Ubicaciones físicamente separadas dentro de una misma región. Cada zona son uno o más datacenters con energía, refrigeración y red independientes. En el examen, “datacenters separados en la misma región” = Availability Zones.
  • Las regiones habilitadas tienen al menos 3 zonas, conectadas por fibra dedicada de alto ancho de banda con latencia inferior a 2 ms entre zonas.
  • Los números de zona (1, 2, 3) están mapeados lógicamente por suscripción: la "zona 1" tuya no es necesariamente la misma instalación física que la "zona 1" de otra suscripción.
  • Al desplegar VMs en zonas distintas de una misma región, tenés protección contra la caída de un datacenter completo — algo que un Availability Set no puede darte.
ModeloCómo funcionaEjemplos típicos
Zonal
(fijado a una zona)		 Vos elegís la zona. El recurso vive en esa zona; si la zona cae, el recurso cae. La redundancia la construís vos desplegando instancias en varias zonas. VM, managed disk, Public IP Standard zonal, NIC de una VM zonal
Zone-redundant
(replicado solo)		 Azure replica y distribuye el recurso automáticamente entre zonas. Sobrevive a la pérdida de una zona sin que vos hagas nada. Standard Load Balancer, ZRS en Storage, Application Gateway v2, Public IP Standard zone-redundant, VPN/ExpressRoute Gateway zone-redundant
Non-zonal / regional Sin garantía de ubicación zonal: Azure lo coloca donde quiere dentro de la región. VM sin zona seleccionada, Public IP Basic, LRS
⚠️ Trampa del examen: no podés cambiar la zona de una VM ya creada. No hay botón de "mover a zona 2". El procedimiento correcto es: snapshot de los discos → crear discos administrados en la zona destino → crear la VM nueva ahí (o usar Azure Site Recovery para migrar entre zonas). Cualquier opción que diga "cambiar la zona en Configuration" es distractor.
⚠️ Trampa del examen: ojo con el SKU de la Public IP y del Load Balancer. Las zonas requieren SKU Standard. Una Public IP Basic no puede ser zonal ni zone-redundant, y no se puede asociar a un Standard Load Balancer. Si el escenario menciona zonas y una opción usa recursos Basic, esa opción está mal.
✅ Regla mental de lectura rápida: si la pregunta dice "rack" o "mantenimiento planificado" → Availability Set. Si dice "datacenter", "edificio", "inundación", "corte de energía en una instalación" → Availability Zones. Si dice "región completa" o "desastre regional" → otra región + Azure Site Recovery.

Detalles finos que cambian la respuesta
  • Para el SLA de una sola VM, la condición del tipo de disco aplica a todos los discos: si el disco de OS es Premium pero un disco de datos es Standard HDD, no calificás para 99,9 %.
  • El SLA cubre conectividad a la VM, no que tu aplicación adentro funcione.
  • Las VMs Spot no tienen SLA de disponibilidad: se pueden desalojar en cualquier momento. Si el escenario habla de cargas críticas, Spot está mal.

  • Zone-redundant describe al Load Balancer / Public IP, no a las VMs. Tres VMs con --zone 1 siguen siendo un solo datacenter.
⚠️ Trampa del examen: "tengo dos VMs en dos regiones distintas, ¿qué SLA me da?". El SLA de VMs de 99,99 % es para zonas dentro de una misma región. Un despliegue multi-región es una estrategia de disaster recovery, no una configuración con SLA de VM publicado — y en el examen se resuelve con Traffic Manager / Front Door + Site Recovery, no con la tabla de arriba.

Virtual Machine Scale Sets: Uniform vs Flexible Escalado horizontal
Qué es un VMSS
  • Un grupo de VMs gestionado como una unidad lógica, con capacidad de crecer y decrecer automáticamente según demanda o calendario.
  • Escala horizontalmente (scale-out / scale-in = más o menos instancias), no verticalmente (scale-up = VM más grande).
  • Se despliega detrás de un Load Balancer o Application Gateway, que reparte el tráfico entre las instancias.
  • Puede distribuirse entre Availability Zones y, dentro de cada zona, entre fault domains.
  • El VMSS en sí no tiene costo: pagás las VMs, discos y networking que genera.
AspectoUniformFlexible
ModeloUn modelo de VM compartido: todas las instancias son idénticasVMs individuales agrupadas en el scale set
Mezclar tamaños de VMNo — un solo SKUSí — distintos tamaños y hasta Spot + on-demand juntos
Administración de instanciasComo instancias del scale set (API propia de VMSS)Como VMs normales: aparecen en la lista de Virtual Machines y usan la API estándar de Compute
Orientado aCargas stateless homogéneas de gran escalaCargas mixtas, incluidas stateful y quorum-based
Fault domainsGestionados por la plataformaDefinís explícitamente el fault domain count y las instancias se reparten
EstadoModo legado, todavía soportadoDefault recomendado por Microsoft para despliegues nuevos
Distribución: zonas y fault domains
  • Podés seleccionar una o varias zonas al crear el scale set. Con varias zonas, el VMSS distribuye las instancias entre ellas — esto es lo que te lleva al SLA de 99,99 %.
  • El zone balancing mantiene la diferencia de instancias entre zonas en el mínimo posible. En modo strict, el scale set falla la operación si no puede mantener el balance; en best effort, sigue adelante desbalanceado.
  • Dentro de cada zona, las instancias se reparten entre fault domains para sobrevivir a la caída de un rack.
  • En Flexible elegís el fault domain count (típicamente 1 cuando desplegás entre zonas, porque la separación ya la da la zona).
⚠️ Trampa del examen: el escenario pide "instancias de distintos tamaños en el mismo grupo", "mezclar VMs Spot y regulares" o "administrar cada VM individualmente" → la respuesta es Flexible orchestration. Si en cambio pide "todas las instancias exactamente iguales gestionadas como un conjunto" → Uniform. Y ojo: el orchestration mode se define al crear el scale set y no se puede cambiar después.
💡 Scale-up vs scale-out en el vocabulario del examen: vertical (scale-up) = cambiar el tamaño de la VM, requiere reinicio y tiene techo en el SKU más grande. Horizontal (scale-out) = agregar instancias, es lo que hace el VMSS y es la respuesta cuando piden "sin interrumpir el servicio" o "manejar picos de tráfico".

Autoscale: anatomía de una regla Alta frecuencia
Los tres tipos de escalado
  • Manual: vos fijás el número de instancias y ahí se queda. Útil para entornos de prueba o cuando la carga es predecible y constante.
  • Custom autoscale basado en métricas: reglas que reaccionan a CPU, memoria, cola de mensajes, métrica personalizada. Es la respuesta cuando el escenario dice "según la carga" o "cuando el CPU supere X".
  • Basado en schedule: perfiles con fecha/hora (recurrentes o de fecha específica). Es la respuesta cuando el escenario dice "todos los lunes a las 8", "durante el Black Friday" o "en horario laboral".

Un mismo setting de autoscale puede tener varios profiles: uno default siempre activo, más profiles de schedule que lo pisan en su ventana horaria.

Reglas críticas
  • Hay que definir scale-out Y scale-in. Si solo creás la regla de "aumentar cuando CPU > 70", el scale set crece y nunca vuelve a bajar. Es la falla de diseño que más se pregunta.
  • Los umbrales tienen que dejar margen suficiente entre scale-out y scale-in. Si escalás para arriba en CPU > 50 y para abajo en CPU < 50, entrás en flapping: agregás una instancia, baja el promedio, sacás la instancia, sube el promedio, y así infinitamente. Usá algo como > 70 / < 30.
  • Autoscale estima el impacto de un scale-in antes de ejecutarlo: si al remover instancias la métrica volvería a cruzar el umbral de scale-out, no lo hace.
  • Con varias reglas de scale-out, alcanza con que una se cumpla para escalar hacia arriba; para hacer scale-in, en general se exige que todas las condiciones de scale-in se cumplan.
  • El maximum también está limitado por tu quota de vCPU en la región y por el backend pool del Load Balancer. Un escenario clásico: "el scale set no supera N instancias" → revisá quotas.
⚠️ Trampa del examen: "configuraste una regla de scale-out por CPU y el costo se disparó porque las instancias nunca se reducen". La respuesta correcta es agregar una regla de scale-in, no "bajar el maximum" ni "cambiar a manual". Y si el problema es que el scale set agrega y quita instancias constantemente, la respuesta es separar más los umbrales y/o aumentar el cool down.

Scale-in policy: a quién se lleva puesto Pregunta de detalle
El problema que resuelve

Cuando el autoscale decide reducir, alguien tiene que elegir qué instancia se borra. La scale-in policy es esa decisión, y se configura a nivel del scale set.

PolíticaCómo eligeCuándo la pregunta apunta acá
Default Primero balancea entre Availability Zones, después entre fault domains dentro de la zona más cargada, y recién ahí elimina la instancia. Prioriza mantener la distribución pareja. Cuando el escenario pide mantener la alta disponibilidad y el balance entre zonas mientras se reduce.
NewestVM Elimina la instancia creada más recientemente (respetando primero el balance entre zonas y FDs). Cuando querés conservar las instancias viejas: nodos que ya tienen caché caliente, o instancias que arrancaste primero y están estables.
OldestVM Elimina la instancia creada hace más tiempo (también respetando el balance entre zonas y FDs). Cuando querés rotar y retirar instancias antiguas con imágenes o configuración desactualizada. Típico de cargas stateless con ciclo de vida corto.
💡 Las tres políticas respetan el balance entre zonas y fault domains primero. NewestVM y OldestVM solo definen el criterio de desempate dentro del grupo ya elegido: nunca rompen la distribución para borrar una VM por antigüedad.
✅ Si además necesitás que una instancia específica no se toque durante un scale-in — porque estás depurando algo en ella — el mecanismo es instance protection: podés proteger una instancia from scale-in o proteger su configuración from the scale set model.

Upgrade policy y salud de instancias Escenario clásico
Qué es el "modelo" del scale set

El scale set tiene un modelo (imagen, tamaño, extensiones, configuración). Cuando cambiás el modelo, la upgrade policy define cómo se propaga ese cambio a las instancias que ya están corriendo. Excepción: cambios del OS disk / Data disk Profile no siguen la policy (ni Rolling). Hay que aplicarlos instancia por instancia con Set-AzVmssVM.

Upgrade policyComportamientoDowntimeCuándo elegirla
Manual Las instancias existentes no se actualizan solas. Quedan marcadas como "latest model: No" y vos disparás el upgrade instancia por instancia. El que vos decidas Cuando necesitás control total del momento y del orden. Es el default histórico.
Automatic Azure aplica el cambio a las instancias sin orden garantizado y potencialmente a todas a la vez. No hay pausas ni comprobación de salud. Sí, posible caída total Solo para cargas donde la interrupción no importa (dev/test).
Rolling Actualiza por lotes: define un batch size (porcentaje de instancias por lote), una pausa entre lotes, y umbrales máximos de instancias no saludables. Si la salud se degrada, detiene el rollout. Sin downtime La respuesta cuando el escenario dice "actualizar sin interrumpir el servicio".
⚠️ Trampa del examen: "necesitás desplegar una imagen nueva a 40 instancias sin downtime". La opción Automatic suena bien por el nombre pero es la peor: reinicia sin control ni verificación de salud. La correcta es Rolling upgrade. Y para que Rolling funcione, el scale set necesita un health probe del Load Balancer o la Application Health extension — sin señal de salud, Azure no tiene forma de saber si el lote quedó sano y el rolling upgrade no se puede habilitar.
Elegí un cmdlet: aplicar OS/Data disk Profile a las instancias ya creadas

Upgrade policy = Rolling. Cambiaste el perfil de disco del modelo. Rolling no empuja ese cambio. Hay que tocarlo en cada instancia existente.

az vmss update -g RG -n vmss1

az vmss rolling-upgrade start -g RG -n vmss1
⚠️ Trampa del examen: Rolling en el enunciado es carnada. OS/Data disk Profile no sigue la upgrade policy → Set-AzVmssVM. Update-AzVmssInstance parece “la instancia” y es el distractor de Manual. Start-AzVmssRollingOSUpgrade es parche de imagen de plataforma, no el perfil de disco.
Health probes, Application Health extension y auto-repair
  • Un scale set puede monitorear la salud de sus instancias de dos formas: con un health probe del Load Balancer o con la Application Health extension instalada dentro de cada instancia.
  • La Application Health extension reporta el estado desde adentro de la VM (por ejemplo, consultando un endpoint HTTP local). Es la opción cuando no hay Load Balancer delante o querés una señal a nivel aplicación.
  • Automatic instance repair: si una instancia se reporta unhealthy de forma sostenida, el scale set la elimina y crea una nueva automáticamente. Requiere salud monitoreada (probe o extension) y tiene un grace period para dar tiempo a que la aplicación arranque después del boot.
  • Los automatic OS image upgrades (mantener el OS parcheado con la última imagen del publisher) también exigen monitoreo de salud y se aplican por lotes.
⚠️ Trampa del examen: si las instancias del scale set "se quedan colgadas pero nunca se reemplazan", el problema es que no hay señal de salud configurada o que automatic repairs está deshabilitado. Agregar más instancias, subir el maximum o cambiar la scale-in policy no arregla nada: hace falta Application Health extension o un health probe + automatic instance repair.

⚠️ Trampa del examen: para un scale set distribuido en Availability Zones, tanto el Load Balancer como la Public IP tienen que ser SKU Standard. El SKU Basic no soporta zonas y ya no es una opción válida para diseños nuevos. Además, el SKU del LB y el de la Public IP tienen que coincidir: no podés asociar una Public IP Basic a un Standard Load Balancer.
💡 El Standard Load Balancer es zone-redundant por default en su frontend: no se cae si desaparece una zona. Pero eso no vuelve zone-redundant a tus VMs — la disponibilidad del backend depende de que vos hayas distribuido las instancias entre zonas.
