Tenant, Subscription y Management Groups Fundacional
La relación de confianza
  • El tenant (también llamado directory) es una instancia dedicada de Microsoft Entra ID. Guarda identidades, no recursos. Se identifica por un GUID (Tenant ID) y por al menos un dominio *.onmicrosoft.com.
  • La subscription es el contenedor de facturación de recursos de Azure. Cada subscription confía en exactamente un tenant para autenticar.
  • Relación: 1 tenant → N subscriptions. Nunca al revés: una subscription no puede estar en dos tenants al mismo tiempo.
  • Los Management Groups viven dentro del tenant y agrupan subscriptions para aplicar Azure Policy y RBAC heredados hacia abajo.

Mover una subscription a otro tenant
  • Se hace desde la subscription → Change directory. Necesitás rol Owner sobre la subscription y ser usuario existente en el tenant destino.
  • Los recursos no se mueven ni se borran: siguen en la misma subscription, con las mismas IDs.
  • Lo que sí se pierde: todas las asignaciones de Azure RBAC (hay que rehacerlas), los administradores clásicos, y se rompen las system-assigned managed identities (se deshabilitan y rehabilitan para recrearlas).
  • Los Key Vaults quedan apuntando al tenant viejo: hay que actualizarles el tenant ID y rehacer las access policies.
⚠️ Trampa del examen: Global Administrator no es Owner de las subscriptions. Un Global Admin administra identidades, no recursos de Azure. Para tomar control necesita ir a Entra ID → Properties → Access management for Azure resources → Yes (elevate access), lo que le da User Access Administrator en el scope raíz /. Si la pregunta dice "el Global Admin no ve la subscription", la respuesta es elevar acceso, no crear otro rol.

Usuarios: Member vs Guest, cloud vs synced Identidades
Los dos ejes que tenés que separar
  • Eje 1 — userType: Member o Guest. Define los permisos por defecto sobre el directorio.
  • Eje 2 — Source (origen): Microsoft Entra ID (cloud-only) o Windows Server AD (sincronizado con Entra Connect) o External Azure AD (invitado B2B).
  • Son independientes: podés tener un guest cloud-only, y un member sincronizado. El examen mezcla los dos ejes a propósito.

UPN y dominios
  • El UPN (User Principal Name) es el identificador de inicio de sesión: usuario@dominio. El dominio tiene que ser un verified domain del tenant.
  • Para verificar un dominio custom se agrega un registro TXT o MX en el DNS público del dominio.

  • El UPN tiene que ser único en el tenant, y sigue reservado mientras el usuario esté en la papelera.

⚠️ Trampa del examen: un grupo dinámico es o de usuarios o de dispositivos, nunca los dos. Al crearlo elegís Dynamic User o Dynamic Device y la regla solo admite el prefijo correspondiente. Si el escenario pide "un grupo con todas las laptops de Marketing y sus dueños", la respuesta es dos grupos. Segunda trampa del mismo combo: una vez que el grupo es dinámico, no podés agregar miembros manualmente — y si cambiás el tipo de Assigned a Dynamic, se pierden los miembros cargados a mano.
Role-assignable groups: para asignar roles de Entra ID a un grupo hay que crearlo con la opción "Microsoft Entra roles can be assigned to the group" = Yes. Esa opción solo se define al crear el grupo y no se puede cambiar después. Además el grupo tiene que ser Security con membresía Assigned (un grupo dinámico no puede ser role-assignable) y requiere P1. Ojo: esto es distinto de asignar RBAC de Azure a un grupo, que funciona con cualquier security group.
ℹ️ Group-based licensing requiere P1 y no procesa grupos anidados: la licencia se aplica solo a los miembros directos del grupo. Y una licencia heredada de un grupo no se puede quitar en el usuario — hay que sacarlo del grupo. Los errores de asignación (MutuallyExclusiveViolation, CountViolation, etc.) se detallan en Licencias.

Colaboración B2B y guests Externos
Qué pasa cuando invitás a alguien
  • Se crea un objeto de usuario guest en TU tenant, con userType = Guest y UPN del tipo ana_contoso.com#EXT#@tutenant.onmicrosoft.com.
  • Ese objeto no tiene credenciales propias: la autenticación la hace el home tenant del invitado (o su cuenta Microsoft / Google / one-time passcode por email). Las passwords y la MFA del invitado viven en su tenant, no en el tuyo.
  • Mientras no acepte la invitación queda en estado PendingAcceptance, pero el objeto ya existe y ya se le pueden asignar grupos, roles y RBAC.
  • Para sacarle el acceso, borrás el objeto guest de tu tenant. La cuenta original en el tenant de origen no se toca.

Roles y mínimo privilegio
  • Guest Inviter: el rol de mínimo privilegio para invitar guests sin poder tocar nada más del directorio. Es la respuesta correcta cuando el escenario pide "que puedan invitar externos pero no administrar usuarios".
  • User Administrator también puede invitar, pero es más privilegio del necesario.
  • Las Cross-tenant access settings controlan por tenant partner qué se permite en inbound/outbound, e incluyen la opción de confiar en la MFA del tenant de origen para no pedirle al guest doble MFA.
B2B vs B2C vs ADFS: qué es cada uno

El examen mezcla estos nombres. Son productos distintos, no sinónimos de “login externo”.

  • B2B (Business-to-Business) — colaboración entre organizaciones. Invitás a empleados de otro tenant (o una cuenta Microsoft) como guest en el tuyo. Ellos siguen autenticándose en su home tenant con su UPN de siempre (user@company2.com). Tu tenant solo guarda el objeto guest. Incluido en Entra ID, rápido y sin costo extra para este escenario. Es el camino correcto cuando piden SSO con las credenciales que ya tienen.
  • B2C (Business-to-Consumer) — ahora parte de Entra External ID para clientes. Es un tenant aparte pensado para consumidores de una app pública: se registran con email, one-time passcode o redes (Google, Facebook, Apple). No es para que cinco empleados de Company2 entren a las apps internas de Company1. Tiene facturación por MAU y el signup no usa el UPN corporativo de Company2 como IdP de la empresa.
  • ADFS (Active Directory Federation Services) — rol de Windows Server on-prem. Es un Security Token Service (STS): el usuario llega a la app en la nube, Entra lo redirige a tus servidores ADFS, ADFS valida contra AD DS y emite un token SAML/WS-Fed. También se puede federar con el AD de otra empresa. Requiere granja ADFS + Web Application Proxy en DMZ, certificados, HA y parches. Ni rápido ni gratis.
  • Cuentas en el AD de Company1 — identidades nuevas que Entra Connect sincroniza. Tendrían password (y UPN) de Company1, no SSO con company2.com. Es el anti-patrón de “usar las credenciales que ya tienen”.

Administrative Units (AU) Delegación
Para qué existen
  • Una AU es un contenedor lógico para acotar el scope de administración delegada. Es el equivalente conceptual de una OU de AD DS, pero solo para delegar permisos: no sirve para aplicar Group Policy ni para organizar objetos jerárquicamente.
  • Puede contener usuarios, grupos y dispositivos. Un mismo objeto puede pertenecer a varias AUs.
  • Membresía asignada o dinámica (con reglas iguales a las de grupos dinámicos, y con la misma limitación: usuarios o dispositivos, no ambos).
  • Requiere Entra ID P1. Crear o borrar AUs pide Global Administrator o Privileged Role Administrator.
Roles que se pueden asignar con scope de AU
  • User Administrator · Groups Administrator · Helpdesk Administrator · Password Administrator · Authentication Administrator · License Administrator · Cloud Device Administrator (para dispositivos).
  • El patrón de pregunta: "el helpdesk de la sucursal X tiene que resetear passwords solo de la gente de X" → AU con los usuarios de X + Helpdesk (o Password) Administrator con scope de esa AU.
⚠️ Trampa del examen: Global Administrator no se limita con una AU. Los roles que ya son tenant-wide siguen viendo todo el directorio; meterlos en una AU no los recorta. La AU restringe al administrador delegado, no al objeto: si le asignás a alguien User Administrator a nivel tenant y además con scope de AU, gana el permiso más amplio. Para achicar de verdad hay que quitar la asignación tenant-wide.
ℹ️ Si además necesitás que ni siquiera los Global Admins toquen esos objetos sin activar permisos explícitos, eso es Restricted Management Administrative Units, que requiere P1 (una licencia P1 por cada administrador de la AU; los miembros solo necesitan Free).

Device settings (Entra ID → Devices → Device settings)
  • Users may join devices to Microsoft Entra ID: All / Selected (usuarios o grupos) / None. Aplica solo al join, no al register.
  • Users may register their devices: All / None. Queda forzado en All si tenés Intune o MAM habilitado.
  • Require Multifactor Authentication to register or join devices: Yes / No. Microsoft recomienda hacerlo con Conditional Access en lugar de este toggle.
  • Maximum number of devices per user: valores 5, 10, 20, 50, 100, Unlimited, con 50 por defecto. Cuenta dispositivos Entra joined y Entra registered juntos. Los hybrid Entra joined no cuentan hacia este límite.

⚠️ Trampa del examen: el límite de Maximum number of devices per user se evalúa al momento del join/register, y borrar o deshabilitar un dispositivo en el portal no lo saca del equipo: la máquina sigue funcionando localmente, lo que pierde es el acceso SSO a recursos y el token. La otra confusión clásica: join no es lo mismo que enroll — unir el dispositivo a Entra ID no lo inscribe en Intune salvo que configures el automatic enrollment.
💡 Regla mnemotécnica para elegir: personal → registered; corporativo sin on-prem → joined; corporativo con dominio AD DS → hybrid joined. Si el escenario menciona "ya tenemos Active Directory" y "las apps usan autenticación integrada de Windows", es hybrid sí o sí.

Self-Service Password Reset (SSPR) Clásico
Scope: las únicas tres opciones
  • None — SSPR deshabilitado (default).
  • Selected — habilitado para un solo grupo. No podés elegir dos grupos: si necesitás varios conjuntos de usuarios, armás un grupo que los contenga (podés anidar security groups).
  • All — todos los usuarios del tenant.
Yes/No: SSPR en híbrido + cloud-only

Cuentas sincronizadas (Entra + AD DS) y algunas solo en la nube. Hay que desplegar SSPR.

Mecánica de asignación
  • Las licencias de Entra ID son por usuario. Se asignan al usuario directamente o a través de un grupo (group-based licensing, que ya es P1).
  • El usuario necesita Usage location configurada antes de poder recibir una licencia. Sin usage location la asignación falla.
  • Una licencia heredada de un grupo no se puede quitar desde el usuario: se saca al usuario del grupo o se quita la licencia del grupo.
  • La edición Free tiene cuota por defecto de 50.000 objetos de directorio (300.000 si el tenant tiene un dominio verificado). El 500.000 de la página de precios es un techo que se pide por soporte; P1/P2 no eliminan esta cuota.
  • Microsoft 365 E3 incluye Entra ID P1; Microsoft 365 E5 incluye P2.
Errores de group-based licensing (Graph)

Cuando un script de Microsoft Graph PowerShell falla al asignar licencias por grupo, el código no es genérico: cada nombre mapea a una causa. El examen te tira el error y cuatro definiciones; tenés que emparejarlas.

Error en GraphCausaQué hacés
MutuallyExclusiveViolation Un producto del grupo trae un service plan que choca con otro plan que el usuario ya tiene por otro producto (p. ej. Exchange Plan 1 y Plan 2). Sacar al usuario de uno de los grupos, o deshabilitar el plan en conflicto en una de las asignaciones.
CountViolation No hay licencias suficientes para un producto del grupo. Comprar más SKUs o recuperar licencias no usadas.
DependencyViolation Un service plan del grupo exige otro plan habilitado (en el mismo u otro producto) para funcionar. Habilitar el plan dependiente; no deshabilitar el prerequisito.
ProhibitedInUsageLocationViolation El producto no está disponible en la usage location del usuario por leyes locales. También falla si el usuario no tiene usage location. Corregir usageLocation o no asignar ese SKU a esa geografía.
Microsoft Graph PowerShell — asignar y diagnosticar
Connect-MgGraph -Scopes "User.Read.All","Group.ReadWrite.All","Organization.Read.All"

# Usage location (obligatoria antes de licenciar)
Update-MgUser -UserId ana@contoso.com -UsageLocation "AR"

# SKUs del tenant: id, consumidas, disponibles
Get-MgSubscribedSku | Select-Object SkuPartNumber, SkuId, ConsumedUnits

# Asignar el SKU al grupo (group-based licensing)
Set-MgGroupLicense -GroupId $groupId -AddLicenses @{SkuId = $skuId} -RemoveLicenses @()

# Miembros del grupo cuya licencia quedó en error  ← cmdlet clave
Get-MgGroupMemberWithLicenseError -GroupId $groupId

# Causa exacta: State + Error por usuario
Get-MgUser -UserId ana@contoso.com -Property LicenseAssignmentStates |
  Select-Object -ExpandProperty LicenseAssignmentStates |
  Format-Table SkuId, State, Error, AssignedByGroup

# Planes ya asignados al usuario (para ver el conflicto)
Get-MgUserLicenseDetail -UserId ana@contoso.com
  • Set-MgUserLicense es asignación directa al usuario. Group-based usa Set-MgGroupLicense. El error vive igual en licenseAssignmentStates del usuario.
  • AssignedByGroup distinto de $null = la licencia vino del grupo. $null = asignación directa.
  • State en error: Error o ActiveWithError. El campo Error trae el nombre (MutuallyExclusiveViolation, etc.).
⚠️ Trampa del examen: “el script de Graph falla con MutuallyExclusiveViolation”. No es falta de licencias (CountViolation), ni un plan que depende de otro (DependencyViolation), ni restricción geográfica (ProhibitedInUsageLocationViolation). Es un service plan del grupo que choca con otro plan que el usuario ya tiene por un producto distinto. Para verlo: Get-MgGroupMemberWithLicenseError y después LicenseAssignmentStates.Error del usuario.
ℹ️ Para features que se licencian "por quien la usa": en dynamic groups se necesita P1 por cada usuario miembro del grupo; en Administrative Units, P1 por cada administrador con scope de AU. El examen rara vez lo pregunta al detalle, pero explica por qué la respuesta nunca es "una sola licencia P1 para el tenant".

Entitlement Management (Identity Governance) P2 · Graph

No es Azure RBAC ni “meter gente a un grupo a mano”. Es el motor de Entra ID Governance para dar (y sacar) un paquete de accesos a escala: grupos, apps y sitios de SharePoint, con solicitud, aprobación y vencimiento. Licencia: Entra ID P2 o Entra ID Governance. En Graph: módulo Microsoft.Graph.Identity.Governance y permiso EntitlementManagement.ReadWrite.All.

Las cuatro piezas (de afuera hacia adentro)
Catálogo
General u otro
→
Recursos
grupo, app, sitio
→
Access package
el paquete que se pide
→
Policy
quién, aprobación, caduca
  • Catálogo: caja que contiene los recursos que podés meter en paquetes. El tenant trae uno llamado General (no lo creás). Podés crear catálogos extra para delegar (Marketing maneja el suyo). Todo access package vive dentro de un catálogo.
  • Recurso del catálogo: un grupo/app/sitio que ya agregaste a esa caja. El ID que usa Entitlement Management no es el object ID de Entra del grupo: es el ID del recurso dentro del catálogo.
  • Access package: el “combo” que el usuario pide o que un admin le asigna. Adentro van roles de esos recursos (p. ej. Member del grupo Sales, no Owner).
  • Assignment policy: quién puede pedirlo (empleados, guests, un grupo), si hace falta aprobación, cuántos días dura el acceso. Sin policy el paquete existe pero nadie entra.
Por qué Graph siempre empieza por el ID del catálogo

Casi todos los cmdlets piden -AccessPackageCatalogId (o un body con catalog.id). Si la política dice “usá el catálogo General”, el primer comando es buscar ese objeto y guardar su Id. Recién después: agregar el grupo Sales, listar recursos, listar roles, crear el access package.

OrdenQué hacésCmdlet
1 · primeroObtener el ID de GeneralGet-MgEntitlementManagementCatalog
2Agregar Sales al catálogo (como recurso)New-MgEntitlementManagementResourceRequest
3Listar recursos del catálogoGet-MgEntitlementManagementCatalog -ExpandProperty resources
4Roles del recurso (Member / Owner)Get-MgEntitlementManagementCatalogResourceRole (o equivalente)
5Crear access package + policyNew-MgEntitlementManagementAccessPackage
 
Connect-MgGraph -Scopes "EntitlementManagement.ReadWrite.All","Group.ReadWrite.All"

# Paso 1 — SIEMPRE primero
$catalog = Get-MgEntitlementManagementCatalog -Filter "displayName eq 'General'"
$catalog.Id

# Paso 2 — el grupo Sales como recurso del catálogo
$g = Get-MgGroup -Filter "displayName eq 'Sales'"
New-MgEntitlementManagementResourceRequest -BodyParameter @{
  requestType = "adminAdd"
  resource    = @{ originId = $g.Id; originSystem = "AadGroup" }
  catalog     = @{ id = $catalog.Id }
}
⚠️ Trampa del examen: “Graph PowerShell, grupo Sales, catálogo General, ¿qué hacés primero?”. Retrieve the catalog identifier. No “add the Sales group” ni “retrieve catalog resources” ni “retrieve resource roles”: todos esos cmdlets necesitan el ID del catálogo. General ya existe; no lo creás. PIM es otra feature (roles privilegiados just-in-time), no este flujo.
