Los dos tipos de dato
  • Metrics: números en una serie temporal. Livianos, indexados por tiempo, latencia de segundos. Viven en una time-series database propia (no en el workspace). Retención de 93 días para platform metrics.
  • Logs: registros con muchos campos y contexto (quién, qué, con qué resultado). Latencia de minutos. Se guardan en un Log Analytics Workspace y se consultan con KQL.

⚠️ Trampa del examen: los Insights (Application Insights, VM Insights, Container Insights, Network Insights, Storage Insights) no son un tercer tipo de dato. Activity Log en detalle
  • Es a nivel de subscription, no de recurso individual.
  • Categorías clásicas: Administrative, Service Health, Resource Health, Alert, Autoscale, Policy, Recommendation, Security.
  • Responde a "¿quién borró la VM y cuándo?" — no responde "¿por qué se cayó el servicio adentro de la VM?".
  • Retención por defecto 90 días, y no se puede extender in situ. Para guardarlo más tiempo lo exportás con una Diagnostic Setting a Log Analytics, Storage o Event Hub.
  • Una vez exportado a un workspace, se consulta con KQL en la tabla AzureActivity.
⚠️ Trampa del examen: "Necesitás retener los registros de operaciones administrativas por 1 año con el menor costo posible". La respuesta no es cambiar la retención del Activity Log (no existe esa opción). Es crear una Diagnostic Setting a nivel de subscription exportando el Activity Log a una Storage Account. Si la pregunta pide además consultarlo con KQL, entonces el destino es Log Analytics Workspace.

Una Diagnostic Setting es la configuración que le dice a un recurso: "estas categorías de logs y estas métricas, mandálas a estos destinos". Sin ella, los resource logs simplemente no se recolectan y se pierden para siempre.

Reglas que hay que saber de memoria
  • Un mismo recurso puede tener varias diagnostic settings — es la forma de mandar el mismo log a Storage (archivo barato) y a Log Analytics (análisis) al mismo tiempo.
  • Cada setting define qué categorías se envían: podés mandar solo AuditEvent a Storage y todo a Event Hub.
  • También podés exportar AllMetrics por esta vía — así las métricas terminan en el workspace y quedan consultables con KQL en la tabla AzureMetrics.
  • El destino Storage Account no puede ser premium para este propósito, y suele exigirse en la misma región del recurso.
  • Se pueden crear en masa con Azure Policy usando efecto DeployIfNotExists — la respuesta típica a "asegurate de que todos los recursos nuevos manden logs sin intervención manual".
⚠️ Trampa del examen: la pregunta clásica es "creaste un Log Analytics Workspace y no ves logs de tu Application Gateway / NSG / Key Vault, ¿qué falta?". Nunca es el agente (esos recursos PaaS no tienen agente): falta la Diagnostic Setting apuntando al workspace. Los agentes son solo para el sistema operativo invitado.
💡 Nemotecnia: Metrics vienen solas, Logs hay que invitarlos. Platform metrics aparecen sin hacer nada; los resource logs necesitan una invitación formal (Diagnostic Setting).

Agentes: AMA, DCR y Azure Arc Modernizado

Para todo lo que pase adentro del sistema operativo — contadores de performance, Event Log de Windows, Syslog de Linux, archivos de log de una app — Azure no ve nada desde afuera. Necesitás un agente.

AgenteEstadoConfiguraciónNotas

Log Analytics agent (MMA / OMS) retirado Config a nivel de workspace Migrar a AMA es la respuesta correcta si aparece.
Azure Diagnostics extension (WAD / LAD) legacy Config XML/JSON por VM Mandaba a Storage y a metrics. Superado por AMA.
Dependency agent complemento Junto a AMA Solo si querés el mapa de dependencias de VM Insights.
Data Collection Rules (DCR) — el corazón de AMA
  • Un DCR define tres cosas: qué se recolecta (data sources), cómo se transforma opcionalmente, y a dónde va (destinations, típicamente un workspace).
  • Relación muchos a muchos: un DCR se asocia a muchas máquinas, y una máquina puede tener varios DCR asociados. Esto permite separar "recolectar Syslog de seguridad" de "recolectar contadores de performance".
  • La asociación se llama DCRA (Data Collection Rule Association) y es un recurso propio.
  • El DCR es regional: debe estar en la misma región que el workspace destino y que las VMs asociadas.
  • Los Data Collection Endpoints (DCE) son puntos de ingesta que se usan para escenarios como Private Link, custom logs y máquinas en redes aisladas.

Log Analytics Workspace Diseño

Es el contenedor donde viven los logs. Es un recurso de Azure normal: vive en un resource group, en una región, y tiene RBAC propio.

Características que se preguntan
  • Retención por defecto: 30 días (interactiva). Analytics se puede subir hasta 730 días (2 años). Sentinel o App Insights workspace-based: 90 días incluidos. Se puede fijar por tabla (ej. SecurityEvent largo, Perf corto).
  • Archive / long-term: hasta 12 años (totalRetentionInDays ≤ 4383). No es query interactiva: hace falta un search job (asíncrono) que deja el recorte en una tabla de resultados.
  • El costo tiene dos componentes: ingesta por GB y retención más allá del período incluido. Hay commitment tiers por volumen. La palanca barata de logs verbosos es el plan de tabla, no otro workspace.
  • Un workspace puede recibir datos de múltiples suscripciones y regiones, incluso de otros tenants con configuración adecuada. La región del workspace es donde viven los datos (soberanía).
  • El tipo de recurso es Microsoft.OperationalInsights/workspaces. Registrar: az provider register --namespace Microsoft.OperationalInsights. Microsoft.Insights cubre alertas y métricas, no el workspace.

¿Un workspace o varios?
  • Uno solo (centralizado): correlacionás todo con una query, administración simple, mejor aprovechamiento de commitment tiers. Es el default recomendado.
  • Varios cuando hay: soberanía de datos (los logs de la UE no pueden salir de la UE), aislamiento por RBAC entre equipos o clientes, chargeback por unidad de negocio, o retenciones legalmente distintas.
  • Con varios workspaces todavía podés hacer cross-workspace queries con workspace() y union, pero es más incómodo.
  • Ojo con los cargos de egreso si mandás datos entre regiones a un workspace centralizado.

KQL: los operadores que se preguntan Lectura, no escritura

Una query KQL empieza siempre con una tabla y encadena operadores con el pipe |. Cada operador recibe la tabla del anterior y devuelve otra tabla. Se lee de arriba hacia abajo.

OperadorQué haceEjemplo
searchBusca un texto en todas las columnas (y hasta en todas las tablas). Cómodo pero caro.search "error"
whereFiltra filas por condición. Ponelo lo más arriba posible.where Level == "Error"
projectSelecciona qué columnas devolver (y en qué orden)project Computer, TimeGenerated
project-awayDevuelve todo menos las columnas indicadasproject-away TenantId
extendCrea una columna calculada nuevaextend GB = Size / 1024 / 1024 / 1024
summarizeAgrega filas; con by agrupasummarize count() by Computer
order by / sort byOrdena. Son sinónimos exactos. desc por defectoorder by TimeGenerated desc
topOrdena y corta en N. Equivale a sort + taketop 10 by CounterValue desc
take / limitDevuelve N filas sin garantía de orden. Sinónimostake 100
distinctValores únicos de las columnas indicadasdistinct Computer
countCuenta filas del resultado (operador, no función)| count
joinCombina dos tablas por una clavejoin kind=inner (Perf) on Computer
unionApila filas de varias tablas (no necesita clave)union Event, Syslog
renderDibuja el resultado como gráficorender timechart
letDefine una variable o subquery reutilizablelet umbral = 90;
Tiempo: lo que aparece en casi toda query
  • TimeGenerated es la columna estándar de timestamp en todas las tablas del workspace.
  • ago(1h), ago(7d), ago(30m) — punto en el pasado relativo a ahora. Unidades: d, h, m, s.
  • bin(TimeGenerated, 5m) — redondea el timestamp hacia abajo en cubetas. Es lo que hace posible un timechart: agrupa por intervalos.
  • now(), startofday(), between(datetime(...) .. datetime(...)).
Comparaciones: la letra chica que se pregunta
  • == es case-sensitive; =~ es case-insensitive. (!= y !~ son sus negaciones.)
  • contains busca una subcadena en cualquier parte, case-insensitive. contains_cs es la variante sensible a mayúsculas.
  • has busca un término completo (palabra indexada). Es mucho más rápido que contains porque usa el índice. Preferilo cuando buscás una palabra entera.
  • startswith, endswith, in (...), matches regex.
  • Ejemplo de la diferencia: has "win" no matchea "Windows"; contains "win" sí.

Query 1 — VMs que no reportan hace más de 15 minutos (detección de máquinas caídas):

Heartbeat
| where TimeGenerated > ago(24h)
| summarize UltimoLatido = max(TimeGenerated) by Computer
| where UltimoLatido < ago(15m)
| order by UltimoLatido asc

Query 2 — CPU promedio por máquina en cubetas de 5 minutos, graficado:

Perf
| where ObjectName == "Processor" and CounterName == "% Processor Time"
| where TimeGenerated > ago(6h)
| summarize CPUProm = avg(CounterValue) by Computer, bin(TimeGenerated, 5m)
| render timechart

Query 3 — quién borró recursos en los últimos 7 días (Activity Log ya exportado al workspace):

AzureActivity
| where TimeGenerated > ago(7d)
| where OperationNameValue has "DELETE"
| where ActivityStatusValue =~ "Success"
| project TimeGenerated, Caller, OperationNameValue, ResourceGroup, _ResourceId
| order by TimeGenerated desc

Query 4 — top 10 de errores por computadora con percentil de duración:

Event
| where TimeGenerated > ago(1d)
| where EventLevelName == "Error"
| summarize Errores = count(), Ultimo = max(TimeGenerated) by Computer, Source
| top 10 by Errores desc
⚠️ Trampa del examen: confundir take con top. take 10 te devuelve 10 filas cualquiera, sin orden garantizado — sirve para espiar el shape de una tabla, nunca para "los 10 más altos". Para eso es top 10 by Columna desc. Otra que cae seguido: summarize count() es una función de agregación dentro de summarize, mientras que | count a secas es un operador que devuelve una sola fila con el total.
💡 Kinds de join que conviene reconocer: innerunique (el default en KQL, deduplica la clave del lado izquierdo), inner, leftouter, rightouter, fullouter, leftanti / rightanti (las filas que no matchean — buenísimo para "qué servidores están en el inventario pero no reportan").

Action Groups

Un action group es una lista reutilizable de destinatarios y acciones. Se crea una vez y se referencia desde muchas alert rules.

  • Notificaciones: Email, SMS, Azure app push notification, Voice, y "Email Azure Resource Manager role" (mandarle a todos los que tengan un rol dado en la suscripción).
  • Acciones: Webhook, Secure Webhook, Logic App, Azure Function, Automation Runbook, Event Hub, e ITSM (ServiceNow, System Center Service Manager, etc., vía ITSM Connector / ITSMC).
  • Si la pregunta pide remediar automáticamente (reiniciar la VM, escalar), la respuesta pasa por Automation Runbook, Function o Logic App dentro del action group. Si pide abrir un ticket en SCSM/ServiceNow con mínimo esfuerzo, es ITSMC + acción ITSM en el action group, no un runbook a SCSM.
  • Webhook, Function, Logic App y Runbook no tienen el rate limit de SMS/voz/email: si la alerta dispara cada minuto, esas acciones corren las 60 veces.

Estados y supresión
  • Monitor condition (la determina el sistema): Fired o Resolved. Las metric alerts se auto-resuelven cuando la condición deja de cumplirse.
  • Alert state (la manejás vos): New → Acknowledged → Closed. Cambiarla no afecta a la monitor condition.
  • Alert processing rules (antes "action rules"): suprimen notificaciones o agregan acciones en bloque. El caso canónico es silenciar alertas durante una ventana de mantenimiento planificado sin tener que deshabilitar cada regla una por una.
⚠️ Trampa del examen: si el enunciado pide la menor latencia posible para reaccionar a un umbral numérico, la respuesta es metric alert, no log alert — aunque el dato también exista en el workspace. La log alert tiene que esperar a que el dato se ingiera (minutos) más el intervalo de evaluación. Al revés: si necesitás correlacionar varias fuentes o buscar un patrón en texto, la metric alert no puede y va sí o sí log alert.
⚠️ Trampa del examen: el action group no es opcional para notificar. Muchos escenarios describen una alerta "que no notifica a nadie" — la falla es que la regla se creó sin action group asociado, o que el action group existe pero el destinatario no está en él. Y recordá: los action groups son un recurso global aparte, reutilizable entre reglas.

Network Watcher es un servicio regional: se habilita por región y por suscripción, y una instancia solo puede diagnosticar recursos de esa región. Históricamente Azure lo crea automáticamente en un resource group llamado NetworkWatcherRG cuando creás una VNet en una región nueva. Next Hop A dónde enruta el paquete: Internet, VirtualNetwork, VirtualNetworkPeering, VirtualNetworkGateway, VirtualAppliance, None. Te devuelve también el ID de la route table que decidió. "El tráfico no llega y sospechamos de una UDR / de la NVA"
Effective security rules La unión resuelta de todas las reglas NSG que aplican a una NIC (NSG de NIC + NSG de subnet), incluyendo las default. "Quiero ver todas las reglas efectivas sobre esta VM"
Connection Troubleshoot Test de conectividad puntual de origen a destino: latencia, saltos y qué componente bloquea. "Probá si la VM A puede llegar al puerto 443 de B, una vez"
Connection Monitor Monitoreo de conectividad continuo y en el tiempo, con métricas de latencia, pérdida y alertas. Híbrido: Azure (VM/VMSS) y on-prem (agente) hacia el mismo destino (URL, IP, Storage). "Comparar latencias on-prem vs Azure hacia el mismo endpoint"
Packet Capture Captura de paquetes real desde la VM, guardada en Storage Account o disco local. Requiere la extensión de Network Watcher agent en la VM. "Necesitamos analizar el contenido del tráfico en Wireshark"
VPN Troubleshoot Diagnóstico de VPN Gateway y conexiones site-to-site; resultados a una Storage Account. "El túnel S2S no levanta"
VNet Flow Logs (reemplazo de NSG Flow Logs) Registro de todos los flujos permitidos y denegados a nivel de VNet/subnet. Se escriben a una Storage Account (JSON). Traffic Analytics Los flow logs procesados y enriquecidos en un Log Analytics Workspace: mapas de tráfico, top talkers, geografía, puertos abiertos, hosts maliciosos. "Visualizar patrones de tráfico y detectar anomalías"
Topology Vista interactiva de la red: recursos y relaciones, no un diagnóstico de un paquete. "Visualizar la arquitectura de red que heredé"
Usage + quotas Cuántos recursos de red hay vs el límite de la región/subscription. "No me deja crear otra Public IP / VNet en East US"

Script del examen: packet capture de SFTP desconocido

La VM inicia la conexión (puerto local efímero). El servicio remoto es desconocido → cualquier IP. SFTP va por SSH = TCP 22, no FTP 21.

$res = Get-AzResource | Where-Object {
  $_.ResourceType -eq "Microsoft.Network/networkWatchers" -and $_.Location -eq "EastUS"
}
$networkWatcher = Get-AzNetworkWatcher -Name $res.Name -ResourceGroupName $res.ResourceGroupName
$diagnosticSA = Get-AzStorageAccount -ResourceGroupName Diagnostics-RG -Name "Diagnostics-Storage"

$filter1 = New-AzPacketCaptureFilterConfig -Protocol TCP `
  -RemoteIPAddress "0.0.0.0-255.255.255.255" `
  -LocalIPAddress "10.0.0.3" -LocalPort "1-65535" -RemotePort "22"

New-AzNetworkWatcherPacketCapture -NetworkWatcher $networkWatcher `
  -TargetVirtualMachineId $vm.Id `
  -PacketCaptureName "Capture SFTP Traffic" -StorageAccountId $diagnosticSA.Id `
  -TimeLimitInSeconds 60 -Filter $filter1
